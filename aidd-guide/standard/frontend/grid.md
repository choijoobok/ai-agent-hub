# 그리드 — 화면 뼈대 · `api` 선언 · 저장

> **편집 폼을 두지 않는다. 이것이 나머지의 전제다.**
> 화면에 남는 폼은 조회조건 하나뿐이며, **등록은 그리드의 새 행이고 수정은 셀 더블 클릭 편집**이다. 별도 수정 버튼이나 편집 모드 전환을 두지 않는다.
> 배치·1:1 항목·하단 탭·엑셀 기본값은 [마스터-디테일 §1](../../playbook/master-detail.md)을 따른다.
>
> 컬럼은 [grid-columns.md](./grid-columns.md), 정렬·필터·검증은 [grid-validation.md](./grid-validation.md).

## 1. 왜 폼이 없나

| | |
|---|---|
| **저장 경로가 하나가 된다** | 폼을 함께 두면 **같은 테이블에 저장 경로가 둘**이 되고 액션 판정도 두 API 를 따라간다 |
| **컴포넌트가 하나로 닫힌다** | 폼 상세는 화면마다 레이아웃이 갈린다. 그리드는 크롬 하나로 전 화면이 같다 |
| **화면 전환이 없다** | 목록에서 보고 그 자리에서 고친다 |

**상태 플래그가 섞인 테이블도 폼으로 도망가지 않는다** — 지켜야 할 규칙은 폼이 아니라
**컬럼별 편집 가능 여부**로 지킨다.

> **없앤 것은 *행을 편집하는 폼* 이다.** 실행 버튼이 인자를 받는 **파라미터 모달**은
> 그리드 행이 아니라 **API 호출의 인자**를 받으므로 이 규칙 밖이다. **엑셀 업로드 탭**도
> 밖이다 — 저장 API 를 새로 만들지 않고 **업무 탭의 `save` 를 그대로 부른다.**
> **판별 기준은 *같은 테이블에 저장 경로가 둘이 되는가* 다.**

## 2. 화면 뼈대

```tsx
<FillColumn>                        // 뿌리 — 그리드가 남는 높이를 채운다
  {searchHeader}                    // useSearchFormHeader()
  <DataGrid {...grid} />            // useGridController 가 만든 것
</FillColumn>
```

**그리드는 남는 높이를 채운다 — 셸이 그것을 줘야 한다.** 콘텐츠 영역의 높이가 `auto` 면
화면의 `height: 100%` 가 **0 으로 풀려 그리드가 줄 하나 없이 접힌다.**

### 크롬 — 모든 그리드가 같은 자리에 같은 것을 둔다

```
┌ 사용자 목록      [조회] [추가] [저장] [잠금 해제]         [⤓▾] [⚙] ┐
│  ↑ 제목           ↑ api 선언이 채운다                      ↑ 도구  │
├────────────────────────────────────────────────────────────────────┤
│  그리드 본문                                                        │
├────────────────────────────────────────────────────────────────────┤
│ 총 128건 · 7페이지      ‹ 1 2 3 … 7 ›              20건씩 ▾        │
└────────────────────────────────────────────────────────────────────┘
```

**화면마다 다르면 사용자가 화면마다 다시 배운다.**

**검색 폼의 버튼은 초기화 하나다** — **조회는 그리드가 갖는다.**

## 3. 그리드가 하는 일은 전부 `api` 에 있다

| 키 | 개수 | 무엇 |
|---|---|---|
| `read` | **하나** | 조회 |
| `save` | **하나** | **일괄 저장 — 등록/수정/삭제로 쪼개지 않는다** |
| `actions` | **여럿** | 그 밖의 모든 버튼 |

**칸의 목록은 [declarations.md](./declarations.md) §3 이 갖는다** — 여기에 옮겨 적지 않는다.
한때 이 자리에 요약이 있었고 **낡았다**: 소스에 없는 `params` 를 `read`·`save` 에 달아
두었다. 요약이 둘이면 갈렸을 때 **어느 쪽이 참인지 알 방법이 없다**.

**`params` 는 `actions` 만 갖는다.** 조회 조건은 `api` 가 아니라 컨트롤러가 받는다
(`useGridController({ params })`) — 그것은 **폼이 검증해서 주는 것**이라 층이 다르다.
**API 를 부르지 않는 버튼은 `controls` 에 선언한다.**

> **`actions` 를 `execute` 라 부르지 않는다** — 액션 `EXECUTE` 와 섞인다.
> **잠금 해제는 `actions` 의 하나이지만 액션은 `SAVE`** 다.
> **선언에 액션을 적지 않는다** — 액션은 **경로 접두**가 정하며, 선언에 또 적으면
> 같은 사실이 두 곳에 표현되어 시드와 어긋난다.

### 버튼은 자동으로 렌더링된다

**화면이 손으로 놓지 않는다.** `api` 선언을 읽어 그리드 헤더가 만든다.

| | |
|---|---|
| 순서 | **조회 → 추가 → 저장 → `actions` 선언 순서** |
| 라벨 | 추가의 표시는 **추가**로 통일한다. `label` 메시지 키를 쓰고, 없으면 `read`·`save`는 표준 라벨 |
| **권한** | 각 URL 의 액션을 유효 권한과 대조해 **없으면 감춘다** |
| 비활성 | 실행 중 잠금 · 마스터-디테일 상태 · 대상 없음 |

> **화면이 `<Permission>` 을 손으로 두르지 않는다.** 버튼과 URL 이 한 선언에 있으므로
> 판정에 필요한 것이 이미 다 있다. 손으로 두르면 **버튼을 추가하고 권한을 빠뜨리는**
> 경로가 열린다.

**행 추가는 `addRow` 가 정한다 — 선언하지 않으면 버튼이 없다.**
추가의 방식이 빈 행·조회 팝업 선택·기준정보 콤보 중 무엇인지는 화면 요건을 따른다. 기본 추가와 별도 추가 명령을 중복 표시하지 않는다.
**엑셀 다운로드와 그리드 설정은 `api` 에 없다** — 프론트가 자기 데이터로 만들고,
설정은 개인화다. **서버가 만드는 엑셀만** `actions` 의 하나가 된다.

**그래서 ②를 끄는 것도 `api` 로 하지 않는다.** `api` 를 빼면 저장 버튼이 함께 사라진다 —
**`excel={false}`** 가 그 자리다([playbook/excel-download.md](../../playbook/excel-download.md) 넷째 갈래).

## 4. 저장은 버튼을 누를 때 한 번 일어난다

셀을 고치면 **행에 상태가 붙을 뿐** 서버로 나가지 않는다. 저장을 누르면 **추가·수정·삭제
상태의 행을 한 번에** 보낸다.

- **API 는 하나다.** 행 상태는 URL 이 아니라 **페이로드 안**에 있다.
- **액션도 `SAVE` 하나다.** 행 상태별 권한은 **API 경계에서 집행할 수 없어** 장식이 된다.
- **컬럼 필터로 숨겨진 행도 함께 저장된다.** 필터는 **표시만** 거른다 — 그래서 저장 전
  확인에서 **보이지 않는 변경 행이 몇 건인지** 알린다. 알리지 않으면 *"내가 안 고친 것이
  저장됐다"* 가 된다.

흐름은 **검증 → 확인 → 저장 → 재조회**다.

**저장은 `issues` 를 갈아 끼운다.** 첫 줄이 `validate` 를 다시 돌려 그 결과로 **덮으므로**,
밖에서 넣어 둔 오류는 **저장을 막지 못한다** — 붉은 셀이 보이는 채로 요청이 나간다.
막아야 하는 오류는 `api.save.validate` 안에 있어야 한다 — *파일을 읽을 때 붙인 오류가
저장을 막는다* 로 읽기 쉬운 자리다.

**실패는 붉은 셀과 표로 함께 말한다** — 셀만 칠하면 안 보이는 행의 실패를 놓치고, 표만 내면
*어느 줄인가* 를 글에서 읽어 내야 한다. 규칙은 [save-errors.md](./save-errors.md) 가 갖는다.

### 미저장 변경이 있으면 재조회를 확인한다

**서버 재조회는 행을 통째로 갈아 끼운다** — 상태가 붙은 행이 사라진다.
재조회를 부르는 행위는 **넷이고 넷 다 같은 규칙**이다.

| 행위 | |
|---|---|
| **조회** 버튼 | 확인 다이얼로그 |
| **페이지 이동** | 〃 |
| **페이지 사이즈 변경** | 〃 |
| **정렬**(헤더 클릭) | 〃 — **서버 정렬이므로 재조회다** |

> **하나만 적으면 나머지 셋에서 사고가 난다.** 한때 *페이지 이동* 에만 적혀 있었는데
> **정렬이 더 자주 눌린다.**

- 다이얼로그는 **미저장 변경이 있을 때만** 뜬다. 묻는 것은 `useConfirmDiscard()` 하나다.
- **신규 행만이 아니다** — 수정·삭제 상태의 행도 같이 사라진다.
- **컬럼 필터와 접기는 여기 없다** — 서버를 부르지 않는다.
- **저장·실행 뒤의 재조회에는 다이얼로그가 없다** — 방금 냈으므로 잃을 편집이 없다. 대신
  **보던 자리로 간다**: 커서형은 쪽수가 없어 커서로 되돌아간다. 건별 처리 뒤의 갈림은
  [../backend/row-transaction.md](../backend/row-transaction.md) §7 이 갖는다.

**대부분의 편집 그리드에는 이 상황이 오지 않는다.** 검색 폼이 없는 그리드는 응답이
`all` 이라 **페이지가 없고 정렬이 클라이언트**다 — 갈아 끼울 일이 없다.

> **`offset` 인데 결과가 1페이지뿐이어도 다이얼로그가 뜬다.** 건수로 판정하면
> *"정렬해도 편집이 안 날아간다"* 를 배운 사용자가 **데이터가 늘어난 날 작업을 잃는다.**

## 5. 시스템 컬럼과 행 상태

**`columnDefs.tsx`의 순서는 번호 → 다중 선택 체크박스 → 상태 → 업무 컬럼 → 삭제다.**
번호는 항상 맨 왼쪽이고, 단일 선택에는 체크박스가 없다. 상태는 `controller.canEdit`일 때 왼쪽 고정이며,
삭제는 `deletable && controller.savesItself && controller.canSave`일 때 맨 오른쪽 고정이다. 시스템 컬럼은 숨기거나 옮기지 않는다.
행 상태는 **신규 · 수정 · 삭제 · 그대로**다. 남의 저장에 포함되는 하단도 편집 가능하면 상태를 표시한다.
- 신규 행은 고쳐도 신규다. 신규 삭제는 편집본에서 즉시 제거한다.
- 기존 삭제는 저장 전 표시이며, 해제하면 값도 원본으로 돌아간다. 수정 상태에서만 되돌리기 아이콘이 나타난다. 해당 행의 전체 변경만 취소하며 다른 행은 유지한다. 툴바에 편집 취소 버튼을 두지 않는다.
- 행별 삭제 금지는 비활성 버튼 대신 사유가 있는 대시(—)를 표시한다.
- 즉시 저장은 예외이며 화면이 선언한다.

## 6. 응답을 받기 전에는 다시 실행하지 않는다

버튼은 요청이 도는 동안 잠긴다. **중복 요청 방어와 별개의 층**이다 — 이쪽은 UX 이고
저쪽은 서버의 방어다.

## 7. `useGridController` 선언

```ts
const grid = useGridController<UserRow>({
  menuCd: MENU_CD,
  columns,
  api: { read, save, actions },
  addRow,                    // 없으면 행 추가 버튼이 없다
  params: () => form.validate(),        // 사용자가 좁힌 것 — null 이면 조회하지 않는다
  searchParams: () => ({ parentId }),   // 화면의 구조 — 마스터-디테일의 부모 키
  pageSize,
  editable,
});
```

> **`params` 와 `searchParams` 는 다른 축이다.** 앞은 **사용자가 좁힌 것**이고 뒤는
> **화면의 구조**다. 부모 키를 조건 목록에 두면 화이트리스트를 지나며 **선택적**이 되어,
> **부모를 빠뜨린 요청이 전 그룹의 자식을 한 판에 쏟는다.**

> **매 렌더 새 함수를 넘기지 않는다** — 조회·저장 콜백이 전부 새것이 된다.
