# 진행률 — 맡기고 돌아온다

> **요청 스레드를 붙잡지 않는 것이 전부다.** 붙잡으면 그 요청이 타임아웃까지 열려 있고,
> 사용자는 *화면이 멈췄다* 를 겪으며 새로고침한다 — 그러면 **같은 작업이 또 시작된다.**
>
> 화면 쪽은 [../frontend/progress.md](../frontend/progress.md), 표는
> [knowledge/sys/progress-lock.md](../../knowledge/sys/progress-lock.md).

## 1. 흐름

```
컨트롤러 (요청 스레드)
  │ progressHelper.start(totCnt, progress -> service.bulk(list, progress))
  │   ├ userId · 언어를 여기서 붙든다      ← 작업 스레드에는 요청이 없다
  │   ├ jobId 발급 + RUNNING 사전 등록     ← 첫 폴링이 "없음" 을 받지 않게
  │   └ progressExecutor 에 맡긴다
  └ return { jobId }                        ← 즉시 돌아온다

progress- 스레드
  work.accept(progress) → progress.step() … → complete() / fail(문구)
```

**컨트롤러가 돌려주는 것은 `jobId` 하나**이고 화면이 그것으로 폴링한다.

## 2. 요청 스레드에서 **붙들어야** 하는 것 둘

| 값 | 왜 |
|---|---|
| **`userId`**(`AuditorAware`) | 작업 스레드에 `SecurityContext` 가 없다. 안에서 물으면 **주인 없는 진행률**이 되어 **시작한 사람조차 자기 것을 볼 수 없다** |
| **언어**(`RequestLang`) | 실패 문구는 사용자 언어여야 하는데 **그 규칙은 요청을 아는 쪽**에 있다 |

> **`RequestLang` 이 인터페이스인 이유**는 언어를 정하는 규칙이 `api` 에 살고 **도메인은
> `api` 를 참조하지 않기** 때문이다 — 값을 받을 구멍을 도메인이 선언한다. `AuditorAware`
> 와 같은 자리다.

## 3. `Progress` — 쓰기를 **조절한다**

**진행률 1% 또는 1초 중 늦은 쪽**에 한 번 쓴다.

- **건별로 쓰지 않는다.** 10만 건마다 `UPDATE` 를 치면 *진행률을 보여 주려고 작업을
  느리게 만드는* 꼴이 된다. 10만 건이면 `UPDATE` 는 100회이고 폴링이 1초 주기이므로
  **사용자가 보는 정밀도는 그대로**다.
- **둘 중 늦은 쪽인 것이 요점이다.** 1% 만 보면 **건수를 모르는 작업**(`totCnt == null`)이
  영영 안 쓰고, 1초만 보면 초당 수천 건이 도는 작업이 **1초마다** 쓴다.
  건수를 모르면 **시간만** 본다.
- **종료는 조절하지 않는다.** `complete`·`fail` 은 즉시 쓴다 — 늦으면 **끝난 작업이 99%
  에서 멈춰 보인다.**
- **여러 스레드가 함께 세도 된다** — §3.1.

### 3.1 세는 것과 쓰는 것을 나눈다

| | 무엇 | 막는가 |
|---|---|---|
| **세는 것** | `AtomicLong` | **막지 않는다** — 일하는 스레드가 서로를 기다리지 않는다 |
| **쓰는 것** | `ReentrantLock` + **`tryLock`** | 남이 쓰고 있으면 **그냥 돌아간다** — 그 쓰기가 이미 내 걸음을 포함한다 |
| **구간 경계 · 단계 문구 · 종료** | 같은 락(**기다린다**) | 놓치면 안 되는 것들이다 |

> **한동안 *스레드 하나가 쓴다* 를 전제로 아무 보호가 없었다.** 지금 쓰는 두 실행이 단일
> 루프라 드러나지 않았을 뿐이고 **구조가 그것을 막고 있지는 않았다** — `parallelStream`
> 하나면 **조용히** 어긋난다: 카운트가 유실되어 **100% 에 못 닿고**, 조절 상태가 찢어지며,
> 저장소가 `CUR_CNT` 를 덮으므로 늦게 도착한 값이 **막대를 뒤로 되돌린다.**

- **`curCnt` 만 원자적이면 모자라다.** 조절 상태(`lastWrite`·`lastPercent`)와 **실제로
  기록한 건수**가 함께 움직여야 한다 — 락 안에서 `curCnt` 를 읽는 것이 그 보장이다.
- **종료 뒤에는 쓰지 않는다.** 늦게 도착한 걸음이 `MOD_DTM` 을 되돌리면 **만료 청소가 그
  행을 *방금 끝난 작업* 으로 읽어** 그만큼 늦게 지운다.
- **구간의 경계는 부르는 쪽이 혼자 넘는다.** 락이 막는 것은 *쓰기가 찢어지는 것* 이지
  *일이 아직 안 끝난 것* 이 아니다 — 구간을 다 돌고 나서 `reset` 한다.

### 구간이 갈리는 작업 — `reset`

행마다 딸린 디테일 수천 건을 처리하는 실행에서 **하나의 퍼센트로는 둘 중 하나만 말할 수
있다**(50행 중 3행 / 이 행의 3,000건 중 1,200건).

```java
progress.reset("주문 A-1023 (1/50)", 3_000L);   // 막대가 0 으로
items.forEach(item -> { ...; progress.step(); });
progress.reset("주문 A-1024 (2/50)", 1_200L);
```

| 메서드 | 언제 | 쓰기 |
|---|---|---|
| `step()` / `step(문구)` | 한 건 처리 | **조절**. 단, **문구가 오면 즉시** — 단계가 바뀐 것은 사용자가 기다리던 신호다 |
| `subTitle(문구)` | 소제목만 바꾼다 | **즉시** + 건수를 함께 민다 — 안 그러면 *새 이름 + 낡은 건수* 가 1초 뜬다 |
| `reset(소제목, 전체)` | **구간 경계** | **즉시** — 늦으면 폴링이 *새 구간의 건수 대 앞 구간의 전체* 를 보고 **100% 를 넘긴 막대**를 그린다 |

> **전체를 나중에 아는 작업도 `reset` 을 쓴다.** `null` 로 열어 두고(불확정 막대) 센 순간
> 앉힌다. **`0` 을 주지 않는다** — `0/0` 은 **완료로 보인다.**

## 4. 저장소 — 인터페이스이고 구현은 **하나**다

`JobProgressStore` 는 `jdbc` · `redis` · `caffeine` · `inmemory` 로 갈릴 수 있지만
**서 있는 것은 `jdbc` 하나**다.

> **나머지를 미리 만들지 않는 이유**는 그 셋이 전부 **노드 로컬**이라, 폴링이 작업을 실행한
> 노드가 아닌 곳으로 가면 **조용히 못 찾기** 때문이다. 골라 쓸 수 있게 두면 *단일
> 인스턴스에서 잘 돌던 것* 이 배포에서 깨지고, 그 고장은 **가끔 못 찾는다** 로만 보인다.

| 규칙 | |
|---|---|
| **쓰기마다 `REQUIRES_NEW`** | 작업의 트랜잭션과 묶이면 도는 동안 아무것도 커밋되지 않아 **0% 에서 멈춰 보이고**, 롤백되면 **실패 사유까지 사라진다** |
| **조절은 저장소가 아니라 `Progress` 가 한다** | 저장소마다 다른 조절을 갖게 두면 **같은 작업이 배포 형태에 따라 다른 정밀도**로 보인다 |
| **`app.progress.store` 가 비면 `jdbc`** | 기본값이 **문서가 아니라 코드에 있어야** 둘이 갈리지 않는다 |
| **모르는 값을 삼키지 않는다** | `redis` 라 적으면 빈이 없어 **기동이 죽는다** — 삼키면 Redis 를 쓰는 줄 알고 배포한 클러스터가 DB 를 쓰면서 **잘 돈다** |

**`JobProgressView` 는 엔티티가 아니라 사진이다.** 엔티티를 그대로 내보내면 `USER_ID` 가
응답에 실린다 — 그 값은 **인가의 근거**이지 화면이 그릴 것이 아니다.

## 5. 실행기 — 전용 풀 하나(`progressTaskExecutor`)

```
core 2 · max 4 · queue 20 · thread "progress-" · shutdown 대기 60초
```

| 결정 | 왜 |
|---|---|
| **일반 `@Async` 와 섞지 않는다** | 여기 도는 것은 **분 단위**로 스레드를 붙잡는다. 같은 풀을 알림 발송이 쓰면 사용자가 겪는 것은 *알림이 안 온다* 이고 원인은 **전혀 다른 화면의 배치**다 |
| **배치 풀과도 다르다** | 저쪽은 스케줄러가 깨우고 여기는 **사람이 버튼을 눌렀다**([batch.md](./batch.md)). 나눠 쓰면 야간 배치가 큐를 채운 시간에 누른 버튼이 **아무 반응 없이** 기다린다 |
| **풀이 작다** | 전부 DB 를 쓰므로 **커넥션 풀이 진짜 상한**이다. 키우면 사용자 요청이 커넥션을 못 잡는다 |
| **큐가 짧다** | 사람이 누른 버튼이라 *언젠가 시작된다* 는 답이 되지 않는다 — **지금 붐빈다**를 말하는 편이 낫다 |
| **종료 때 기다린다** | 안 기다리면 `RUNNING` 행이 남아 **영영 도는 작업**으로 보인다 |

**큐가 차서 거절되면 그 자리에서 실패로 닫는다.** 사전 등록한 `RUNNING` 을 그대로 두면
사용자는 **만료 청소가 지울 때까지** 창을 열어 둔 채 기다린다.

## 6. 실패 문구는 **코드로 푼다** — 예외의 `getMessage()` 가 아니다

| 갈래 | 문구 |
|---|---|
| **업무 규칙 위반**(`BusinessException`) | `ErrorCode.code()` 를 키로 **그 사람의 언어**로 `SYS_MESSAGE` 에서 읽는다 |
| **예상 밖의 고장** | **`err.internal` 하나로 닫는다** — 원인은 로그가 갖는다 |

> **한 번 어긋나 있었다.** `getMessage()` 를 그대로 `ERR_MSG` 에 적었는데 그 값은 **로그의
> 것이고 응답의 것이 아니다** — 서버 언어이고 개발자용 문자열이다. 진행률 창에
> *amount is closed: SO-2026-1021* 이 떴다.

- **`Throwable` 까지 잡는다.** 실행기로 새어 나가면 스택은 로그에만 남고 진행률 행은
  `RUNNING` 인 채 굳는다 — 사용자에게는 **끝나지 않는 작업**이다. 상태를 닫고 **다시 던진다.**
- **문구를 읽는 자리에서 던지면 안 된다.** 메시지를 못 읽는 상황이 바로 작업이 실패하는
  상황이므로 **여기서만** 예외를 삼키고 기본 문구로 간다.

## 7. 청소 — **저장소를 따라다닌다**

`JdbcProgressSweeper` 는 `JdbcJobProgressStore` 와 **같은 조건**으로 선다 — Redis 로
갈아타면 **함께 사라진다**(그쪽은 native TTL 이다).

| 결정 | 왜 |
|---|---|
| **`@Scheduled` 가 아니다** | 이 프로젝트에 `@EnableScheduling` 이 없다 — 달아도 **돌지 않고**, 그 실패는 *아무 일도 안 일어남* 이라 드러나지 않는다 |
| **등록 배치도 아니다** | 그 행이 **Redis 배포에도 남아** 아무 일도 안 하면서 성공으로 끝난다 |
| 자기 데몬 스케줄러 + `ApplicationReadyEvent` | Liquibase 와 커넥션 풀이 선 뒤여야 한다 |
| **락을 잡지 않는다** | 조건부 `DELETE` 라 둘이 동시에 돌아도 두 번째는 지울 것이 없다. 락을 씌우면 **청소가 청소를 필요로 한다** |

## 8. 인가 — `USER_ID` 대조

**다른 사람의 `jobId` 는 없는 것이다.** 가르지 않고 돌려주면 *존재는 한다* 가 새어 나가는데,
진행률 문구에는 업무 데이터가 섞이므로(*"주문 A-1023 처리 중"*) 그것은 진행률이 아니라
**업무 정보의 노출**이다.

폴링 경로는 **`/api/common/progress/{jobId}`** — 메뉴에 매이지 않는 공통 API 다.
화면마다 엔드포인트를 두면 **인가 시드가 그것을 전부 나열하게 된다.**
Hub CR-038의 목표는 `/api/system/common/progress/getProgress/{jobId}`다. 현재 구현과 구별하고
정확한 handler/method/template·단일 jobId·현재 ADMIN 본인 소유 검사를 유지한다. 플랫폼 저장
소유를 system 사용자 상태 저장으로 옮기지 않는다.

## 9. 체크리스트

- [ ] `start` 의 `totCnt` — 모르면 **`null`**(`0` 이 아니다)
- [ ] 구간이 갈리면 `reset`, 아니면 `subTitle`
- [ ] 실패 경로가 **코드로 문구를 푸는가**
- [ ] 오래 걸리는 실행을 **일반 `@Async` 에 태우지 않았는가**
- [ ] 새 저장소를 붙였다면 **청소도 함께** 정했는가
- [ ] 여러 스레드로 도는 작업이면 **`step(문구)` 를 뜨겁게 부르고 있지 않은가**(§3.1 — 그 경로만 기다린다)
