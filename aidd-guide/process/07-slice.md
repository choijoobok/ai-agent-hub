# 슬라이스 규약 — 구현은 어떻게 도는가

## 1. 슬라이스란

**수직 슬라이스** = 하나의 `FEAT-###` 을 설계 확인부터 관찰 가능한 계약·테스트까지
관통해서 동작하게 만드는 최소 단위. 계층별(전체 DB 먼저 → 전체 API → 전체 UI)로 만들지
않는다. 기능에 없는 층은 억지로 만들지 않는다 — UI 없는 agent 기능은 DB·서비스·계약·테스트,
화면 어댑터는 계약·UI·테스트만 가질 수 있다.

```
SLICE-007 = FEAT-012 스키마 카탈로그 등록
  ├─ DB   : ENT-004 테이블 + 마이그레이션
  ├─ API  : API-031 POST, API-032 GET
  ├─ UI   : SCR-008 등록 화면
  └─ TEST : TC-0121(정상), TC-0122(중복), TC-0123(권한없음)
```

## 2. 슬라이스 순서 정하기 (P3 말미에 백로그 확정)

우선순위 = **의존성 → 리스크 → 업무 가치** 순서로 정렬한다.

1. **기반 슬라이스 먼저** — 인증/권한, 공통 코드, 조직/사용자 관리. 여기 없으면 나머지가 다 막힌다.
2. **가장 불확실한 것을 그다음에** — 외부 연동, 복잡한 계산 규칙, 성능 리스크가 있는 것.
   불확실한 것을 늦게 하면 늦게 터진다.
3. **핵심 업무 흐름(Happy Path)을 관통** — 사용자가 "돌아가는 걸" 볼 수 있게.
4. **부가 기능·관리 화면·리포트** 마지막.

## 3. 슬라이스 실행 절차 (매 슬라이스 동일)

시작 전에 `slices[]`의 `workstream`·`features`·`testcases`를 확인하고, 소유 작업흐름 G3가
승인됐는지 검사한다. 각 TC는 구현 슬라이스 하나에만 배정한다. 그래야 T13이 현재 슬라이스의
테스트 코드만 강제하고 뒤 슬라이스의 TC를 미리 구현하게 만들지 않는다. 작업흐름 G3 뒤에
추가된 기능은 승인된 변경 요청의 미니 설계가 먼저다.

```
① 스펙 재확인   해당 FEAT/UC/ENT/API/SCR/TC spec 을 읽는다. 기억에 의존하지 않는다.
② 설계 확인     구현 방식이 spec과 어긋나면 코드가 아니라 CR을 먼저 낸다.
③ TEST-FIRST    TC를 실행 가능한 테스트 코드로 먼저 작성한다 (실패 확인).
④ 필요한 층      DB → 서비스/API → UI 중 이 기능에 존재하는 층만 구현한다.
⑤ 계약 확인      외부에서 관찰 가능한 API·이벤트·응답 블록이 spec과 일치하는지 확인한다.
⑥ 통합           소비자 또는 제공자와 계약 테스트를 실행한다.
⑦ 통과 확인     ③의 테스트 전부 통과. skip/xfail 0건.
⑧ 미니게이트    G4 체크리스트 + 사용자에게 결과 제시 (실행 결과/스크린샷).
⑨ 상태 갱신     slices[].status = done. 통합 후 검증을 넘겼으면 별도 pending_rechecks에 둔다.
```

모듈 간 계약을 바꾸는 기능은 한 슬라이스에 양쪽 구현을 섞지 않는다. `integration` 계약
슬라이스를 먼저 닫고 제공자·소비자 슬라이스가 그 계약 버전을 따른다.

완료 슬라이스가 최신 main 통합의 영향을 받아도 `done`을 되돌리지 않는다. 통합자가 시험을
마치면 커밋에 근거를 남기고, 넘기면 `pending_rechecks.<SLICE-###>`를 등록한다. 누구나 해당
TC를 실행해 근거와 함께 항목을 제거할 수 있다([공동 작업](14-collaboration.md)).

### ③ TEST-FIRST를 강제하는 이유
AI는 코드를 먼저 쓰면 그 코드에 맞는 테스트를 쓴다. 이건 검증이 아니라 자기 확인이다.
**spec의 TC를 먼저 코드로 옮기고, 실패하는 것을 확인한 뒤** 구현한다.

## 4. 슬라이스 크기 규칙

| 기준 | 값 |
|---|---|
| 1 슬라이스 = | FEAT 1개 (예외적으로 밀접한 2개) |
| 코드 변경량 목표 | 500~1500 라인 |
| 초과 시 | 슬라이스를 쪼갠다 (`SLICE-007a`, `SLICE-007b`) |
| 미달 시 | 인접 FEAT와 묶는다 |

**한 세션에 슬라이스 여러 개를 연속 처리해도 되지만, 미니게이트는 슬라이스마다 통과해야 한다.**
"3개 한꺼번에 만들고 한 번에 확인" 은 금지 — 첫 번째의 오류가 나머지에 복제된다.

## 5. 구현 중 spec 오류를 발견했을 때 (자주 일어난다)

```
발견 → 즉시 구현 중단 → [PM] 모자로 전환
  ├─ 명백한 spec 오타/누락 (Low)   → spec 수정 + 한 줄 통지 후 계속
  ├─ 설계 결함 (Medium)            → 영향 분석 + CR 등록 + 사용자 통지 후 계속
  └─ 요구사항 모순/누락 (High)      → 구현 중단 + 사용자 결정 요청 (다른 슬라이스로 이동)
```

**절대 금지**: spec과 다르게 구현하고 나중에 spec을 맞추기. spec이 먼저 바뀌어야 한다.

## 6. 슬라이스 완료 보고 포맷

```markdown
## ✅ SLICE-007 완료 — FEAT-012 스키마 카탈로그 등록

**구현**
- ENT-004 `inbound_plan` 테이블 (migration V007) — 롤백: V007_rollback.sql
- API-031 `POST /api/admin/service/schemaCatalog/create`, API-032 `POST /api/admin/service/schemaCatalog/getOne`
- SCR-008 카탈로그등록 화면

**테스트**  3/3 통과
- TC-0121 정상 등록 ✅
- TC-0122 중복 예정번호 거부 ✅
- TC-0123 권한 없는 사용자 차단 ✅

**확인 방법**
`npm run dev` → http://localhost:3000/admin/hub/schemaCatalog (계정: test-admin)

**발견 사항**
- spec에 예정수량 상한이 없어 CR-003 등록 (999,999로 임시 적용 [ASM-011])

**다음**: SLICE-008 (FEAT-013 카탈로그 조회/수정)
```
