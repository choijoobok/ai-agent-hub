# 검증 비용 — J-커브를 미리 알리고, 측정하고, 지켜낸다

## 1. 무엇이 문제인가

DORA 2025/2026 보고서의 **J-커브**:

> 팀은 AI에서 가치를 얻기 **전에 일시적인 생산성 하락**을 겪는다.
> 원인은 두 가지다 — 도구 학습 비용, 그리고 **verification tax**:
> AI가 만든 것이 믿을 만하고 안전하며 아키텍처에 맞는지 **확인하는 데 드는 추가 노력**.

같은 보고서의 다른 결론이 이걸 더 무겁게 만든다. **"AI는 증폭기다."**
잘하는 조직의 강점도, 망가진 조직의 역기능도 같이 키운다. 수익은 도구가 아니라
조직 시스템(플랫폼 품질, 워크플로 명확성, 팀 정렬)에서 나온다.

이 방법론에서 J-커브가 나타나는 지점은 명확하다.

```
체감 속도
  ▲
  │      ┌─── P4 구현: 갑자기 빨라짐 (여기서 방심한다)
  │     ╱                    ╲
  │    ╱                      ╲___ P5 검증: 다시 느려짐 (누적 검증 비용 청구서)
  │   ╱                            ╲___ 이후 안정
  │  ╱
  │ ╱  P0~P3: 느리게 느껴짐 (문서만 만들고 돌아가는 게 없다)
  └──────────────────────────────────────────▶ 시간
        ↑                    ↑            ↑
     "왜 이렇게 오래 걸려"   "역시 AI네"   "왜 안 끝나"
```

**세 지점 모두에서 사용자가 프로세스를 줄이자고 요구한다.** 이 문서는 그때
무엇을 줄일 수 있고 무엇은 줄이면 안 되는지를 미리 정해 둔다.

## 2. 장치 A — 기대치 정렬 (P0에서 한 번, 필수)

헌장 확정 전에 AI가 **먼저** 말한다. 사용자가 묻기를 기다리지 않는다.

```markdown
### 진행 속도에 대해 미리 말씀드립니다

이 방식은 **처음이 느리고 중간이 빠르고 끝이 다시 느립니다.**

- **지금부터 설계 확정까지**: 돌아가는 화면이 하나도 안 나옵니다.
  질문에 답하고 문서를 승인하는 구간입니다. 답답하실 겁니다.
- **구현 구간**: 기능이 빠르게 쌓입니다. 여기서 "이럴 거면 앞에서 왜 그랬나" 싶으실 텐데,
  앞에서 정한 것 덕분에 빠른 겁니다.
- **검증 구간**: 다시 느려집니다. AI가 만든 코드는 사람 코드보다
  논리 오류가 75% 많다는 게 2026년 관측치라, 확인하는 데 시간이 듭니다.

**AI를 쓴다고 총 기간이 줄지는 않을 수 있습니다.** 줄어드는 건 사람이 문서를 쓰는 시간이고,
늘어나는 건 확인하는 시간입니다. 대신 **문서가 코드와 일치하고, 왜 그렇게 만들었는지가
남습니다.** 그게 2차 개발과 운영에서 값을 합니다.

지금 이 이야기를 드리는 이유는, 중간에 "너무 느리니 절차를 줄이자"는 판단을 하실 때
**무엇을 줄여도 되고 무엇은 안 되는지**를 미리 합의해 두기 위해서입니다.
```

`documents/spec/00-charter/_index.yaml` 에 기록한다.

```yaml
expectations:
  briefed_at: "2026-09-04"
  j_curve_acknowledged: true
  user_priority: quality        # speed | quality | balanced
  # speed 를 택하면 §4의 '줄일 수 있는 것'을 P0에서 미리 적용한다
  reduced_scope: []             # 사용자 합의로 줄인 절차. 근거와 함께.
```

**`user_priority` 를 P0에서 받아 두는 것이 핵심이다.** 나중에 압박이 왔을 때
"처음에 quality라고 하셨습니다"가 아니라, 그때 정한 규칙대로 협상할 수 있다.

## 3. 장치 B — 검증 부담 측정 (P4, 슬라이스마다)

도구 로그에 실제 시간이 있으면 병목 분석에 쓴다. 로그 없이 소요 시간·절감률을 추정하지 않는다.
기본 지표는 **셀 수 있는 것**이며, 비영향 전수 반복 대신 `quality/test-design.md` §0으로 범위를 정한다.

`documents/project.state.yaml` 의 각 슬라이스에 기록한다.

```yaml
slices:
  - id: SLICE-007
    feature: FEAT-012
    status: done
    verification_load:
      fix_rounds: 3          # 테스트 실패 → 수정 사이클 횟수
      unverified_rules: 1    # 변경된 중요한 규칙 중 반례/검증 근거가 없는 수
      quality_fails: 2       # quality-check.mjs 미충족 횟수 (중복/예외삼킴/태깅)
      spec_defects: 1        # 구현 중 발견한 spec 오류 (CR 발생 수)
      redteam_fixes: 2       # 레드팀 지적 중 실제 수정으로 이어진 수
```

**해석**

| 추세 | 의미 | 대응 |
|---|---|---|
| 슬라이스가 갈수록 지표가 **내려간다** | J-커브를 빠져나오는 중. 정상 | 그대로 |
| **평평하다** | 학습이 일어나지 않고 있다 | 반복되는 결함 유형을 찾아 `AGENTS.md` 나 슬라이스 규약에 규칙으로 추가 |
| **올라간다** | 슬라이스가 너무 크거나 설계가 부실 | 슬라이스를 쪼개거나 해당 영역 설계를 재검토 |
| `spec_defects` 가 계속 나온다 | **P3 설계가 부실했다** | 남은 슬라이스의 spec을 선제 점검 |
| `unverified_rules` 가 계속 나온다 | **P3 테스트 케이스 설계가 부실했다** | TC 작성 기준을 강화 |

**5개 슬라이스마다 보고한다.**

```markdown
### 검증 부담 추이 (SLICE-001~010)

| 슬라이스 | 수정 라운드 | 미검증 규칙 | 품질 미충족 | spec 오류 | 레드팀 수정 |
|---|---|---|---|---|---|
| 001~005 평균 | 4.2 | 1.4 | 2.6 | 1.8 | 2.2 |
| 006~010 평균 | 2.4 | 0.4 | 0.8 | 1.6 | 1.4 |

**J-커브 상태: 회복 중.** 수정 라운드 43% 감소.
다만 `spec 오류`가 줄지 않습니다(1.8 → 1.6). P3 설계에 반복되는 누락 유형이 있습니다 —
지금까지 6건 중 4건이 "권한별 화면 차이 미정의"였습니다.
남은 슬라이스 14개의 화면 spec을 미리 점검할까요? (약 슬라이스 0.5개 분량)
```

## 4. 장치 D — 게이트에서 J-커브 위치 보고

`/pm-status` 와 게이트 승인 요청에 한 줄로 포함한다.

```
J-커브: 하강 구간 (P0~P3, 산출물만 쌓이는 시기) — 예상대로입니다
J-커브: 상승 구간 (P4, 슬라이스 7/24) — 검증 부담 43% 감소 중
J-커브: 2차 하강 (P5, 누적 검증) — 결함 21건 중 14건 처리
```

**"예상대로입니다"를 말해주는 것이 이 장치의 핵심이다.**
사용자가 느끼는 답답함이 실패 신호가 아니라 예정된 구간임을 알면 절차를 깎지 않는다.

## 5. 회고에 남길 것 (P6)

`documents/generated/98-회고.md` 에 이 프로젝트의 실측치를 남긴다. 다음 프로젝트의 견적 근거가 된다.

- 슬라이스별 `verification_load` 추이
- 반복된 spec 결함 유형 (→ P3 체크리스트에 추가)
- 반복된 미검증 규칙 유형 (→ TC 작성 기준에 추가)
- 실제로 줄인 절차와 그 결과 (문제가 됐는가, 안 됐는가)

## 6. 장치 C 는 어디 있나

**"절차를 줄이자" 에 답하는 3분류는 [scope-reduction.md](12-scope-reduction.md) 가 갖는다.**
분리한 이유는 그 문서가 스스로 적고 있다 — `AGENTS.md` 가 그것만 직접 가리키기 때문이다.
