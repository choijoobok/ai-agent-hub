# 추적성 — ID 체계와 연결 규칙

## 1. 왜 강제하는가

AI는 세션이 바뀌면 "이 코드가 왜 여기 있는지"를 모른다. 추적성 체인은 **AI의 외장 기억**이자
변경 영향 분석의 유일한 수단이다. 체인이 끊기면 AI는 안전하게 고칠 수도, 지울 수도 없다.

## 2. ID 체계

| Prefix | 대상 | 발번 단계 | 예 |
|---|---|---|---|
| `ACT-` | 액터(사용자 유형/외부 시스템) | P0 | ACT-003 업무 지식 관리자 |
| `CON-` | 제약사항 | P0 | CON-002 예산 상한 |
| `PRC-` | 업무 프로세스 / 단계 | P1 | PRC-01-02 SQL 검증·실행 |
| `REQ-` | 요구사항 (FR/NFR) | P1 | REQ-011 |
| `TRM-` | 용어 | P1 | TRM-004 스키마 카탈로그 |
| `ADR-` | 아키텍처 결정 | P2~ | ADR-004 인증방식 |
| `NFR-` | 비기능 목표치 | P2 | NFR-002 응답시간 |
| `UC-` | 유즈케이스 | P3 | UC-004 스키마 카탈로그 등록 |
| `FEAT-` | 기능 (화면·공유 업무·배치·이벤트 처리) | P3 | FEAT-012 |
| `ENT-` | 엔티티/테이블 | P3 | ENT-004 스키마 카탈로그 |
| `API-` | API 엔드포인트 | P3 | API-031 |
| `SCR-` | 화면 | P3 | SCR-008 |
| `JOB-` | 관리형 스케줄 배치 명세 (실행 등록 ID와 별개) | P3~P6 | JOB-003 스키마 불일치 검사 |
| `IF-` | 외부 인터페이스 | P3 | IF-002 ERP 스키마 읽기 |
| `TC-` | 테스트 케이스 | P3~ | TC-0121 |
| `SLICE-` | 구현 슬라이스 | P4 | SLICE-007 |
| `DEF-` | 결함 | P4~ | DEF-013 |
| `ASM-` | 가정 | 상시 | ASM-007 |
| `CR-` | 변경 요청 | P3~ | CR-002 |
| `CMP-` | **공통물**(`shared/` · `core/` · `support/` 의 폴더 하나) | 상시 | CMP-009 그리드 |

**발번 규칙**: 3자리 연번, 재사용 금지(삭제해도 번호를 비워 둔다), `documents/project.state.yaml` 의 `counters:` 로 관리.

JOB는 소유 FEAT·UC·REQ와 검증 TC를 갖고, 설정/결과 화면 SCR·운영 RUN·현재 구현 소스를 연결한다. 같은 BatchJob의 여러 스케줄 등록은 하나의 JOB 명세를 참조한다. JOB 연결은 추적성 검사와 변경 영향 분석에 포함하며 구현체 누락·필수 계약 공란은 오류다.

### `CMP-` 만 다른 두 가지

**① 원장이 `counters:` 밖에 있다.** `documents/` 는 고객사마다 갈리는데 공통물은 **고객사가
바뀌어도 같은 것**이다(`AGENTS.md` §1 의 판별식). 그래서 발번을
[`.claude/hooks/commons-ids.txt`](../../.claude/hooks/commons-ids.txt) 이 갖고, 목록은
[`standard/registry.md`](../standard/registry.md) 가 **생성물로** 낸다 — 폴더를 더하면
저절로 발번되므로 사람이 세지 않는다.

**② 위로 올라가는 체인이 없다.** 공통물은 어느 `REQ` 의 실현체가 아니다 — 화면 여럿이
쓰는 **수단**이라 하나의 요구사항에 속하지 않는다. 억지로 붙이면 추적성을 위해서만 존재하는
거짓 `REQ` 가 생긴다(T4 가 `NFR` 을 받아들이는 것과 같은 이유다). 그래서 §3 의 체인에
`CMP-` 를 넣지 않고, **T1~T14 도 `CMP-` 를 검사하지 않는다.**

**그럼 무엇에 쓰나 — 이름이다.** 폴더 경로는 바뀌고 문서 제목도 바뀌는데 ID 는 남는다.
결정 기록·변경 요청·커밋 메시지가 **한 공통물을 두 번 같은 이름으로** 부를 수 있게 하는 것이
전부이며, 그 이상을 주장하지 않는다.

## 3. 필수 연결 체인

```
                    ┌─────────────── ADR-### (근거)
                    │
ACT-###  ─┐         │
          ├──▶ REQ-### ──▶ UC-### ──▶ FEAT-### ──┬──▶ ENT-### ──▶ (DDL)
PRC-###  ─┘                                       ├──▶ API-### ──▶ (sources/)
                                                  ├──▶ SCR-### ──▶ (sources/)
                                                  └──▶ TC-###  ──▶ (tests/) ──▶ DEF-###
NFR-### ──────────────────────────────────────────────────────────▶ TC-###(비기능)
```

### 검사 규칙 (`/trace` 스킬 및 훅이 자동 검사)

| # | 규칙 | 위반 시 |
|---|---|---|
| T1 | 모든 `REQ` 는 최소 1개 `ACT` 와 연결 | 오류 |
| T2 | 모든 FR `REQ` 는 최소 1개 `UC` 또는 `FEAT` 로 실현 | 오류 · **뒤 차수이거나 소유 작업흐름 G3 전이면 경고**. 작업흐름 G3 검사에서는 `REQ.workstream`으로 아직 연결되지 않은 요구도 포함 |
| T3 | 모든 `UC` 는 최소 1개 `REQ` 로 역추적 | 오류 (근거 없는 유즈케이스) |
| T4 | 모든 `FEAT` 는 최소 1개 `UC` · `REQ` · **`NFR`** 로 역추적 | 오류 (고아 기능) |
| T5 | 모든 `FEAT` 는 최소 1개 `TC` 보유 | 오류 · **뒤 차수이거나 소유 작업흐름 G3 전이면 경고** ([왜](./04-gates.md)) |
| T6 | 모든 `TC` 는 정상 1건 + 예외 1건 이상 짝을 이룸 | 경고 |
| T7 | 모든 `NFR` 은 **측정 방법(`measurement`) · 측정 원천(`source`) · `TC`** 보유 | 오류 (**소유 작업흐름 G3 이후** · 뒤 차수나 G3 전이면 경고) |
| T8 | 모든 `ENT` 는 최소 1개 `FEAT` 에서 사용됨 | 경고 (미사용 테이블) |
| T9 | 모든 `API`/`SCR`은 소유 `FEAT`를 갖고 공통 사용 관계·소스 경로가 유효함 | 오류 |
| T10 | **기능 코드**는 헤더에 존재하는 `@feat FEAT-###` 태그 보유 | 경고 |
| T11 | 참조된 ID가 실제로 존재함 (dangling reference) | 오류 |
| T12 | ID 중복 없음 | 오류 |
| T13 | 모든 `TC`는 **테스트 이름**에 나타나며 명시한 `screen_cases`와 화면의 TC 참조가 유효함 | 경고 (**소유 구현 슬라이스 시작 이후 오류**) · 거꾸로 spec 에 없는 TC 를 부르면 **오류** |
| T14 | 모든 FR `REQ` 는 **정련 카드**([P1 §5](../phase/P1-discovery.md))를 갖는다 — 칸 완전성 · 정상/예외 사례 · `Must`·`Should` 의 `confirmed`. 카드끼리는 **연계가 양방향**(`depends_on`↔`constrains` · `conflicts_with`)이고 `realization.features`↔`FEAT.reqs` 가 맞으며, `confirmed` 에 G1 전 `open` 이 없다 | 완전성은 경고 (**`--g1` 에서 소유 작업흐름 G1 승인 전이면 오류** · 이미 승인된 작업흐름은 소급 대상이라 경고) · **정합 위반은 언제나 오류** |

### T13 에 명단이 없는 이유 — **방향이 T10 과 반대다**

T10 은 *모든 소스가 태그를 갖는가* 라 템플릿 817건이 한꺼번에 위반이 돼 명단이 필요했다.
T13 은 *모든 `TC` 가 코드에 있는가* 다 — **이미 선 테스트는 대상이 아니므로 명단이 없다.** `70-testcases/_index.yaml` 이 빈 때부터 켜고 이름에 박아 케이스 단위로 잠근다.
G3는 P4를 여는 경계이지 뒤 슬라이스의 테스트를 미리 만드는 경계가 아니다. `slices[].testcases`가 TC를 슬라이스 하나에 배정하고, `planned`이면 경고·`in_progress` 이상이면 오류다. spec에 없는 TC를 부르는 역방향은 항상 오류다.

### T4 가 `NFR` 도 받는 이유

**비기능 목표만 실현하는 기능이 실재한다** — 모델 단가 관리 · 전사 예산 계획 · 토큰 집계 ·
스케줄러는 어느 기능 요구사항의 실현체도 아니고 **비용·안정성 목표의 실현체**다.
그것을 고아로 부르면 **없는 `REQ` 를 만들어 붙이게 되고**, 그 `REQ` 는 추적성을 위해서만
존재하는 거짓 항목이 된다 — **검사를 통과시키기 위해 spec 을 오염시키는 것**이다.

### T10 은 무엇을 세나 — 면제가 둘이고 **뜻이 다르다**

| | 무엇 | 성격 |
|---|---|---|
| **기능 없는 층** | `core` · `support` · `bootstrap` · `shared` · `layouts` · `app` · `locales` · 진입점 · 빌드 설정 | **영구 규칙** |
| **템플릿 명단** | [`feat-baseline.txt`](../../.claude/hooks/feat-baseline.txt) | **갚아야 할 빚** |

#### ① 기능 없는 층 — 물어도 답이 없다

여기 있는 코드의 존재 이유가 **여러 기능이 함께 쓴다**는 것이다. 공통물은 **두 번째
사용에** 올라오므로(`AGENTS.md` §8) 정의상 둘 이상의 기능에 속하고, 그중 하나를 골라 적으면
나머지와의 연결이 조용히 사라진다. 프레임워크 최하층과 셸은 아예 어느 기능도 아니다.

**태그를 요구하면 결국 아무 `FEAT` 나 붙는다.** 그리고 **거짓 연결은 빈칸보다 나쁘다** —
빈칸은 *모른다* 고 말하지만 거짓 연결은 **안다고 말하고**, T4·T9 가 그 위에서 초록이 된다.

전제는 **기능 코드가 그 층에 살지 않는다**는 것이다(백엔드는 `domain`·`api`, 프론트는
`features`). 경계가 무너지면 이 면제도 무너지므로 **거기에 기능을 넣지 않는 것**이 규칙의
절반이다. 목록은 `lib.mjs` 의 `FEATURELESS` 하나가 갖고 **두 게이트가 그것을 함께 읽는다** —
따로 두었다가 같은 규칙에 답이 갈린 적이 있다(963 대 0).

#### ② 템플릿 명단 — 오늘의 빚

`sources/` 에 먼저 들어온 백오피스 템플릿은 이 체계보다 앞서 만들어졌고, **그 기능을
실현하는 코드에 Hub 의 `FEAT-###` 를 붙이는 것은 거짓 연결이다.** 그래서 명단으로 고정하고
**명단 밖만 센다.** 건수로 집계만 하면 **영구히 켜진 경고**가 되고, 그것은 **사람에게
경고를 무시하는 법을 가르친다.** *헌법은 요구하는데 실물에 0건* 인 상태도 같은 결과를
낸다 — 어느 쪽을 따를지 알 수 없어진다.

**명단은 줄어들기만 해야 한다.** 태그를 단 파일은 지운다. 새 파일을 더하는 것은 **규칙을
끄는 것**이며, 그럴 이유가 있으면 커밋 메시지에 적는다.

**①에 해당하는 파일은 명단에 두지 않는다.** 둘이 함께 덮으면 층 규칙을 고쳐도 아무 일도
일어나지 않는다 — 겹치던 219줄을 걷어 내 명단의 뜻을 하나로 남겼다.

## 4. 코드 태깅

소스 파일 상단에 기계가 읽을 수 있는 태그를 남긴다.

```java
/**
 * @feat FEAT-012 스키마 카탈로그 등록
 * @uc   UC-004
 * @api  API-031, API-032
 */
```
```typescript
// @feat FEAT-012  @scr SCR-008
```
```sql
-- @ent ENT-004 스키마 카탈로그
```

훅이 `sources/` 쓰기를 감지하면 이 태그를 확인하고, 없으면 경고한다.

## 5. 변경 영향 분석

정본 책임·관계 필드는 [spec-schema.md](../artifact/spec-schema.md)의 「설계 문서의 책임과 연결」을 따른다.

```bash
node .claude/hooks/trace-check.mjs --impact API-558
node .claude/hooks/trace-check.mjs --source sources/backend/modules/system/src/main/java/com/aiagent/system/api/config/ConfigController.java
```

- `--impact`는 REQ·UC·FEAT·ENT·API·SCR·IF·TC·NFR에서 시작한다. `--source`는 저장소 상대 경로와 선택 `#메서드`를 받는다.
- 단수/복수 화면·기능 참조를 합쳐 읽고 `uses_features`·`uses_screens`의 모든 소비자로 전파한다. 소유자와 소비자의 작업흐름은 구분한다.
- 근거 REQ는 설명 문맥으로 함께 표시하되 FEAT/API/SCR에서 시작한 조회를 그 REQ의 무관한 형제 기능까지 확산시키지 않는다.
- `sources`·`source_contract`·파일 머리의 `@feat`/`@scr`로 소스에서 시작한다. 삭제된 파일도 이전 명세의 경로로 찾는다.
- 정본·화면 문서·테스트·운영 절차·명시 소스·구현 슬라이스를 대조한다. 공통 화면은 메뉴 경로가 없어도 문서 경로로 찾는다.
- 연결을 찾지 못하면 **영향 없음이 아니라 확인 필요**다. 미등록 소비자·동적 호출·실제 API 전수 일치·업무 의미는 별도 확인한다.
- 변경 전후를 조회하고 같은 변경에서 정본·소스를 현행화한 뒤 파생물을 생성한다. 결과는 보고만 하며 승인·자동 수정하지 않는다.
- 회귀 fixture: `node aidd-guide/harness/runtime/trace-model.self-test.mjs` — chain 실행·공통 소비자·다대다·순환·삭제 경로·화면 없는 배치·잘못된 참조.

## 6. 추적성 매트릭스 (생성물)

`/trace --report` 로 `documents/generated/90-추적성매트릭스.md` 를 생성한다.

| REQ | 우선순위 | UC | FEAT | ENT | API | SCR | TC | 상태 |
|---|---|---|---|---|---|---|---|---|
| REQ-011 | Must | UC-004 | FEAT-012 | ENT-004 | API-031 | SCR-008 | TC-0121, TC-0122 | ✅ 구현완료 |
| REQ-012 | Must | UC-004 | FEAT-013 | ENT-004 | API-033 | SCR-008 | TC-0131 | 🔨 구현중 |
| REQ-018 | Should | — | — | — | — | — | — | ❌ **미실현** |

마지막 행 같은 항목이 하나라도 있으면 G3를 통과할 수 없다. 작업흐름 게이트는 기능의 `workstream:` 또는 `module:`을 따라 **소유 체인만** 오류로 센다([13-workstreams.md](13-workstreams.md) §2~4).

화면·HTTP API가 없는 기능의 빈 칸은 정상이다. 미실현 요구사항은 T2, 테스트 결손은 T5/T7의 단계별 판정으로 구분한다.
