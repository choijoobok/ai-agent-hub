# 레드팀과 뮤테이션 — 테스트가 진짜 검증하는가

## 3. 레드팀 패스 — AI의 자기반박 (게이트마다 필수)

AI의 최대 실패 모드는 **자기 산출물에 대한 무비판**이다. 절차로 강제한다.

### 실행 방법
`[QA-레드팀]` 모자로 전환하고, **작성자가 아니라 인수 심사자의 입장에서** 아래 4개를 산출한다.

```markdown
### [QA-레드팀] G3 자기반박

**1) 이 설계가 틀렸다면, 가장 가능성 높은 이유 3가지**
   (추상적 우려 금지. "무엇이 어떻게 잘못되는지" 구체적으로)
   1. 마스킹 시점을 결과 표시로 잡았는데 보안팀은 SQL 실행 전을 기대할 수 있음
      → 실제 결과: 원본이 실행 로그에 남아 감사에서 개인정보 유출로 판정
   2. ...

**2) 다루지 않은 예외·경계**
   - 조회 결과를 엑셀로 내려받은 뒤의 보관·파기 정책 미정의
   - 권한이 회수된 사용자의 실행 중인 질의 처리

**3) 사용자가 나중에 "이거 아닌데" 할 지점**
   - 조회 결과 캐시를 범위 밖으로 뒀음 (현업은 같은 질문에 두 번 기다리게 됨)

**4) 지금 결정을 미루면 나중에 얼마나 비싼가**
   - 마스킹 적용 시점: 구현 후 변경 시 슬라이스 5개 재작업 (High)
```

### 레드팀 규칙
- **"문제 없습니다"는 유효한 결과가 아니다.** 최소 3개를 반드시 낸다. 없으면 아직 안 들여다본 것이다.
- 지적한 것은 반드시 처리한다: 수정 / `ASM-###` 등록 / 사용자 결정 요청 중 하나.
- 레드팀 결과를 게이트 승인 요청에 **그대로 포함**한다. 숨기지 않는다.

## 4. 중요한 위험의 반례와 선택적 변이 검사

검증 선정의 정본은 [test-design.md §0](test-design.md)이다. 변경된 중요한 업무 규칙을
실제로 검증해야 하지만, 모든 규칙을 뒤집거나 자동 변이 점수를 매번 측정할 필요는 없다.

### 기본 — 중요한 실패를 막는 반례

인증·권한·민감정보·데이터 손실·중복/비가역 실행 등 실제 변경에 해당하는 위험을 고른다.
거부 상태뿐 아니라 업무 효과·노출·중복 저장이 없는지 확인한다. 정상 흐름과 중요한 반례를
기존 시험이 충분히 검증하면 재사용한다. 경미한 표시·구현 형태를 그대로 복제하는 시험은 늘리지 않는다.

### 검증 공백이 의심될 때 — 조건 하나만 뒤집기

1. 위험한 조건 하나를 제거하거나 반대로 바꾼다.
2. 관련 시험만 실행해 실제 단언/업무 결과의 실패를 확인한다. 컴파일 실패는 근거가 아니다.
3. 원문을 복구한다. 실패를 못 잡으면 필요한 반례를 보강한다.

이 선택 검사를 했을 때만 조건·실패 시험·원문 복구를 기록한다. 전 규칙 순회는 하지 않는다.
변경된 중요한 규칙의 필수 반례/검증 근거가 없으면 G4는 미충족이다.

### 자동 변이 — 구체적인 의심을 해소할 때만 선택

PIT 등은 특정 규칙/클래스와 빠른 단위 시험으로 좁혀 사용한다. 자동 변이·고정 점수는
트랙과 무관하게 G4 필수가 아니다. 전체 클래스·실제 DB/Redis/HTTP·장애/복구를 매 변이마다
반복하지 않는다. 과거 점수를 변경 후 전체 코드의 새 측정값으로 표현하지 않는다.

```bash
./gradlew :backend:domain:pitest -PmutationTargets=com.aiagent.domain.order.OrderService -PmutationTests=com.aiagent.domain.order.OrderServiceTest
```

두 대상 옵션을 생략하면 실행을 거부한다. 기본은 진단용 점수만 출력하며,
명시 합의한 목표가 있을 때만 `-PmutationThreshold=...`로 별도 문턱을 지정한다.
장시간 검사에서 이미 통과한 비영향 근거는 보존하고, 남은 중요한 위험의 집중 시험으로 전환한다.
