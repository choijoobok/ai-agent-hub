# 테스트 케이스 설계 — 최소 세트와 비기능 TC

## 0. 변경과 중요한 위험에 맞춘 최소 검증

검증은 많이 실행하는 대신 실제 실패를 잡는 데 필요한 범위로 선정한다. 아래가 구현·G4의 공통 기준이다.

| 변경 | 반드시 확인할 것 |
|---|---|
| 문서·문구·단순 표시 | 변경 문서/정적 검사 또는 해당 화면 한 번. 구현을 그대로 따라 쓰는 새 시험은 만들지 않는다 |
| 일반 업무 로직 | 대표 정상 흐름과 변경된 중요한 예외·경계. 기존 시험으로 충분하면 재사용한다 |
| 인증·권한·민감정보·금전/쿼터·비가역 실행 | 권한 우회·다른 주체·중복 실행·부분 확정·데이터 손실 중 실제 영향이 있는 반례 |
| 저장 구조·트랜잭션·동시성 | 바뀐 계약의 실제 DB 적용/복구 또는 경합·원자성 대표 시험 |
| 외부 연결·저장소·프로토콜 | 연결/직렬화/장애 복구가 바뀔 때 실제 환경의 대표 정상·중요 장애 시험 |

- 먼저 변경점·위험·필수 시험을 짧게 정한다. 요구사항/수용 기준을 삭제하거나 중요한 실패를 skip하지 않는다.
- 수정 중에는 관련 시험만 돌린다. 같은 원인의 환경 차이는 해당 시험을 고쳐 좁게 재실행한다.
- 통과한 코드·설정·스키마와 의존성이 바뀌지 않았으면 결과를 재사용한다. 재사용 범위와 미실행 범위를 구별한다.
- 여러 층의 같은 단언을 반복하지 않는다. 단위 시험으로 확인되는 판단 로직을 실제 DB/Redis/HTTP에서 매번 반복하지 않는다.
- 전체 회귀는 공통 배선/빌드·여러 소비자 영향 또는 회귀 근거 부재 때 최종 한 번만 실행한다. 단순 문서 수정 뒤 제품 시험을 다시 돌리지 않는다.
- 자동 변이와 모든 규칙의 수동 반전, 고정 변이 점수는 필수가 아니다. 중요한 규칙의 검증 공백이 의심될 때만 해당 조건/클래스를 선택한다.
- 장시간 검사가 계속되면 실행 범위와 가치를 먼저 재평가한다. 이미 확보한 비영향 근거를 버리고 전수 실행을 반복하지 않는다.

## 1. 테스트 케이스 설계 (P3에서 작성, 구현 전에 존재해야 함)

### 설계 시 확인할 유형 — 실행 범위는 §0에서 선정한다

이 최소 세트는 **그 기능의 작업흐름 G3를 청구할 때** 적용한다. 아직 상세 설계를 미룬 다른
작업흐름의 기능은 결손을 경고로 보이되 현재 게이트의 오류로 세지 않는다.
| 유형 | 필수 | 내용 |
|---|---|---|
| 정상 (Happy) | ● | UC 기본 흐름대로 성공 |
| 입력 검증 | ● | 필수 누락, 형식 오류, 길이/범위 초과 |
| 업무 예외 | ● | UC 예외 흐름 각각 (권한 없음, 중복, 상태 불일치 등) |
| 권한 | ● | 권한 없는 액터의 접근 차단 |
| 경계값 | ○ | 0, 1, 최대값, 최대값+1, 음수, 빈 목록 |
| 동시성 | △ | 같은 자원 동시 수정 (해당되는 FEAT만) |
| 멱등성 | △ | 같은 요청 2회 (결제·확정 등 되돌릴 수 없는 액션) |

모듈 간 계약 기능은 제공자·소비자 각각의 단위 테스트에 더해 `integration` 작업흐름이
버전·필수 필드·알 수 없는 표현 블록 처리를 계약 테스트로 잠근다.

### TC 작성 형식 (`documents/spec/70-testcases/_index.yaml`)
```yaml
- id: TC-0122
  feature: FEAT-012
  usecase: UC-004
  type: business_exception
  title: 동일 예정번호 중복 등록 거부
  precondition: "예정번호 IP-20260101-001 이 이미 존재"
  actor: ACT-003
  steps:
    - "카탈로그등록 화면에서 이미 등록된 테이블 HR.EMPLOYEE 선택"
    - "저장 클릭"
  expected: "'이미 등록된 테이블입니다' 오류. 저장되지 않음. 기존 데이터 불변."
  priority: high
```

## 2. 화면 케이스는 무엇으로 잠그나 — **선언을 읽는다**

요건서 §9 의 케이스 절반이 *화면을 봐야* 판정되는 것처럼 보인다 — 헤더에 버튼이 셋인가,
배지 색이 셋인가, 그 컬럼이 기본 숨김인가. **그런데 이 프로젝트의 화면은 선언형이다.**
그것들은 전부 컬럼·버튼 선언 객체에 적혀 있고, **브라우저도 렌더링 라이브러리도 없이 읽힌다.**

| 케이스가 묻는 것 | 무엇을 읽나 | 잠기나 |
|---|---|---|
| 버튼이 셋뿐이다 · 저장 버튼이 없다 | `api` 선언에 `save` 키가 없다 | **단위** |
| 정렬이 한 컬럼만 열린다 | `sortable` 이 붙은 컬럼 수 | **단위** |
| 배지 색이 셋 · 글자가 열다섯 | `tone` 맵의 값 집합 크기 | **단위** |
| 그 컬럼이 기본 숨김이다 | `hidden` | **단위** |
| 그 컬럼이 아예 없다 | 컬럼 배열 | **단위** |
| 조회조건 콤보가 둘로 갈려 있다 | `searchFields` 배열 | **단위** |
| 저장한 뒤 목록이 갱신된다 · 모달의 결과가 그리드에 선다 | 화면을 띄워 눌러 본다 | **E2E** |
| 권한 없는 액터가 실제로 막힌다 | 〃 | **E2E** |
| 배지가 실제로 그려진다 · 툴팁에 전체 값이 뜬다 | 렌더링 결과 | 사람 |
| 레이아웃이 접히지 않는다 | 브라우저 | 사람 |

- **선언 검사는 단위 테스트다.** `buildColumns()` 를 부르고 배열을 검사하면 끝난다 —
  컴포넌트를 마운트하지 않으므로 빠르고 깨지지 않는다.
- **`되면 안 되는 것` 은 대개 선언의 부재로 이룬다**(감추는 코드가 아니라). 그래서
  *"없다"* 를 검사하는 것이 곧 그 케이스를 잠그는 것이다.
- **잠글 수 없는 것을 잠금으로 적지 않는다.** 요건서의 케이스 표에 *단위 / E2E / 사람* 을
  표시하고, 사람 몫은 §6.3 ⑤ 사용자 테스트로 넘긴다 — **AI 의 게이트 초록이 그것을
  갈음하지 않는다**(AGENTS.md §6.3).

### E2E 는 셋째 칸이다 — **잠기지만 비싸다**

선언 검사와 사람 사이에 하나가 더 있다. **여러 화면·여러 요청을 넘나드는 흐름**은 선언을
읽어서 잠기지 않고, 그렇다고 사람이 매번 보기에는 같은 것의 반복이다.

| E2E 로 잠근다 | E2E 로 잠그지 않는다 |
|---|---|
| 저장한 뒤 목록이 갱신된다 · 모달의 결과가 그리드에 선다 | 컬럼·버튼·배지의 배치 — **선언이 이미 잠갔다** |
| 권한 없는 액터가 **실제로 막힌다** — 화면 숨김만으로는 미충족이다 | 문구 · 정렬 · 기본 숨김 |
| 되돌릴 수 없는 액션(삭제·확정)의 확인과 취소 | 한 화면 안에서 끝나는 검증 거부 |
| 상태 전이가 화면을 건너 이어진다 | 렌더링의 모양 — 그것은 사람 몫이다 |

- **두 번 잠그지 않는다.** 선언으로 잠긴 것을 E2E 로 또 잠그면 **느려지기만 한다** —
  그리고 느린 검사는 결국 꺼진다. **꺼진 검사는 없는 검사보다 나쁘다**(있다고 믿게 한다).
- 비용은 시나리오 수·픽스처·필요한 전제로 설명하고, 실제 실행 로그가 있으면 소요 시간을 함께 쓴다.
  근거 없는 시간·절감률은 추정하지 않는다([P4-build.md](../phase/P4-build.md) §5).
- **묻는 자리는 ④-c 다**([artifact/screen/screen.md](../artifact/screen/screen.md)) — 게이트를
  초록으로 만든 **뒤**, ⑤ 로 넘기기 **직전**이다. 앞에 두면 무엇이 남는지 아직 모르고,
  ⑤ 뒤에 두면 사용자가 이미 손으로 다 해 본 뒤다.
- @defer P4 **E2E 러너를 아직 고르지 않았다** — `package.json` 에 없고 playwright 는
  `/manual-site` 의 캡처에 **옵션 의존**으로만 있다. 첫 화면이 ④-c 에서 *짠다* 로 판정될
  때 고른다 — 그 전에 고르면 근거가 추정이다.

## 3. 열거형을 나눈 묶음 — **전수 커버를 테스트가 잠근다**

코드 열다섯을 *실패 · 종료 · 성공* 셋으로 접는 것 같은 묶음이 있다. **새 코드를 더하면서
묶음을 안 정하면 그 코드는 어느 묶음에도 안 걸려, 그 조회를 하는 사람의 목록에서
말없이 빠진다.** 조용한 누락이 틀린 값보다 나쁘다.

**테스트가 주 방어선이다.**

```java
for (LoginResultCode code : LoginResultCode.values()) {
    assertThat(어느_묶음에_들었나(code)).as("%s 가 어느 묶음에도 없다", code).isNotNull();
}
```

- **정적 초기화에 기대지 않는다.** 그것이 기동에 도는지는 *누가 그 클래스를 먼저
  건드리나* 에 달렸고, **아무것도 그 의존을 선언하지 않는다** — 투영 목록을 메서드 안으로
  옮기는 흔한 리팩터 하나로 검사가 조용히 첫 조회로 밀린다. 남겨 두는 것은 좋으나
  **이중 방어이지 방어선이 아니다.**
- **기동에서 터지는 것도 늦다.** 운영에서 발견되지만 빌드는 개발자 자리에서 끝난다.
- **접두로 판정하지 않는다**(`startsWith("FAIL_")`). 열거형에 이름을 더하는 순간
  **묶음이 조용히 바뀐다** — 집합을 적어야 안 정한 코드가 드러난다.
- 실물: `domain/auth/LoginResultGroup` · `LoginLogSpecTest`.

## 4. 비기능 테스트 (NFR별로 반드시 하나)

측정하지 않은 NFR은 존재하지 않는 것으로 본다. G5에서 실측값 없으면 미충족.

| NFR 유형 | 측정 방법 예 |
|---|---|
| 응답시간 | 대표 트랜잭션 3종, 목표 데이터량 상태에서 p50/p95/p99 |
| 처리량 | 동시 사용자 N명 시나리오, 초당 처리 건수 |
| 가용성 | 장애 주입 후 복구 시간 측정 |
| 보안 | 인증 우회, 권한 상승, SQL 인젝션, 민감정보 노출 점검 |
| 데이터 정합성 | 동시 질의 후 토큰 쿼터 합계 일치 검증 |
| 운영성 | 로그로 장애 원인 추적 가능한지 실제로 해보기 |
