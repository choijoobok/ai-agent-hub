## 1. 이 문서의 성격

[프레임워크 조사](agent-frameworks.md)와 같은 **비규범 조사 자료**다. 다만 앞 문서가 자료 조사였다면 이것은 **실행 결과**다 — 코드를 만들어 돌렸고, 여기 적힌 PASS/FAIL과 발견은 전부 실측이다.

- [프레임워크 조사](agent-frameworks.md) 5.2가 "문서상의 비교로는 축 C·D를 결정할 수 없다"고 한 판단에 따라, 같은 시나리오를 두 안으로 각각 구현해 비교했다.
- C안(LangChain4j)과 D안(자체 구현)은 제외했다 — 전자는 agentic 모듈이 experimental이고, 후자는 공급사 API 대응 부담 때문이다.
- **PoC 코드 위치**: 저장소의 `poc/`. **제품 코드가 아니다** — 설계 판단의 근거를 재현하기 위한 실험이며, 여기서 검증된 것은 코드가 아니라 결론이다. 빌드 산출물(`poc/target`, `poc/data`, `poc/libs`)은 추적하지 않는다.

### 1.1 확정된 전제

| 항목 | 결정 | 영향 |
|---|---|---|
| Spring Boot 노선 | **최신 안정 버전을 계속 따라간다. 현재 4.x** | Spring AI는 **2.0 계열**로 확정된다 ([프레임워크 조사](agent-frameworks.md) 3.4의 갈림길 해소). Jakarta EE 11 / Jackson 3 / Spring Framework 7 기반 |
| 개발기 모델 | CLI 사용이 불가하면 **Gemini 무료 API**로 대체 | 토큰 한도로 원활한 테스트가 어려울 수 있음 → 이 PoC는 **결정적 스크립트 구현체**로 돌려 모델 없이 검증했다 (`aidd-guide/standard/hub-conventions.md` §12.9) |
| SQL 파서 | **설정으로 교체 가능한 구조 필요** | ARCH-030의 데이터소스별 파서 지정과 같은 방향. 파서 인터페이스는 우리가 정의한다 |
| 폐쇄망 의존성 | **로컬 Maven 서버 제공** | 전이 의존성 반입은 해결. 다만 반입할 목록의 크기는 여전히 선택 기준이다 (5.2) |
| 고객사 협의 | 사전 협의로 처리 | CON-015~032의 기존 방침과 같다 |

### 1.2 실행 환경과 조건

| 항목 | 값 |
|---|---|
| JDK | Temurin 25.0.3 |
| Spring Boot | 4.1.1 |
| Spring AI | 2.0.1 (`spring-ai-client-chat`) |
| LangGraph4j | 1.8.25 (`langgraph4j-core`) |
| DB | H2 파일 모드 (`AUTO_SERVER=TRUE;WRITE_DELAY=0`) — AI 전용 DB(PostgreSQL) 대역 |

**비교를 공정하게 만들기 위한 통제**

- **하나의 애플리케이션에 오케스트레이터만 두 구현으로 둔다.** 가짜 LLM, 도구, 이력 스키마, 턴 상태 서비스, 쿼터는 두 안이 **같은 코드**를 쓴다. 차이는 오케스트레이션 계층 하나뿐이다.
- **LLM은 결정적 스크립트 구현체**다. `aidd-guide/standard/hub-conventions.md` §12.9가 요구한 "FEAT-304의 테스트용 구현체(고정 응답)" 자리를 그대로 채웠고, 토큰·비용 없이 재현 가능한 시나리오를 얻었다. 한 턴의 스크립트는 `catalog_lookup → run_sql → execute_api(승인 필요) → run_sql → 최종 응답`이다.
- **두 안 모두 Spring AI를 쓴다.** FEAT-304 구현체가 Spring AI `ChatModel`을 감싸고, 스크립트 응답은 `ChatModel` 구현체로 주입된다. 즉 이 비교는 "Spring AI냐 LangGraph4j냐"가 아니라 **"Spring AI 위에 그래프 런타임을 얹느냐"** 다.

## 2. 사전 확인 — LangGraph4j의 확장점

PoC에 앞서 소스를 확인했다. "상태 유형 추가, 처리 전후 인터셉터, 단계별 프롬프트 관리로 우리 쿼터·감사·이력을 태울 수 있는가"에 대한 답이다.

| 확장점 | API | 확인 결과 |
|---|---|---|
| 커스텀 상태 | `AgentState` 서브클래스 + `Map<String, Channel<?>>` 스키마, `Channels.appender / base(Reducer)` | **가능.** 키를 자유롭게 추가하고 병합 규칙(Reducer)을 지정한다. PoC에서 `approvalDecided` 키 하나를 추가하는 데 1줄이 들었다 |
| 노드 전/후 인터셉터 | `addBeforeCallNodeHook` / `addAfterCallNodeHook` / `addWrapCallNodeHook` — **전역 또는 노드 ID 지정** | **가능.** `WrapCall`은 노드 실행 자체를 감싸므로 성공·실패·소요시간을 모두 잡는다. 쿼터는 Before, 스텝 이력은 Wrap에 넣었다 |
| 엣지 인터셉터 | `addBeforeCallEdgeHook` / `AfterCall` / `WrapCall` | 존재한다. 이번 PoC에서는 쓰지 않았다 |
| 동적 인터럽트 | 노드 액션이 `InterruptableAction` 구현. `interrupt(nodeId, state, config)` | **가능.** REQ-030~035의 중단 요청 확인과 REQ-105의 승인 게이트를 여기에 넣었다 |
| 정적 인터럽트 | `CompileConfig.interruptBefore/After(nodeId...)` | 존재한다. 조건 없는 고정 중단점 |
| 체크포인트 저장소 | `BaseCheckpointSaver`(list/get/put/release 4개) 또는 `AbstractCheckpointSaver`(load/insert/update/release 4개) | **가능.** `AbstractCheckpointSaver`가 순서·교체·조회 프로토콜을 처리하므로 **우리 테이블에 직접 쓰는 구현이 65줄**이면 된다 |
| 실행 문맥 전달 | `RunnableConfig` — `threadId`, `checkPointId`, 임의 `metadata` | **가능.** `threadId`에 턴 ID를 실어 훅·노드·saver 어디서나 읽는다 |
| 단계별 프롬프트 | — | **프레임워크가 관여하지 않는다.** 노드는 임의의 자바 코드이고 프롬프트 구성은 전적으로 우리 것이다. A안과 완전히 동일하다 |

**훅과 인터럽트의 실행 순서** (`internal/hook/NodeHooks.java`):

```
BeforeCall 훅  →  interrupt() 판정  →  WrapCall 체인  →  노드 본문  →  AfterCall 훅
```

이 순서가 설계에 영향을 준다 — 4.5 참조.

### 2.1 "체크포인트를 정본으로" 에 대한 답

**가능하다. 단 방향이 반대다.** 체크포인트를 정본으로 승격시키는 것이 아니라, **우리 테이블(`ai_agent_checkpoint`)을 체크포인트 저장소로 만든다.** `BaseCheckpointSaver`를 구현하면 LangGraph4j는 자기 저장소를 갖지 않고 우리 스키마에만 쓴다. 이중 상태 원천 문제 — [프레임워크 조사](agent-frameworks.md) 5.1의 확인 항목 2 — 는 이 방법으로 해소된다.

다만 **체크포인트와 감사 이력을 같은 표로 합치지는 않는다.** 둘은 목적이 다르다.

| | 체크포인트 (`ai_agent_checkpoint`) | 감사 이력 (`ai_agent_step` 등) |
|---|---|---|
| 답하는 질문 | 어디서부터 다시 시작하는가 | 무슨 일이 있었는가 |
| 수명 | 턴 종결 시 정리 대상이 될 수 있다 | REQ-109의 보관 기간을 따른다 |
| 형태 | 재개에 필요한 상태 전체 | 정규화된 이력 컬럼 |

같은 DB·같은 트랜잭션 경계 안에 있으므로 **원천은 하나이고, 표가 둘인 것은 분업**이다.

### 3.1 S6 — 처리 중 입력의 네 갈래 (2026-09-01 추가)

REQ-030~035이 처리 중 입력을 네 갈래로 분기하도록 개정되면서 추가한 시나리오다. **B안만 대상으로 한다** — 오케스트레이션이 B안으로 확정됐고(`02-constraints/_index.yaml` 기술 제약), 되돌림은 그래프 런타임의 시간여행 API에 걸린 문제이기 때문이다.

다른 스레드가 인스턴스 역할로 새 입력을 턴 레코드에 기록하고(S3와 같은 전달 경로), 처리 측이 스텝 경계에서 읽어 분류한 뒤 분기한다.

| # | 시나리오 | 검증 대상 | B안 |
|---|---|---|---|
| S6-boost | "지난달 것도 추가로" → 같은 턴에 반영하고 계속 | REQ-030~035 보강, 병행형 | **PASS** |
| S6-correct | "아니 2번 창고로" → **되돌려 재수행** | REQ-030~035 교정, `03-glossary/_index.yaml` turn_states 회차 | **PASS**(수정 후) |
| S6-new | "그건 그렇고 오늘 재고 얼마야" → 별도 턴 개설, 원 턴은 계속 | REQ-030~035 별개 | **PASS** |
| S6-stop | "됐어 그만" → 중단 | REQ-030~035 중단, REQ-007 | **PASS** |
| S6-block | 액션 실행 후 도착한 입력은 **BOOST로 분류돼도 차단형으로 전환** | REQ-030~035 차단형, `03-glossary/_index.yaml` turn_states 의도 확인 대기 | **PASS** |

- **분류 호출은 감사 이력에 그대로 남는다.** `scripted-classifier-v1` 호출이 스텝 이력·LLM 호출 이력에 기록되고, 다섯 시나리오 모두에서 `턴 누적 토큰 == 호출 기록 합` 대사가 일치했다 (`aidd-guide/standard/hub-conventions.md` §12.5, NFR-010~017).
- **분류 입력이 최소인지를 코드로 강제했다.** 스크립트 분류기는 프롬프트가 지침+컨텍스트 2건이 아니거나 대화 이력·조회 결과가 섞여 있으면 즉시 실패한다. REQ-030~035의 "넣지 않는 것"이 지켜지는지가 시나리오 통과 조건에 포함된다.
- S6-boost에서 주 추론 프롬프트 토큰이 37 → 46으로 늘어, 추가 입력이 실제로 다음 스텝에 병합된 것이 확인된다.

**최종 이력은 두 안이 완전히 동일하다.** S1 기준 — 스텝 5행, LLM 호출 5건, 도구 호출 4건, 누적 토큰 365, 그리고 `턴 누적 토큰 == LLM 호출 기록 합` 대사 일치.

```
turn      : status=DONE tokens=365 steps=5 actionExecuted=true
step 행   : 5   (seq 0~4, reason 노드)
llmCall 행: 5
toolCall 행: 4  (catalog_lookup / run_sql / execute_api[승인됨] / run_sql)
토큰 대사  : 턴 365 == 호출 기록 합 365 OK
```

S2에서는 두 안 모두 **강제 종료 전 3스텝 + 재기동 후 2스텝**으로 이력이 끊김 없이 이어졌고, 도구 재실행은 발생하지 않았다.

## 4. 실행 중 드러난 것

문서 비교로는 나오지 않았을 항목들이다. **이것들이 이 PoC의 실질적 산출물이다.** 4.1~4.5는 2026-08-31의 S1~S5에서, 4.6~4.9는 2026-09-01의 S6에서 나왔다.

### 4.1 `@Transactional` + `AbstractCheckpointSaver` 상속 = NPE (B안)

`JpaCheckpointSaver`에 `@Transactional`을 붙이자 첫 실행에서 터졌다.

```
NullPointerException: Cannot invoke "ReentrantLock.lock()" because "this._lock" is null
```

Spring이 CGLIB 프록시를 **Objenesis로 생성하면서 생성자를 호출하지 않아**, 상위 클래스 `AbstractCheckpointSaver`의 `private final ReentrantLock _lock` 이 초기화되지 않았다. `list/get/put/release`가 `final`이라 프록시가 오버라이드하지 못하고 그대로 실행되면서 null을 만난다.

- **대응**: saver에는 AOP 어노테이션을 붙이지 않고, 트랜잭션 경계를 별도 빈(`CheckpointStore`)으로 분리해 위임한다.
- **일반화**: **프레임워크의 추상 클래스를 상속한 빈에 Spring AOP 어노테이션을 붙이지 않는다.** 이 규칙은 LangGraph4j에 한정되지 않으며, `aidd-guide/standard/hub-conventions.md` §12.4의 계층 규칙에 덧붙일 만한 항목이다.

### 4.2 조기 반환 경로마다 중단 검사를 다시 넣어야 한다 (A안)

2프로세스 S3에서 **A안이 처음에 실패했다.** 중단 요청이 기록됐는데도 턴이 `WAITING_USER`로 진행됐다.

원인은 검사 지점의 위치다. A안은 `while` 루프 머리에서 중단 요청을 확인하는데, **승인 게이트가 루프를 조기 반환**하므로 그 경로에서는 검사를 통과하지 않는다. 즉 `LLM 호출 → 승인 필요 판정 → 반환` 구간에 검사 지점이 없었다.

- **대응**: 승인 게이트 직전에 검사를 한 번 더 넣었다. 재실행 결과 PASS.
- **일반화**: A안에서 중단 확인 지점은 **우리가 코드에 박은 위치에만 존재한다.** 조기 반환 경로가 늘어날수록(조회 계획 확인 REQ-022, 추가 정보 요구 REQ-005, 처리 불가 종결 REQ-025) 빠뜨릴 자리가 함께 늘어난다. B안은 `interrupt()`가 **모든 노드 진입 시점에 호출**되므로 검사 지점이 구조적으로 강제된다 — B안이 같은 시나리오에서 처음부터 통과한 이유다.
- **성격**: A안의 한계가 아니라 **규율의 문제**다. 다만 "빠뜨리면 REQ-030~035을 위반하는데 테스트하지 않으면 드러나지 않는다"는 점은 기록해 둘 가치가 있다.

### 4.3 인터럽트는 상태의 순수 함수다 — REQ-017이 무한 루프에 빠졌다 (B안)

S5에서 **B안이 처음에 실패했다.** 비승인으로 재개하자 같은 노드에서 다시 승인 요청이 나왔고, 턴은 영원히 `WAITING_USER`에 머물렀다.

원인은 재개 의미론이다. `GraphInput.resume(...)`은 마지막 체크포인트로 되돌아가 인터럽트됐던 노드를 **다시 진입**하고, `interrupt()`를 **다시 평가**한다. 판정이 `!state.approved()` 였으므로 비승인은 영구히 인터럽트 조건을 만족한다.

- **대응**: "승인됐다(`approved`)"와 "승인 여부를 물어서 답을 받았다(`approvalDecided`)"를 상태에서 분리했다. 인터럽트 판정은 후자만 본다.
- **일반화**: **HITL 게이트의 판정 조건에는 "이미 물었다"는 사실이 포함되어야 한다.** REQ-017("명시적 승인이 아닌 모든 입력은 비승인으로 취급하고 같은 턴을 계속 처리한다. 나중에 다시 되묻지 않는다")은 이 구분 없이는 구현되지 않는다. A안은 재개가 그냥 다음 코드 줄이라 이 함정이 없다.

### 4.4 그래프 노드는 5.1의 스텝이 아니다 (B안)

훅을 전역으로 걸었더니 스텝 이력이 **5행이 아니라 9행**으로 나왔다. `reason`과 `tool` 노드가 각각 한 행을 만들었기 때문이다.

5.1의 스텝은 **"agent ↔ LLM 1회 왕복"**이지 그래프 노드가 아니다. 훅을 `reason` 노드에 한정해 두 정의를 맞췄고, 도구 실행은 별도의 도구 호출 이력이 담당하게 했다.

- **일반화**: 그래프 구조와 우리 용어(`03-glossary/_index.yaml`)를 **1:1로 매핑하지 않는다.** 노드 분할은 실행 편의의 문제이고, 스텝은 감사·과금의 단위다. 두 개념이 우연히 일치할 때만 훅을 전역으로 건다.

### 4.5 인터럽트된 노드는 `WrapCall`을 타지 않는다 (B안)

2장의 실행 순서에서 `interrupt()` 판정은 **`WrapCall` 앞**에 있다. 따라서 인터럽트로 멈춘 노드는 감싸기 훅을 통과하지 않고, 거기에 붙인 이력 기록도 실행되지 않는다.

- **함의**: 승인 대기·중단 전이는 **훅이 아니라 오케스트레이터가 `InterruptionMetadata`를 받은 자리에서 기록**해야 한다. PoC는 그렇게 했고 이력이 맞아떨어졌다.
- **주의**: `BeforeCall` 훅은 인터럽트 앞에 있으므로 **인터럽트되는 노드에서도 실행된다.** 쿼터 검사를 Before에 둔 것은 이 점에서 안전하지만, Before에 부작용을 두면 인터럽트마다 반복 실행된다.

### 4.6 시간여행의 갱신은 **저장소에 없는 id로 온다** (2026-09-01, S6-correct)

교정의 되돌림은 `CompiledGraph.updateState`로 구현된다. 첫 실행에서 교정이 통째로 실패했다.

```
교정 실패: LeaseLostException: checkpoint update rejected: thread=4 fence=1
```

`updateState`는 되돌린 지점에 **새 id의 체크포인트**를 만들면서 saver의 **갱신 경로**(`updatedCheckpoint`)로 들어온다. 우리 저장소는 4.4에 따라 갱신을 `UPDATE ... WHERE checkpoint_id = :id AND EXISTS(점유 조건)`으로 구현했는데, 그 id가 아직 없으므로 0행이 나온다. 그리고 **0행을 점유 상실로 해석하는 것이 4.4의 규약**이다. 즉 점유는 멀쩡한데 점유 상실로 오판했다.

- **대응**: 갱신을 **점유 보호를 유지한 채 삽입으로 흘러내리는 upsert**로 바꿨다. UPDATE가 0행이면 점유를 따로 확인하고, 점유가 유효하면 새 분기로 INSERT한다. 점유가 무효일 때만 `LeaseLostException`이다.
- **일반화**: **"0행 = 점유 상실"은 조건이 점유뿐일 때만 성립한다.** WHERE에 점유 외의 조건(여기서는 `checkpoint_id`)이 섞이면 0행의 의미가 둘이 되고, 안전한 쪽으로 오판하는 것이 아니라 **정상 처리를 실패로 만든다.** 4.4의 조건부 쓰기를 확장할 때 매번 확인해야 하는 항목이다.
- **성격**: 이것은 "우리 테이블을 체크포인트 저장소로 만든다"(2.1)는 결정의 숨은 비용이다. 프레임워크 기본 saver를 썼다면 나오지 않았을 문제이며, 상태 원천 단일화의 대가로 **saver 프로토콜의 모든 경로를 우리가 책임진다**는 뜻이다.

### 4.7 교정은 도구를 다시 실행하고, 스텝 순번이 중복된다 (2026-09-01, S6-correct)

수정 후 교정이 정상 동작했다. 되돌림 지점은 가장 오래된 체크포인트였고, 최종 이력은 다음과 같다.

```
체크포인트 9건 : seq 0~2 (버려진 것) + seq 3~8 (재수행)
step 행   : 4  (seq = 0, 0, 1, 2)
toolCall 행: 3  (catalog_lookup 2회, run_sql 1회)
```

두 가지가 함께 드러났다.

- **교정은 되돌린 지점 이후의 도구를 다시 실행한다.** `catalog_lookup`이 두 번 나갔다. 조회라 무해했지만 **액션이었다면 중복 실행**이다. REQ-030~035이 "액션을 이미 실행한 턴에서는 차단형으로 전환한다"고 정한 것이 이 실측으로 정당화된다 — S6-block이 그 경로를 통과했다.
- **교정 전후의 스텝 순번이 중복된다** (`seq = 0, 0, 1, 2`). 2장이 "이력의 혼선"을 점유 문제로 들었는데, **교정에서는 점유가 정상인데도 같은 현상이 난다.** 두 기록의 `lease_fence`가 모두 1이므로 **4.4의 구분자가 여기서는 통하지 않는다.**

이 발견이 `03-glossary/_index.yaml` turn_states의 **회차(Revision)** 도입으로 이어졌고, 4.9에서 다시 검증했다.

### 4.8 "입력이 있다"와 "분류했다"를 나눠야 한다 (2026-09-01, S6)

4.3에서 승인에 대해 나온 함정이 처리 중 입력에서 그대로 반복된다. 인터럽트 판정은 재개할 때마다 다시 평가되고 `BeforeCall` 훅은 인터럽트되는 노드에서도 실행되므로(4.5), **분류 결과를 남기지 않으면 재평가마다 분류 LLM 호출이 다시 나간다.**

- **대응**: 분류 결과를 턴 레코드에 기록하고, 값이 있으면 분류를 건너뛴다. 다섯 시나리오 모두 분류 호출이 정확히 1건이었다.
- **일반화**: 4.3의 결론이 승인에 한정된 것이 아니었다. **재개 지점에서 평가되는 모든 판정은 "물었다/했다"는 사실을 상태에 포함해야 한다.** 이 PoC에서 같은 형태의 함정이 두 번 나왔으므로, 세 번째가 있다고 보는 편이 안전하다.

### 4.9 회차를 얹은 재실행 (2026-09-01)

`03-glossary/_index.yaml` turn_states가 회차를 등재한 뒤 PoC에 구현해 S6-correct를 다시 돌렸다. 회차는 점유 토큰과 같은 경로(`RunnableConfig.metadata`)로 노드·훅·saver에 전달되며, 되돌림에서만 올라간다.

```
[교정] 되돌림 지점 node=__START__ / 회차 0 -> 1 / 체크포인트 3건, 이전 회차 3건 정리

turn      : status=WAITING_USER revision=1 tokens=349 steps=4
step 행   : rev=0 seq=0 fence=1        <- 버려진 시도
            rev=1 seq=0 fence=1        <- 재수행
            rev=1 seq=1 fence=1
            rev=1 seq=2 fence=1
toolCall 행: rev=0 catalog_lookup / rev=1 catalog_lookup / rev=1 run_sql
체크포인트 : 6건, 전부 rev=1 (이전 회차는 정리됨)
```

검증 항목과 결과다.

| 항목 | 근거 | 결과 |
|---|---|---|
| 스텝 식별자 `turn + revision + seq`가 유일하다 | 5.1 용어 | **PASS** |
| **`fence + seq`는 여전히 중복된다** | 회차가 필요한 이유 그 자체 | **PASS**(중복 확인) |
| 버려진 회차의 감사 이력이 남아 있다 | PRN-07, REQ-108 | **PASS** |
| 이전 회차의 체크포인트가 정리됐다 | REQ-109 | **PASS** |
| 정리 후에도 재개가 정상 동작한다 | — | **PASS** |
| 토큰 대사 일치 | NFR-010~017 | **PASS** (349 == 349) |

- **fence 중복을 성공 조건으로 삼은 것이 이 시나리오의 핵심이다.** 회차가 없으면 판별이 불가능하다는 사실을 시나리오가 직접 주장한다. 회차만 검사하면 "왜 필요한가"가 검증에서 빠진다.
- **도구 호출 이력도 회차로 갈린다.** `rev=0`의 `catalog_lookup`과 `rev=1`의 것이 구분되므로, REQ-107의 "어떤 데이터를 보고 실행했는가"가 최종 회차 기준으로 답해진다.
- **버려진 체크포인트를 지워도 시간여행 재개가 동작한다.** `updateState`가 만든 분기 체크포인트는 상태 전체를 담고 있어 조상 체인을 필요로 하지 않는다. REQ-109의 조기 정리가 재개를 깨지 않음이 확인됐다 — 정리 후에도 교정이 끝까지 진행되어 승인 대기까지 도달했다.
- 회차 도입 후 전체 회귀(B안 S1·S5·S6 5종·L1~L5, A안 S1·S5)를 다시 돌려 **실패 0건**이었다.

**버려진 체크포인트는 정리하지 않으면 남는다.** `updateState`가 덮어쓰지 않고 새 분기를 덧붙이기 때문이다. 감사 관점에서 "무엇을 하다가 무엇으로 바꿨는가"는 **감사 이력이 답하므로**(위 표), 재개 상태까지 남길 이유가 없다 — REQ-109의 조기 정리가 이 판단이다.

### 5.2 의존성 반입 규모

로컬 Maven 서버로 해결되는 문제지만, 목록의 크기는 여전히 의미가 있다.

- **`langgraph4j-core`가 끌고 오는 전이 의존성은 `org.bsc.async:async-generator` 하나다.** 나머지는 `slf4j-api`로, Spring Boot가 이미 갖고 있다.
- `langgraph4j-core`의 pom에서 **Gson과 Jackson은 `provided` 스코프**다. 즉 기본 직렬화기를 쓰지 않으면 딸려오지 않는다. **Spring AI 2.0이 Jackson 3(`tools.jackson`)을 쓰는데 LangGraph4j가 Jackson 2를 강제하는 충돌은 발생하지 않았다.** PoC는 우리 saver가 직렬화를 맡았으므로 이 경로를 아예 타지 않는다.
- 정리하면 **B안 채택의 의존성 증분은 jar 2개**다. 전체 80개 중 2개이며, 이 축에서 B안의 부담은 사실상 없다.

## 6. 판단

### 6.1 확인된 것

1. **B안은 우리 통제를 전부 수용한다.** 쿼터는 `BeforeCall`, 스텝 이력은 `WrapCall`, 중단·승인은 `InterruptableAction`, 상태 저장은 우리 테이블에 쓰는 saver로 들어갔다. 프레임워크가 우리 정책을 밀어내는 지점은 없었다. 사용자 질문 2에 대한 답은 **가능하다**이다.
2. **상태 원천은 하나로 만들 수 있다.** `ai_agent_checkpoint`가 곧 LangGraph4j의 저장소이며, 별도 저장소는 존재하지 않는다. [프레임워크 조사](agent-frameworks.md) 5.1의 확인 항목 2는 해소됐다.
3. **두 안 모두 S1~S5를 통과했고 이력이 동일하다.** 기능적 우열은 이 범위에서 없다.
4. **각 안에는 서로 다른 종류의 함정이 있다.** A안은 검사 지점 누락(4.2), B안은 재개 의미론(4.3). 둘 다 테스트 없이는 드러나지 않았다.
5. **의존성·버전 충돌 리스크는 낮다.** Boot 4 / Spring AI 2.0 / LangGraph4j 1.8.25 조합이 그대로 동작했고, 증분 jar은 2개다.

### 6.2 확인되지 않은 것

이 PoC의 범위 밖이며, 채택 전에 답이 필요한 항목이다.

| # | 항목 | 왜 남았나 |
|---|---|---|
| 1 | **실제 LLM 스트리밍과 청크 경계 중단** | 스크립트 구현체는 스트리밍하지 않는다. REQ-030~035이 요구하는 "청크 경계에서 중단 확인"은 실모델 검증이 필요하다. REQ-006의 상태·시간 표시는 실제 작업 이력과 서버 시각으로 별도 검증하며 실모델 스트리밍만을 전제로 하지 않는다 |
| 2 | ~~**같은 턴을 두 인스턴스가 동시에 잡는 경우**~~ | **해소됨** — [[턴 실행 점유 설계](../design/turn-execution.md)](../design/turn-execution.md)로 설계하고 L1~L6으로 검증했다. 지적한 대로 LangGraph4j 체크포인터에는 분산 락이 없어 우리가 만들었다 |
| 3 | **PostgreSQL 실환경** | H2로 대역했다. `ai_agent_checkpoint`의 상태 컬럼 크기·인덱스·동시 갱신은 실 DB에서 봐야 한다 |
| 4 | **분기가 많은 실제 흐름** | 5.1에서 적은 대로, 코드량 비교의 결론은 이 PoC 규모에 종속된다 |
| 5 | **컨텍스트 총량 관리 (REQ-003, REQ-002)** | 두 안 모두 메시지를 그대로 누적했다. 과거 턴 요약·원본 재조회는 어느 안에서도 프레임워크가 주지 않는다 ([프레임워크 조사](agent-frameworks.md) 3.1 F축) |
| 6 | **토큰 계측 정확도** | 스크립트 구현체의 토큰은 가짜다. ARCH-040가 지목한 API 구독 확보 후 최우선 검증 항목 그대로다 |
| 7 | **의도 분류의 정확도** | S6의 분류기는 키워드 고정 매핑이다. 검증한 것은 **분류 결과가 그래프 실행에 어떻게 반영되는가**이지 분류가 맞는가가 아니다. 오분류율과 REQ-030~035의 보수적 우선순위(`CORRECT > STOP > NEW > BOOST`)가 실제로 안전한지는 실모델로만 확인된다 |
| 8 | **A안의 처리 중 입력 분기** | S6는 B안만 돌렸다. A안에서 교정의 되돌림은 `conversationJson`을 직접 잘라내는 작업이 되며, 4.2의 "검사 지점을 우리가 박아야 한다"가 여기서도 반복될 것으로 보인다. 오케스트레이션이 B안으로 확정됐으므로(`02-constraints/_index.yaml` 기술 제약) 확인하지 않았다 |

### 6.3 두 안의 성격 차이 — 요약

| | A안 (Spring AI 단독) | B안 (+LangGraph4j) |
|---|---|---|
| 스텝 루프 | 우리 `while` | `CompiledGraph` |
| 재개 지점 | 우리가 정의·직렬화 (`conversationJson`) | 체크포인트 (우리 테이블에 저장) |
| 중단 확인 지점 | **우리가 박은 자리에만** | **모든 노드 진입 시점** |
| 승인 게이트 | 코드 흐름의 조기 반환 | `InterruptableAction` + 재개 |
| 재개 시 재평가 | 없음 (다음 줄부터) | **있음** — 판정 조건 설계 필요 (4.3) |
| 감사 삽입 지점 | 코드 안 임의 위치 | 훅 (단 인터럽트 경로는 예외, 4.5) |
| 흐름의 가시성 | 코드를 읽어야 안다 | 그래프 정의로 드러난다 (Mermaid 출력 가능) |
| 실패 양상 | 검사 지점 누락 → 조용히 정책 위반 | 상태 설계 실수 → 루프·재개 이상 |
| 의존성 증분 | 0 | jar 2개 |
| 코드량 (이 PoC) | 129줄 | 380줄 |

## 7. 다음 단계

6.2의 미확인 항목 중 **1(스트리밍 중단)과 2(턴 점유)** 는 어느 안을 택하든 필요한 작업이므로, 선택보다 먼저 설계되어야 한다. 특히 2는 **프레임워크가 답하지 않는 영역**임이 이 PoC로 확인됐다.

권고 순서는 다음과 같다.

1. **턴 단위 점유(락) 설계를 먼저 확정한다.** 멀티 인스턴스에서 같은 턴의 중복 처리를 막는 장치이며, `03-glossary/_index.yaml` turn_states의 상태 전이와 함께 정의되어야 한다. 안 선택과 독립이다.
2. **API 구독 확보 후 스트리밍 구간을 이 PoC에 얹어 재실행한다.** ARCH-040가 이미 "API 구독 확보 직후 최우선 검증"으로 지목한 세 항목(토큰 집계·스트리밍·동시성)과 같은 작업이다.
3. **그 결과를 근거로 `02-constraints/_index.yaml` 기술 제약·`aidd-guide/standard/hub-conventions.md` §12.5를 개정한다.** 개정 시 반영할 항목은 아래와 같다.

| 개정 대상 | 반영할 내용 |
|---|---|
| `02-constraints/_index.yaml` 기술 제약 기술 스택 | Spring Boot 4 계열 / Spring AI 2.0 계열 명시. 오케스트레이션 계층 선택 결과 |
| `aidd-guide/standard/hub-conventions.md` §12.4 계층 구조 | 프레임워크 추상 클래스 상속 빈에 Spring AOP 어노테이션 금지 (4.1) |
| `aidd-guide/standard/hub-conventions.md` §12.5 외부 모델 호출 규칙 | 프레임워크 모델 추상화는 FEAT-304 **내부 구현**으로만 둔다는 경계 ([프레임워크 조사](agent-frameworks.md) 3.3). 의존성 규칙 검사 대상에 추가 |
| REQ-030~035 (검토) | 중단 확인 지점을 "스텝 경계"가 아니라 **"모든 조기 반환 경로를 포함한 스텝 경계"**로 명확화할지 (4.2) |

> **REQ-030~035은 2026-09-01에 처리 중 입력의 네 갈래로 개정됐고, S6로 검증했다** (3.1, 4.6~4.8). 위 표의 REQ-030~035 검토 항목(4.2)은 A안에 관한 것이라 그대로 남는다.
