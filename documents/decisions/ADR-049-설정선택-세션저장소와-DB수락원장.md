JDBC 기본·Redis 선택을 같은 제품 artifact의 기동 설정으로 제공하고 DB 수락·회수 원장으로 접속을 판정한다. 사용자는 CR-036 A와 저장소 독립 관리 참조인 CR-035 A를 명시 승인했고, 첫 실제 사용 전 최대 1분 예약의 복구 대기를 수용했다. 이 문서는 정책 결정과 그 이유를 기록한다. 물리 모델·v2 공통 조립의 integration 영향 G3는 동결됐으며 승인 상태/일자는 `project.state.yaml`을 따른다. system 소비 영향 G3와 실제 구현/검증은 별도다.

기존 CON-010은 Redis/JDBC 선택을 의도했지만 SLICE-307에서 검증한 조립은 JDBC 구체 저장소·같은 DB 트랜잭션에 결합됐다. Redis와 암호/이력 DB를 하나의 물리 커밋으로 처리할 수 없으며 Redis의 과거 자료 복원으로 폐기한 세션을 다시 수락해서도 안 된다. ADR-046의 영역 분리·현재 권한 보호는 유지한다. 동일 DB 세션 원자성 부분은 JDBC 경로에 한정하고 Redis 경로의 확정 후 실패 복구를 보완한다.

선택한 A는 DB에 영역·주체·현재 세대·기한·전환 epoch·수락/회수 상태를 보관하고 선택 저장소에만 인증/CSRF payload를 둔다. DB에 전체 payload를 복제하지 않는다. DB 암호·이력·구접속 회수가 확정된 뒤 새 Redis 세션을 발급하지 못하면 새 암호로 재로그인한다. 장애 때 WAS 메모리/JDBC로 자동 폴백하지 않는다. 노드마다 epoch를 바꾸지 않고 운영 전환에서만 설정판을 확정하며, 전환/되돌림은 통제된 재시작과 전체 재로그인을 따른다. 관리 API에는 인증 쿠키와 독립인 불투명 관리 참조를 제공한다. 구체 필드·기한·확정 절차는 FEAT-301.session_store_v2와 ENT-267/268이 정본이다.

대안 B는 JDBC를 인증 정본으로 유지하고 Redis를 사본으로 쓰는 것이다. 기존 물리 원자성을 유지하기 쉽지만 Redis로 인증 저장소를 교체하는 요구를 충족하지 못한다. 대안 C는 교체 구조와 Redis 지원을 미루는 것이다. 현재 구현량은 작지만 승인된 선택 요구를 충족하지 못하고 이후 계정·세션 소비 전환을 다시 해야 한다. 사용자는 A를 선택했다.

포기한 것은 Redis와 DB의 단일 물리 원자성, 매 요청 DB 조회 없는 인증, 저장소 변경 중 무중단 접속 유지다. 수락 원장·두 단계 발급·고장 복구·양 provider 시험과 운영 전환이 추가되어 구현 및 운영 비용이 높다. 쿠키는 DB와 선택 store의 발급 가능 확인 뒤에만 전달하며 확정 불명은 재실행하지 않는다.

같은 v2 artifact에서 provider를 되돌릴 때도 새 epoch와 전체 재로그인을 적용한다. 원장 검사가 없는 v1 바이너리로 되돌리는 것은 별도 복구이며, 인증 진입을 닫고 과거 payload를 무효화·검증해야 한다. 새 원장이나 자격/이력을 삭제하거나 암호를 과거로 되돌리지 않는다. SLICE-307의 v1 G4 완료와 비영향 기존 게이트는 보존하고 SLICE-308 및 실제 소비 슬라이스에서 변경 범위만 다시 검증한다.
