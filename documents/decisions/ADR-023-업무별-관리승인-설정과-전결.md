# ADR-023 — 업무별 관리 승인 설정과 저장자 전결

## 1. 맥락

도구의 허용 사용자 그룹과 실제 업무 기능 호출 대상을 바꾸면서 이력만 남기는 초안은 책임자 검토를 담지 못한다.
사용자는 도구도 지식과 같은 전체 후보 스냅샷·요청·책임자 승인 후 활성화 대상으로 정했다.
동시에 구축 기간은 통합 테스트와 책임자·관리자의 오픈 검수로 확인하므로 매 저장의 별도 요청·승인을 요구하지 않도록 했다.
후속 설명에서 지식·스키마 카탈로그·API/도구·쿼터 승급 등 각 업무의 승인 절차 사용 여부를 독립 설정하도록 요구했다.

## 2. 고려한 대안

- A — 업무별 설정 + 동일 근거의 전결 처리(선택): 구축/운영에 같은 후보·승인·반영 모델을 쓰고, 필요한 업무만 별도 승인 절차를 켠다. 혼합 세트 판정과 설정 버전 기록이 필요하다.
- B — 전역 단일 설정: 전환은 단순하지만 API는 승인하고 지식은 전결하는 등의 독립 운영이 불가능해 후속 요구에 맞지 않는다.
- C — 구축 전용 직접 저장 경로: 초기 입력은 단순하지만 스냅샷·승인 근거가 끊기고 오픈 뒤 별도 경로를 다시 만들어야 한다.

## 3. 결정

각 관리 승인 업무에 독립적인 절차 사용 설정을 두고, 미사용일 때는 저장자를 실제 전결 승인자로 기록해 유효값을 반영한다.
제품 규칙의 정본은 [REQ-601의 approval_policy](../spec/10-requirements/011-reference-integration.yaml), 설정 관리는 REQ-614다.
도구와 Hub 내부 API 변경도 같은 후보·기술 검토·최종 승인·반영 세트를 사용한다(REQ-612·608·305·306).

2026-10-22 사용자는 동일 대상의 중복 변경 요청 금지와 제출본 고정·취소 후 새 요청을 모든 관리 승인에 공통 적용하도록 제안했다. 업무별로 규칙이 달라 승인한 내용과 실제 반영 내용이 어긋나는 것을 막기 위한 보완이며, 정본은 REQ-601.request_integrity에 둔다. 같은 날 사용자가 기존 전결·부분 승인·미래 월 적용과 권한 회수 경계를 포함한 REQ-601·305·306·609·117·119 여섯 전체 보완본을 명시 확정했다. 단계 게이트·소스 구현 승인은 별도다.

## 4. 근거

구축 기간의 반복 입력을 막지 않으면서 오픈 후 책임자 승인과 변경 이력을 같은 근거로 조회할 수 있다.
전결을 삭제된 이력이나 다른 책임자의 승인으로 표시하지 않고 실제 행위자·적용 설정을 보존한다.
업무별 설정이 다른 복합 변경도 세트 전체의 유효성을 유지할 수 있다.

## 5. 포기한 것

절차 미사용 업무에서는 매 변경의 다른 사람 검토·승인을 기대하지 않는다.
유효한 작성/변경 권한이 있는 저장자가 자신의 저장 건을 전결하므로, 오픈 전 각 운영 승인 대상의 설정 확인이 필요하다.
실제 업무 실행의 사용자 확인, 외부 API 공동 오픈 검수와 코드 리뷰/배포 통제까지 생략하는 선택은 포함하지 않는다.

## 6. 되돌리기

각 설정을 사용으로 전환해 이후 변경에 별도 승인 절차를 적용할 수 있다. 기존 대기 건과 전결 기록을 소급 재작성하지 않는다.
설정·전결 모델 자체를 폐기하려면 승인 상태·권한·저장/반영 원자성·이력·API·화면·시험을 함께 수정해야 하므로 구현 후 비용이 높다.
오픈 후 전결 상태가 의도와 다르게 유지되거나 설정별로 일부 후보만 반영되는 증상이 나타나면 관련 설정/처리 근거를 확인해 재검토한다.

## 7. 영향과 후속

REQ-601·614의 공통 규칙/설정, REQ-103·105·114·117·119·205·301~308·607·608·609·611·612·616과 연결 기능·화면·PRC-09·11·12·13·권한·용어를 대조한다.
전체 REQ-612 카드는 여전히 사용자 확정 대기이며 이번 부분 정책 결정만으로 admin G1이나 구현을 승인하지 않는다.
업무별 실제 설정 키·저장/로드·설정과 처리 버전의 일관성·다중 인스턴스 전파는 REQ-614의 P2 후속,
후보/요청·전결·반영 상태와 동시성/원자성 계약은 각 요구사항의 P3 후속에서 검증한다.
