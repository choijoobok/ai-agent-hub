# ADR-001 — 턴 오케스트레이션은 상태 그래프 런타임 위에서 수행한다 (B안)

| 항목 | 내용 |
|---|---|
| 결정 일자 | 2026-09-01 (PoC 종료 시점) · **이관 2026-09-07** |
| 상태 | **설계 재현 확인됨(2026-11-10)** — ASM-003, ADR-048 승인 기준의 별도 재판정 |
| superseded_by | **ADR-048 — §8.1(2)의 판정 범위만 부분 대체**. 프레임워크 채택·자체 saver·훅/Hub 소유 결정은 이 문서를 따른다 |

| 반영 위치 | `CON-006` · `documents/design/turn-execution.md` §5 · `03-glossary/_index.yaml` framework_terms |

## 1. 맥락

턴은 **상태를 가진 지속 작업**이다(`03-glossary/_index.yaml` turn_states). 수 초에서 수 분이 걸리고,
사용자 이탈·중단·서버 장애를 견디고 재개돼야 하며(REQ-013 · REQ-016), 처리 중 사용자
개입으로 멈추고 이어가야 하고(REQ-005 · REQ-017), 처리 중 입력의 네 갈래 중 교정은
**이미 지나온 지점으로 되돌아가 다시 수행**한다(REQ-030~035).

이 넷을 직접 만들 것인가 기성 런타임에 맡길 것인가가 이 결정이다. **문서상의 비교로는
답이 나오지 않았다** — 프레임워크의 재개·개입 모델이 우리 상태 여섯과 실제로 맞물리는지는
코드로만 확인되기 때문이며, 그래서 PoC 를 돌렸다.

## 2. 고려한 대안

### 대안 B — Spring AI(모델 계층) + LangGraph4j(오케스트레이션) — **채택**
- 내용: 스텝을 노드로, 턴을 그래프 실행으로 모델링하고 체크포인트로 지속화한다.
- 장점: 재개·개입·중단(축 C·D·E)이 검증된 패턴으로 들어온다. AI 전용 DB 가 PostgreSQL
  고정(CON-001)이라 체크포인터 저장소가 그대로 맞는다. **중단 확인 지점이 모든 노드
  진입 시점에 자동으로 생긴다.** 흐름이 그래프 정의로 드러난다.
- 단점: 체크포인트가 우리 턴 이력과 **이중 상태 원천**이 될 위험 → [`ADR-003`](ADR-003-상태-원천-단일화.md) 이 그 위험을 닫았다.
  재개 시 인터럽트가 **다시 평가된다** — 판정 조건을 상태에 남기지 않으면 무한 루프가 된다.
- 비용: 의존성 증분 jar 2개. 이 PoC 규모에서 오케스트레이션 계층 380줄(A안 129줄).

### 대안 A — Spring AI 단독
- 내용: FEAT-304 구현체를 Spring AI `ChatModel` 로 두고 스텝 루프·턴 상태·재개를 직접 만든다.
- 장점: 의존성 증분 0. Spring 공식이라 수명·문서·인력 확보가 가장 안전하다. 이 PoC 규모에서 코드가 3배 적다.
- 왜 선택하지 않았나: **중단 확인 지점을 우리가 박은 자리에만 갖는다.** PoC 에서 조기 반환
  경로마다 검사를 다시 넣어야 했고(§4.2), 실제 흐름은 이 PoC 보다 분기가 훨씬 많다 —
  4단계 축소 · 조회 계획 교정 · 예제 쿼리 직접 실행 · SQL 검증 실패 재작성 · 결과 교정 ·
  처리 불가 종결. **분기가 늘어나는 만큼 검사 지점 누락이 늘고, 그 누락은 조용한 정책
  위반이다.** 코드량 역전이 어디서 일어나는지는 PoC 가 답하지 못했다.

### 대안 C — LangChain4j (+ langchain4j-agentic)
- 내용: 모델 계층부터 agentic 워크플로까지 한 라이브러리로 가져간다.
- 왜 선택하지 않았나: **agentic 모듈이 공식적으로 experimental 이다** — 문서가 모듈 전체가
  실험적이며 변경될 수 있다고 명시한다. 고객사별로 수년 유지되는 구축형 제품(CON-012·CON-013)의
  핵심 경로에 둘 수 없다.

### 대안 D — 프레임워크 없이 자체 구현
- 왜 선택하지 않았나: 공급사별 tool-call 포맷·스트리밍·에러 시맨틱·프롬프트 캐싱 대응을
  계속 따라가야 한다. 공급사 API 는 계속 바뀐다.

**배제한 후보**: Embabel(GOAP 동적 계획이 핵심 가치인데 우리 흐름은 REQ-021 에서 단계가
고정돼 있다) · Koog(Kotlin) · Google ADK Java·Semantic Kernel Java(공급사 결합이 전제 —
PRN-05 와 폐쇄망 구축형에 맞지 않는다).

## 3. 결정

**B안을 채택한다** — Spring AI 를 모델 계층으로, LangGraph4j 를 오케스트레이션 런타임으로 쓴다.

## 4. 근거

**A안과 B안은 기능적으로 대등했다**(PoC 시나리오 S1~S5 통과, 이력 동일). 갈린 것은 실패
양상이다 — A안은 **검사 지점 누락 → 조용한 정책 위반**, B안은 **상태 설계 실수 → 루프·재개
이상**. 전자는 테스트가 없으면 드러나지 않고 드러났을 때 이미 통제가 뚫린 것이다.
후자는 시끄럽게 실패한다. **PRN-03(크리티컬 경로는 서버가 규칙으로 강제한다)에서 조용한
실패를 택할 수 없다.**

**B안이 우리 통제를 전부 수용하는 것도 확인했다** — 쿼터는 `BeforeCall`, 스텝 이력은
`WrapCall`, 중단·승인은 `InterruptableAction`, 상태 저장은 우리 테이블에 쓰는 saver 로
들어갔다. **프레임워크가 우리 정책을 밀어내는 지점은 없었다.**

## 5. 포기한 것

- **의존성 증분 0 을 포기했다.** jar 2개가 들어오고, 그것이 커뮤니티 프로젝트(MIT · 소수
  메인테이너)라는 유지보수 위험을 안는다.
- **훅 실행 순서에 설계가 묶였다.** `BeforeCall → interrupt() → WrapCall → 본문 → AfterCall`
  이 바뀌면 점유 갱신·중단 확인·의도 분류의 배치가 깨진다(`03-glossary/_index.yaml` hook_order).
- **인터럽트로 멈춘 노드는 `WrapCall` 을 타지 않는다.** 승인 대기·중단의 이력을 훅으로
  일원화할 수 없어 오케스트레이터가 따로 남긴다.
- **노드를 스텝과 1:1 로 두는 자유를 잃었다** — 노드 분할은 구현 사정이고 스텝은 과금
  단위다(`03-glossary/_index.yaml` confusions 첫 항목).

## 6. 되돌리기

- 되돌릴 수 있는가: **어렵다.** 오케스트레이션 계층 전체와 재개 상태 스키마가 바뀐다.
- 되돌리는 방법: A안으로 내려가면 그래프 정의를 `while` 루프로, 체크포인트를 자체 직렬화로
  옮기고 **모든 조기 반환 경로에 중단 검사를 다시 심는다**.
- 예상 비용: 오케스트레이션 계층 재작성 + `documents/design/turn-execution.md` §5 재설계 +
  이력·재개 스키마 마이그레이션. **구현 착수 후에는 슬라이스 여러 개가 재작업 대상이 된다.**
- 되돌려야 한다는 신호: ① LangGraph4j 유지보수가 멈춘다 ② 훅 실행 순서가 바뀌어 우리
  배치가 깨진다 ③ 실제 흐름의 분기에서 그래프 상태 설계가 감당되지 않는다 ④ 폐쇄망
  고객사가 커뮤니티 라이선스 의존을 수용하지 않는다.

## 7. 영향

- 산출물: `CON-006` · `documents/design/turn-execution.md` §5·§6 · `03-glossary/_index.yaml`
  framework_terms 와 hook_order · `31-features/_index.yaml` FEAT-201(질의 처리 오케스트레이션).
- 후속으로 정해야 할 것: **실제 LLM 스트리밍과 청크 경계 중단**(PoC 는 스크립트 구현체라
  스트리밍하지 않았다) · **PostgreSQL 실환경**(H2 로 대역했다) · **분기가 많은 실제 흐름에서의
  코드량과 상태 설계** · 라이선스·공급망 전이 의존성 확인.

## 8. 이관 당시 미확인 사유와 검증 이력

**PoC 코드가 이관되지 않았다.** 원본 저장소의 `poc/` 에 있었고 판단 후 폐기 대상이었다.
그래서 L1~L6·S1~S6 의 결과를 **재현할 수 없고**, ASM-003 이 그 사실을 가정으로 안고 있다.
**G3 에서 확인할 것은 결론이 아니라 재현 가능성이다** — 실환경(PostgreSQL · 실모델 ·
스트리밍)에서 시나리오를 다시 세우는 것이 그 확인이다.

### 8.1 최초 G3 확인 기준 — 변경 전 기록

최초 기준은 아래 넷을 모두 재현해야 ASM-003 을 `확인됨`으로 바꾸는 것이었다. 현재는 1·3·4번과 [ADR-048 §3.1](ADR-048-설계재현과-운영API-수락분리.md)의 2번을 함께 적용한다. **통과했다는 문장만 남기지 않고,
각 항목의 입력·기대값·실제값을 실행 가능한 테스트로 남긴다.**

1. **PostgreSQL 실제 DB + 자체 saver** — `ai_agent_checkpoint` 를 `CheckpointSaver` 로 사용해
   중단·재개·교정 뒤 현재 회차의 체크포인트만 남고, 감사 이력과 재개 상태가 갈리지 않는다.
2. **실제 모델 스트리밍 + 청크 경계 중단** — 스트리밍 중 중단 요청이 들어오면 다음 청크
   경계에서 멈추고, 중단 뒤 모델 출력·상태 전이·토큰 사용량이 누락 없이 기록된다.
3. **훅 실행 순서 회귀** — `BeforeCall → interrupt() → WrapCall → 본문 → AfterCall` 순서를
   버전 고정 테스트로 잠그고, 인터럽트된 노드는 `WrapCall` 을 타지 않는다는 기대값을 확인한다.
4. **제품 통제의 소유권** — LangGraph4j 는 실행 지점만 제공하고, 쿼터 판정·권한·보안·감사
   규칙과 데이터는 Hub 구현이 소유한다. 쿼터 거부가 노드 본문 전에 적용되고, 승인·중단 이력은
   `WrapCall` 에 의존하지 않고 오케스트레이터가 별도로 남기는 것을 확인한다.

### 8.2 2026-11-10 조정 전 부분 재현

이 절은 ADR-048 승인 전 판정의 기록이다. 현재 기준과 재판정은 §8.3을 따른다.

[실환경 재현 근거](../research/orchestration-runtime-verification.md)에 고정 버전·실제 PostgreSQL·실모델 정상/중단·규칙 반전 시험과 실행 소스를 남겼다. §8.1의 자체 saver/훅 순서·Hub 소유 원칙은 격리 실험에서 재현했다. CLI의 중단 접수 ACK/interrupted와 수신 청크의 반영 차단은 확인했지만 공급자 최종 계량/원격 종료를 확인하지 못했다. ASM-003은 미확인으로 유지하며 이 기록은 기존 결정이나 확인 기준을 낮추지 않는다.

2026-11-10 [Codex·Claude 추가 계량 검증](../research/model-provider-usage-verification.md)에서도 중단 최종량 귀속은 확인되지 않았다. CLI 종결/기존 숫자 재표시·오류0을 최종량으로 승격하지 않는다. 남은 기준은 §8.1(2)의 토큰 기록 완전성이며 원격종료 관측을 신규 게이트 조건으로 추가하지 않는다.

### 8.3 2026-11-10 판정 경계 조정과 재판정

사용자가 ADR-048 A를 승인했다. §8.1(2)의 설계 판정은 정상/중단 상태·원천 관측의 보존과 UNKNOWN 처리로 한정하고, 공급 경로의 최종 계량·원격 취소·재시도 지원 수락은 ARCH-032에 남긴다. 이전 기준의 부분 미통과를 소급해 통과로 바꾸지 않는다.

[실환경 재현의 새 기준 대조](../research/orchestration-runtime-verification.md)는 정상 종결 오표기를 수정한30단언, 점유 우회/정상→취소 오표기 변이2종 탐지와 CLI 계량 반례를 대조해 네 설계 항목을 모두 확인했다. ASM-003은 확인됨으로 재판정한다. 실제 제품 원장/쿼터 통합·공급 조합별 운영 API 수락은 미실행이며 integration/agent G3 승인을 이 기록으로 대신하지 않는다.
