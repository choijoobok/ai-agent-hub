# ADR-028 — 계획 배출을 거친 순차 재기동과 연결 호환성

| 항목 | 내용 |
|---|---|
| 일자·상태 | 2026-10-27 · accepted · 사용자 제안에 따른 방향 확정 |
| 등급 | High — 배포 중 실행 허용·대기·연결 효력에 영향 |
| 적용 차수 | RM-P1 |
| 정본 | [ARCH-028](../spec/20-architecture/014-admin-contracts.yaml), [ARCH-070](../spec/20-architecture/013-execution-lease.yaml), [REQ-105](../spec/10-requirements/003-security.yaml) |
| 승인 근거 | 사용자: 한 서버의 추가 접속을 막고 처리 중 작업이 끝나면 재기동한 뒤, 다른 서버의 추가 접속을 막아 새 서버로 보내고 같은 절차를 반복한다 |
| 범위 | 순차 운영의 설계 방향이다. 실제 무중단 검증·admin G2 승인·소스 구현 승인은 별도다 |

## 1. 맥락

초안은 연결 변경 때 관련 실행 경로를 모두 정지하는 방식을 권장했다. 사용자는 다른 서버가 서비스를 계속하는 순차 재기동을 제안했다.
기존 ARCH-070의 종료 신호 처리는 실행 중 스텝 뒤 턴을 중단한다. 사용자가 말한 완료 대기는 종료 신호 **전**에 서버를 비우는 계획 배출로 구분해야 한다.
DB 연결의 기동 로드는 이미 정해져 있다. API·모델 배포 연결도 재기동으로 반영하되 승인 대상과 진행 시도의 고정 구성을 보존해야 한다.

## 2. 대안과 결정

| 대안 | 장점 | 대가·위험 | 판정 |
|---|---|---|---|
| 전체 관련 경로 정지 후 일괄 재기동 | 구·신 실행의 공존을 막기 쉬움 | 호환 변경에도 실행 중지 구간 발생 | 초기 AI 권고. 일반 배포 기본안에서 제외 |
| 계획 배출 후 순차 재기동 | 다른 서버가 서비스를 계속하고 실행 중 작업의 정상 완료를 기다림 | 노드별 신규 배정 차단·완료 판정·구신 호환성 검증 필요 | 사용자 선택 |
| 온라인 효력 원장과 연결 동적 교체 | 프로세스 재기동 없이 연결을 바꿀 여지 | 원장 장애·호출 경합·연결 수명·복구의 추가 구현 | 이번 기본안에서 제외 |

**구·신 구성의 호환성을 확인한 배포는 계획 배출 후 순차 재기동한다.** 호환되지 않는 변경의 기존 전환 규칙까지 무중단으로 바꾸는 결정은 아니다.

## 3. 두 서버의 기본 순서

| 순서 | 서버 A | 서버 B |
|---|---|---|
| 1 | 새 접속·새 작업 배정을 닫고 맡은 실행을 마침 | 정상 서비스 |
| 2 | 배출 완료 후 재기동·검수. 검수 전에는 새 작업을 받지 않음 | 정상 서비스 |
| 3 | 준비 완료 확인 후 새 접속·작업을 받음 | 새 접속·새 작업 배정을 닫고 맡은 실행을 마침 |
| 4 | 정상 서비스 | 배출 완료 후 재기동·검수 |
| 5 | 정상 서비스 | 준비 완료 확인 후 정상 서비스 |

3단계에서 새 A와 배출 중인 구 B의 실행은 잠시 공존할 수 있다. 이것을 금지하기보다 아래 호환성·현재 효력 조건으로 검증한다.
A 검수 실패·용량 부족이면 B의 신규 접수는 유지하고 전환을 보류한다. 서버가 더 많으면 같은 원칙으로 순차 적용한다.

### 3.1 추가 접속 차단의 범위

로드밸런서의 새 HTTP 요청뿐 아니라 새 턴/시도·개인 순서 대기에서의 실행 획득·사용자대기 재개·원천 후속 페이지·스케줄/예약·임베딩 작업의 **새 배정**을 닫는다.
이미 실행을 시작한 작업의 다음 스텝·점유 갱신·중단 입력 처리·결과/사용량/감사 저장은 계속한다. 사용자의 기존 중단 요청은 정상 처리한다.
새 작업 획득과 배출 전환이 경합해도 완료 판정 뒤 작업이 새로 붙지 않도록 같은 배정 경계에서 직렬화하거나 거부한다.
진행 중 HTTP 요청이나 외부 호출 수만 0이라는 이유로 배출 완료라고 판정하지 않는다.

### 3.2 완료 대기와 종료 신호

계획 배출은 그 노드가 맡은 실행과 종료 기록이 완료되고 이후 송신할 작업이 남지 않았음을 확인하는 단계다.
오래 실행되는 작업이 남으면 **재기동을 보류하고 다른 서버의 서비스를 유지**한다. 시간 경과만으로 그 작업을 강제 중단하지 않는다.
배출 완료 뒤 종료 신호를 보낸다. ARCH-070의 종료 신호 후 스텝 경계 중단·드레인 상한은 강제/긴급 종료 경로에 유지하며 계획 배출의 자동 중단 시간으로 쓰지 않는다.
전송 후 결과를 확정하지 못한 업무 실행은 REQ-105의 결과 불명 처리 대상이다. 재기동 완료를 성공·미전송의 근거로 삼거나 다른 노드에서 재전송하지 않는다.

### 3.3 사용자대기·미시작 작업과 세션

사용자대기는 실행 중 작업 수에 넣어 사용자의 응답까지 서버가 붙잡고 기다리지 않는다.
유효한 대기 응답은 다른 가용 노드가 공유 상태·현재 권한·개인 한도·단일 점유를 검증해 이어받는다. 대기·승인·보존 기한을 배포 때문에 늘리지 않는다.
미시작 접수도 영속 접수·중복 획득 방지·순서 계약이 있는 경로만 인계한다. 메모리 큐만 있는 작업은 원 노드에서 배출하거나 해당 기능의 인계 계약을 먼저 구현한다.
점유가 만료된 실행 중 턴이나 종결 시도를 자동 인계하는 정책으로 확대하지 않는다.
현재 공통 진행 상태 저장소가 존재한다는 사실은 작업 큐 이전의 구현 근거가 아니다.
두 서버의 세션 저장소·쿠키·인증/권한 속성 형식과 실행 상태가 호환돼야 한다. 공유 저장소만으로 구·신 코드 간 세션 유지가 보장되지는 않는다.

## 4. 연결 식별과 구·신 구성의 공존

연결 식별자, 불변 연결 리비전, 환경별 배포 세대를 구분한다. 변경하지 않은 연결 리비전은 유지할 수 있다.
배포 산출물이 리비전을 발급하고 고객사/환경·최종 설정 우선순위·노드별 주입값과 묶음 포함 관계를 검수한다. 같은 리비전의 다른 정의를 허용하지 않는다.
일반 감사·카드에는 비밀값이나 비밀 해시를 남기지 않는다. 미사용 선택 연동의 비밀을 전체 기동 조건으로 만들지 않는다.

배포 중 허용할 구·신 세대와 연결 리비전, 배출/신규 배정 가능 노드를 배포 절차에서 명시한다. 노드가 자기 파일만 보고 현재 효력이나 서비스 재가입을 선언하지 않는다.
배출 완료한 구 프로세스의 재가입·자동 재기동과 새 작업 획득을 막는다. 배출 중인 구 프로세스는 등록된 기존 작업만 마무리한다.

### 4.1 호환 배포

공유 DB 스키마, 로그인 세션, 실행 상태/체크포인트, 메시지·설정 정의/기본값, 공개 호출 계약이 구·신 코드에서 함께 유효해야 한다.
진행·대기 시도가 고정한 모델·공급 경로·effort와 보안상 유효한 연결 정의를 수신 노드가 지원해야 한다.
새 모델의 신규 선택과 진행 시도의 기존 선택 유지는 REQ-116·ARCH-040을 따른다. 구 노드가 해석하지 못하는 새 정의를 공통 기본값으로 먼저 활성화하지 않는다.
연결 성공만으로 동일 목적지·테넌트·인증 주체/권한 범위를 증명하지 않는다. 비밀 교체의 승인 유지 예외는 REQ-105의 검수 근거를 따른다.
같은 배포 세대나 호환 판정도 호출 직전 현재 권한·신원 매핑·승인 대상 대조를 대신하지 않는다. 확보한 불변 연결 객체로 전송한다.

### 4.2 별도 전환이 필요한 변경

실제 목적지·주체가 달라지는 비호환 연결 교체는 영향 연결의 구 실행이 더는 송신할 수 없음을 확인한 뒤 새 효력을 연다. 영향 없는 경로는 가능한 범위에서 계속 서비스한다.
구 송신 종료는 현재 통신 0건뿐 아니라 기존 실행의 향후 해당 연결 호출 가능성 제거까지 포함한다. 필요한 대기는 영향 경로의 중지 구간으로 보고한다.
ARCH-019의 계약 주 버전 전환, 호환되지 않는 세션/저장 형식·파괴적 스키마 변경은 기존 별도 전환 규칙을 적용한다.
CR-025에 명시된 일괄 전환·세션 종료 배포를 이번 방향 결정만으로 순차 배포 가능하다고 변경하지 않는다.
임베딩 모델/벡터 설정과 환경 마스터 키 교체도 호환 배포로 자동 분류하지 않고 ARCH-040·REQ-403·ADR-022의 제약을 대조한다.
유효 대기 시도의 호환 정의를 공급할 수 없으면 일반 배포 준비 미완료다. 회수된 비밀·권한을 복원하거나 대기 턴을 임의 종결해 해결하지 않는다.

## 5. 실패·복구와 운영 전제

서비스 중인 나머지 노드가 부하를 감당하는지, 새 노드가 실제 연결·공유 상태·버전 계약을 처리하는지 확인한 후 전환한다.
제어 과정 실패·부분 기동·신 노드 검수 실패에서는 다음 서버를 내리지 않는다. 구 세대 신규 배정을 되열 때에도 현재 권한·연결 유효성과 호환성을 다시 확인한다.
롤백은 새 배포 세대로 기록하고 암호문/키의 짝과 실제 자격증명 유효성을 검수한다. 회수된 승인·만료된 자료·종결 시도를 복원하지 않는다.
무중단 여부는 접수 가용성·로그인 유지·기존 작업/대기 보존·처리 용량의 실환경 시험으로 판정한다. 단일 노드 설치나 비호환 변경에는 같은 보장을 붙이지 않는다.

## 6. 포기한 것·되돌리기·검증

모든 변경을 일괄 정지로 단순화하는 편의성을 포기한다. 장기 작업 때문에 배포 완료가 늦어질 수 있다.
순차 배포를 지원하지 못하는 기능은 인계/배출 계약을 추가하거나 영향 범위를 정지해야 하며, 무중단 완료로 기록하지 않는다.
되돌릴 때는 새 결정으로 ARCH-028·070·배포/복구 절차와 호출 계약 시험을 함께 수정한다. 구현 뒤 되돌리기 비용은 높다.

검증: 신규 배정/배출 경합, 오래 실행되는 작업, 사용자대기 다른 노드 재개, 메모리 큐 인계 불가, 중복 획득, 신 노드 실패/용량 부족, 구 프로세스 재가입, 설정/세션/DB 혼재, 승인 후 대상 변경, 결과 불명과 롤백.
대기 턴 삭제·배포 타이머만으로 작업 중단·종결 시도 재개·구신 비호환 연결 무검증 공존이면 실패다.

## 7. 사용자 결정 — 초기 AI 권고와 상이

초기 권고는 관련 실행 전체 정지였다. 사용자는 서비스 중인 다른 서버를 이용한 순차 재기동을 선택했다.
계획 배출과 호환성 검증으로 그 방향을 반영하며, 남는 위험은 노드별 숨은 작업·형식 불일치·잔여 용량 부족이다.
구체적인 노드 제어·검수 필드·작업 인계·배포 시험은 integration P2/P3에서 명세한다. 현재 소스의 구현 완료를 뜻하지 않는다.

## 2026-11-10 검증 근거 보충

2026-11-10 [현재 소스 대조](../research/integration-auth-prerequisite-verification.md)에 따라 ARCH-028.deployment_contract.p2_operations에 보호된 운영 제어·기동 식별·배정/배출 완료·재검수·복구 책임을 상세화했다. 이 결정 안의 구체화이며 신규 운영 인프라 선택은 아니다. 기존 graceful shutdown을 실제 배출 제어 구현/검증 완료로 해석하지 않는다.

후속으로 같은 연구의 제품 부팅 실험에서 키/암호문 부분 교체 실패와 올바른 새 짝·이전 복구 짝의 재기동 및 기존 합성 행/changelog 보존을 확인했다. 두 노드 배출·부하·실제 배포 세대 전환과 외부 키 보관소 복구는 구현 후 실환경 시험이며 이번 단일 임시 노드 실증으로 대체하지 않는다.
