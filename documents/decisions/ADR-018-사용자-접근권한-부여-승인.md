# ADR-018 — 사용자 접근 권한은 승인 후 부여하고 제거는 승인 없이 처리한다

## 1. 맥락

REQ-609의 대상별 사용자 ID는 대상 시스템 권한으로 접근하는 신원이다.
관리자의 직접 변경과 사후 이력만으로는 오인 매핑이나 사칭을 예방하지 못한다.
사용자는 대상 매핑과 사용자 그룹 추가를 요청 상태로 등록하고 별도 승인 메뉴에서 승인한 뒤 활성화하도록 결정했다.

## 2. 대안

- A — 추가는 승인, 제거는 무승인(선택): 권한 확대를 통제하면서 회수는 지연하지 않는다. 승인 처리 부담이 생긴다.
- B — 추가·제거 모두 직접 처리: 운영은 빠르지만 오인 부여를 사전에 막지 못한다.
- C — 추가·제거 모두 승인: 절차가 대칭적이지만 위험한 권한의 회수까지 기다려야 한다.

## 3. 결정

사용자별 데이터소스·대상 시스템/사용자 ID 매핑과 사용자 그룹 추가는 요청 상태에서 권한이 없다.
별도 사용자 접근 권한 승인 메뉴에서 승인한 내용만 활성화한다. 제거에는 별도 승인을 요구하지 않는다.
제품 규칙의 정본은 REQ-609이며 그룹 판정과 Portal 이용 등록은 REQ-103·616에서 연결한다.

## 4. 근거와 포기한 것

새로운 신원·권한의 부여와 권한 축소를 구분한다. 기존 그룹 직접 추가의 편의는 포기한다.
승인된 대상 매핑은 그룹·행 스코프·대상 시스템 자체 권한을 대신하지 않는다.
변경 ID를 직접 덮어쓰거나 제거한 권한을 복원해 승인을 우회해서는 안 된다.

## 5. 되돌리기

승인 상태·권한 집합·감사·별도 메뉴와 실행 계약을 함께 바꿔야 하므로 구현 후 비용이 높다.
승인 대기가 운영을 막으면 승인 담당·처리 방식을 재검토하되 사칭 위험을 수용하지 않고 승인을 조용히 제거하지 않는다.

## 6. 영향·후속

REQ-103·605·609·616, ARCH-050, PRN-06, AUTHZ-001, PRC-13, FEAT-038, SCR-037.
자기 승인과 이미 판정한 턴의 권한 회수 적용은 OQ-019·018에서 별도로 결정한다.
기존 REQ-108의 판정 유지 결정을 이 기록만으로 변경하지 않는다. API·테이블·화면 상세는 후속 설계 범위다.
