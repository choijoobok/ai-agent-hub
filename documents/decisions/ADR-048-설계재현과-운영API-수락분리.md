## 1. 맥락

사용자는 CON-033·CON-034의 개발 CLI 사용과 운영 API 실증의 구독 확보 후 실행을 이미 선택했다. 이번 요청은 그 순서를 유지하면서 integration G3(설계 베이스라인 승인)와 system G3를 먼저 진행할 수 있는지 검토하는 것이다. API 실증 유예를 다시 결정하는 질문이 아니다.

조정 검토 당시 [ADR-001 §8.1(2)](ADR-001-오케스트레이션-프레임워크.md)은 실모델 스트리밍·청크 경계 중단과 중단 뒤 토큰 기록 완전성을 함께 요구했다. [ASM-003](ASSUMPTIONS.md)의 미확인 때문에 integration 전체 G3와 그 공통 계약을 소비하는 system G3가 대기했다. 실제 PostgreSQL·LangGraph4j·CLI 재현과 [두 CLI 계량 검증](../research/model-provider-usage-verification.md)은 공급자 최종 계량의 부재/오귀속을 확인했으므로 기존 기준을 통과했다고 할 수 없다.

REQ-107·109·116, NFR-010, FEAT-210·211·304의 기록·중단·계량 요구는 유지한다. 변경 대상은 **설계 선택의 재현 판정과 공급 경로의 운영 수락을 어느 게이트에서 확인하는가**다. 일반 G3의 미해결 설계 가정0, 작업흐름 소유권, 일반 G4(슬라이스 구현 완료)의 모든 해당 시험 통과 규칙은 바꾸지 않는다.

|---|---|---|---|

## 3. 결정 — 2026-11-10 사용자 A 승인

**사용자가 A를 승인했다. 아래 기준을 반영하고 실제 재현 결과를 다시 대조해 ASM-003을 판정한 다음, integration G3 → system G3 순서로 각각 청구한다.** 이 ADR의 승인만으로 ASM 확인이나 어느 G3도 자동 승인하지 않는다. 한 턴에 넘는 게이트는 하나다.

### 3.1 ASM-003의 설계 확인 범위

ADR-001 §8.1의 1·3·4번은 유지하고, **2번의 토큰 완전성 판정 범위만** 다음으로 조정한다.

> 실제 모델의 정상/중단 스트림에서 청크 경계 이후 Hub 출력 반영을 차단하고, 수신한 출력·사용량 원천 관측을 유실 없이 보존한다. 정상 완료와 로컬 중단의 상태·감사·그래프 반환 상태를 구별한다. 원천이 최종 사용량을 제공하지 않거나 귀속이 불명확하면 UNKNOWN으로 보존하고 0·이전 호출 누적량으로 확정하지 않는다. 공급자 원격 종료·호출별 최종량·재시도 통제의 지원 여부와 실제 제품 원장/쿼터 원자 반영은 각각 운영 API 수락과 소유 구현 시험에서 판정한다.

이 조정은 **기존 기준의 부분 변경**이며 기존 미통과를 통과로 소급하지 않는다. [실환경 재현](../research/orchestration-runtime-verification.md)의 입력·기대·실제값으로 네 항목을 재대조한다. 이전 시험 코드의 정상 완료를 취소로 기록하는 오류를 수정하고 DB 상태·감사·checkpoint 반환값 직접 검사와 정상→취소 오표기 변이 탐지를 선행한다. 테스트 더블만으로 실모델 재현을 대신하지 않는다.

승인 후 ADR-001에는 §8.1(2)의 판정 범위만 이 ADR로 부분 대체됐음을 연결하고, 프레임워크 채택·자체 saver·훅/Hub 소유 결정과 과거 부분 실패 기록은 보존한다. ASSUMPTIONS의 확인 날짜/근거는 기준 승인과 별도의 재판정으로 기록한다.

### 3.2 후속 운영 API 검증의 소유·기한·종결

시험 내용의 정본은 [ARCH-032.operational_usage_acceptance](../spec/20-architecture/016-provider-connections.yaml), integration FEAT-304·UC-048·TC-3043~3048이다. agent FEAT-211·TC-2112~2119가 실제 기록/쿼터 소비를 검증한다. 중복된 별도 시험 목록이나 새 관리 화면을 만들지 않는다.

| 경계 | 승인된 판정 경계 |
|---|---|
| integration G3 | 공급자 관측/오류/취소/UNKNOWN·재시도 통제·원 호출 귀속 계약, 후속 시험 입력/기대, 최소 생산/소비 의존을 동결한다. 운영 API 실행 통과를 주장하지 않는다 |
| system G3 | integration 공통 계약 동결 후 CR-033 인증·권한/배치와 CR-034 통지 공개 계약, 변경 화면을 검수한다. 모델 계량 시험으로 system 소유 설계 검토를 대신하지 않는다 |
| 운영 API 구독·유효 시험 연결 확보 직후 | API 실증을 우선 실행한다. 공급자·모델·SDK·전송 방식·버전별로 미실행/지원/미지원/미확인을 구별하고 실제 요청 참조와 재현 근거를 남긴다. 하나의 조합 통과로 전체를 지원 처리하지 않는다 |
| 해당 모델 통합 슬라이스 G4 완료 및 해당 기능 최초 활성화 전 | **둘 중 먼저 오는 시점 전**에 필요한 운영 능력과 모든 해당 TC를 실제 제품 경로로 판정한다. 미실행이면 해당 모델 통합 완료를 보류한다. 대역 단위시험만으로 G4를 닫지 않는다 |
| P5 통합·성능/정확 쿼터 인수, P6 운영 인수 | 차수 필수 범위의 실제 호출·지연/정정·중복·동시성·원장/쿼터 통합을 실행한 근거가 있어야 한다. API 유예를 전체 인수의 포괄 예외로 쓰지 않는다 |

운영 API가 중단 최종량을 제공하지 않는다면 **그 능력은 UNSUPPORTED(미지원)**로 판정하고 UNKNOWN 기록·필요 기능 차단을 시험한다. 존재하지 않는 숫자를 무한히 기다리는 조건을 만들지 않는다. 이때 지원하는 경로의 정상 동작과 미지원 거부 시험은 통과할 수 있지만, 해당 차수의 필수 요구를 충족하지 못한다면 해당 G4/G5를 완료 처리하지 않는다. 다른 지원 조합을 검증하거나 정식 CR로 범위/계약을 다시 결정한다. 원격 중단과 정확한 계량은 서로 독립된 능력이다.

### 3.3 개발 개방 범위

공통 계약과 슬라이스 의존의 정본은 [단계별 개발 계획](../spec/31-features/001-delivery-strategy.yaml)과 [integration 공개 계약](../spec/50-api/017-integration-common-contracts.yaml)이다.

- integration 전체 FEAT-301~305 G3가 승인되면 소유 순서에 맞춰 SLICE-307(인증 공통), 설정·접근·외부 사건 기반을 구현할 수 있다. 다른 소유의 미승인 구현은 열리지 않는다.
- system G3와 해당 화면 검수 뒤 SLICE-307 → SLICE-520(인증·권한/배치) → SLICE-521(역할 기반 외부 사건 알림) 순으로 진행한다. 이 경로에 모델 호출은 필요하지 않다.
- agent 최소 호출·사용량 생산 SLICE-230은 **agent 전체 G3**와 기존 선행 슬라이스를 요구한다. integration 모델 SLICE-304는 이 실제 생산자를 소비하며 대역을 제품 통합 완료로 취급하지 않는다.
- admin 선행19화면은 admin 소유 G3/화면 승인과 실제 생산 의존을 따른다. 이 조정으로 후행 admin·제품 Portal 또는 배제한 감사/이력/품질 목업의 개발을 앞당기지 않는다.

## 4. 근거와 반례 검토

기존 실험은 프레임워크의 훅·실제 PostgreSQL·별도 JVM 재개/교정·Hub 통제 소유를 재현했다. 계량 검증에서는 Codex의 이전 누적 재표시와 Claude의 오류0/부분 자리표시를 발견했다. 따라서 **관측을 보존하는 설계의 가능성**과 **특정 공급 원천이 최종량을 제공하는가**를 분리하는 것이 사실에 맞다. A의 채택에는 시험 코드 오류 수정 후 재검증 근거가 필요하다.

| 실패 가능성 | 대응과 중단 조건 |
|---|---|
| ASM0을 맞추려고 명칭만 바꿔 불확실성을 숨긴다 | 기존 §8.1(2)의 실패와 새 기준을 나란히 남긴다. 기준 승인 후 네 항목별 실제값으로 재판정하고 API 시험은 미실행으로 유지한다 |
| 구독 확보 후가 무기한 유예가 된다 | 연결 확보 직후 우선 실행하고, 해당 조합 최초 활성화/모델 통합 G4 중 먼저 도래하는 시점 및 P5/P6를 완료 제한으로 둔다 |
| CLI 취소/숫자 존재를 원격 종료·정산 완료로 승격한다 | 원천 범위·관측 단계·정확 귀속·선택 유효성을 검사한다. 최종량 부재/오귀속은 UNKNOWN이며 업무 실행·정확 쿼터 등 필요한 경로는 비활성화한다 |
| integration G3로 agent/Portal 구현까지 연다 | 기존 소유 게이트와 SLICE-230/304 의존을 그대로 검사한다. 새로운 부분 G3나 작업흐름을 암묵적으로 만들지 않는다 |
| API 실증 결과가 동결 계약과 충돌한다 | 영향을 받는 모델/계량 슬라이스를 멈추고 CR로 계약·DB·시험 변경 및 재승인 범위를 정한다. 이미 통과한 독립 인증 시험까지 자동 무효화하지 않는다 |

## 5. 포기한 것과 되돌리기

A는 모든 운영 공급자 불확실성을 설계 승인 전에 제거하는 방식을 포기한다. API 구독 지연 중에도 공통 기반 개발은 진행할 수 있으나 실제 모델 통합 완료·정확 쿼터·운영 인수 일정은 보장할 수 없다. 해당 API의 실제 형태에 따라 FEAT-304·FEAT-211·ENT-258~264·TC-3043~3048/2112~2119에 재작업이 생길 수 있다.

승인된 결정을 되돌릴 때는 새 ADR로 이전 기준 복원을 결정한다. G3 동결·구현 후에는 CR로 영향 게이트/슬라이스를 재개방하고 호출·계량·저장 회귀를 수행한다. 되돌리기 비용은 **높음**이다. API가 현재 계약의 원 호출 귀속·필수 통제·필수 사용량 요구를 충족하지 못하거나 고객 일정이 API 선실증을 요구하면 재검토한다.

## 7. 결정 카드와 사용자 질문

1. 공통 설계 검증을 마치면 integration, 이어 system 설계 승인을 별도로 진행한다.
2. 운영 API는 구독/시험 연결 확보 직후 검증하고 해당 모델 통합 완료·최초 활성화 전에 통과해야 한다.
3. 최종 사용량을 제공하지 않는 경로는 미지원/미확인으로 처리하며, 필요한 기능은 열지 않는다.
4. 후속 API 결과로 모델·계량 설계를 다시 고칠 가능성은 감수한다. 되돌리기 비용 높음.

**OQ-038 — 필수, 권장 A:** 이 경계로 설계 재현과 운영 API 수락을 분리할까요? 선택지는 A(권장), B(현행 G3 대기), C(작업흐름 정식 분할)이다. 영향은 integration/agent의 ASM 판정, system 선행 의존, 모델 통합 완료·운영 활성화 일정이다.

역확인: A는 인증·관리 기반 개발을 앞당기지만, 운영 API가 준비되지 않으면 실제 모델 통합 완료는 대기하고 실증 결과에 따라 재작업할 수 있다는 일정 전제로 이해하면 되는가?
