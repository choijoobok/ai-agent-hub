# ADR-041 — Hub 권장 신원 확인과 일회용 난수 토큰

| 항목 | 내용 |
|---|---|
| 일자·상태 | 2026-11-03 · accepted · 사용자가 설명된 흐름과 구조를 Hub의 권장 신원 확인 프로세스로 요구사항에 반영하도록 승인 |
| 등급 | High — 대상 시스템과의 신원 확인·인증 경계를 정하는 결정. 권장 프로세스 채택 승인과 제품 구현/고객사별 공동 오픈 승인은 구분 |
| 범위 | REQ-604·608·609, ARCH-028·050, IF-002·009, FEAT-004·005·205, UC-018·024·044, SCR-004 |

## 1. 맥락

대상 시스템마다 사용자 아이디의 생성·변환·전달 위치·검증 방식이 다르다. 업무 API의 신원 필요 스위치 하나로 이 계약을 표현하면 누락과 우회가 생긴다. 식별자를 가리는 것만으로 변조·탈취한 값의 재사용을 막을 수 없다.

사용자는 Hub가 난수 토큰을 발급해 DB에 신원 연결을 보관하고, 인증된 대상 시스템이 서버 간 검증·일회 소비로 대상 사용자 아이디를 확인하는 흐름을 권장 프로세스로 채택했다. 대상은 Hub DB를 직접 조회하지 않는다.

## 2. 고려한 대안

- A — 기존 사용자 식별자/암호문 직접 전달: 고객사 기존 계약과 연결하기 쉽지만 식별 정보 보호와 호출자 증명·변조/재사용 방지를 별도로 검수해야 한다. 기존 검수 계약은 유지할 수 있으나 권장 토큰 경로의 장애 폴백으로 사용하지 않는다.
- B — 서명된 자체 검증 토큰 또는 표준 위임 토큰: 대상의 온라인 Hub 조회를 줄일 수 있지만 대상의 검증 지원·키 배포가 필요하며 현재 회수와 한 번만 소비하는 상태가 자동 보장되지 않는다. 고객사별 다른 검수 계약의 대안으로 남긴다.
- C — 불투명 난수 토큰과 인증된 Hub 검증·일회 소비 API(선택): 아이디를 요청에 직접 넣지 않고 현재 매핑·회수·대상/요청 결합을 한 경계에서 확인할 수 있다. 내부 왕복 호출·DB 상태와 대상/게이트웨이 지원이 필요하다.

## 3. 결정

제품 사실의 정본은 [REQ-609.identity_verification](../spec/10-requirements/012-reference-business.yaml)로 둔다. C를 Hub 권장 프로세스로 제공하고 대상별 공동 검수에 따라 채택한다. API의 신원 필요 컬럼은 제거하며 선택 연결의 명시 신원 계약을 따른다.

## 4. 근거

대상 시스템은 확인된 같은 요청의 사용자로 자체 권한을 검사할 책임을 유지한다. 난수 토큰의 해시·정확 대상/요청·현재 신원 버전·만료·소비 상태를 결합하면 데이터 노출·오인 해석·다중 소비의 검수 기준을 분리할 수 있다. 원 요청의 Hub 호출자 증명과 소비 요청의 대상 인증이 함께 있어야 탈취한 토큰만으로 신원을 사용할 수 없다.

[토큰 인트로스펙션](https://www.rfc-editor.org/rfc/rfc7662.html)은 인증된 서버가 유효성과 신원 정보를 확인하는 참고 표준이다. 일회 소비와 요청 결합은 Hub 추가 계약이며 표준 자체의 보장으로 표현하지 않는다. [인증서에 결합된 토큰](https://www.rfc-editor.org/rfc/rfc8705.html)과 [OAuth 보안 권고](https://www.rfc-editor.org/rfc/rfc9700.html)의 호출자/대상 제한을 참고한다.

## 5. 포기한 것

토큰만으로 대상이 독립 실행하는 단순함과 Hub 검증 장애 중 계속 실행하는 가용성을 포기한다. 단일 DB 소비가 대상의 업무 실행까지 한 트랜잭션으로 만드는 것은 아니므로 응답 유실·결과 불명·중복 실행은 기존 REQ-105·113으로 처리한다. PRN-09의 고객사 기존 시스템 변경 비강제 원칙은 유지한다.

## 6. 되돌리기

구현 전에는 위 요구와 연결 계약·흐름·화면·검수 계획을 함께 바꾼다. 구현 후에는 유효/소비 토큰을 안전하게 배출·만료하고 대상/게이트웨이 검증 계약과 실제 적용 시점을 함께 전환해야 한다. 인증 경계·고객사 연동 재검수 비용이 높으며 요청 대기 증가나 내부 왕복 지원 제약이 요구를 충족하지 못하면 다른 검수 계약을 검토한다. 실패 시 자동으로 이전 방식으로 되돌리지는 않는다.

## 7. 영향과 후속

요구 흐름 UC-044와 검증 인터페이스 IF-009를 연결하고 호출자/요청 변조·동시 소비·회수 경합·응답 유실·비노출을 계획 시험으로 정의한다. 물리 모델·서비스 배치·API 경로/DTO·만료/보존 수치·키 교체·콜백 용량은 후속 상세 설계 및 고객사 공동 검수 대상이다. 제품 소스·DB 적용·작업흐름 단계/게이트 전이는 포함하지 않는다.
