## 1. 맥락

ADR-021은 비밀 설정값을 암호화된 yml로 관리하고 환경별 활성 마스터 키 하나만 외부에 두되 Jasypt를 기본 구현으로 선택했다. 이후 사용자는 Spring Security Crypto의 설정 자동 복호화 미제공, 자체 구현 범위와 예상 규모, Jasypt의 유지보수 상태를 검토한 뒤 Spring Security Crypto와 자체 설정 연동을 명시 선택했다. 제품 규칙의 정본은 [REQ-403](../spec/10-requirements/008-derived.yaml)이며 CON-011·FEAT-302가 연결된다.

Jasypt 핵심 저장소는 2025-11-07 보관 처리됐고 더 이상 유지보수하지 않는다고 명시한다. 별도 프로젝트인 jasypt-spring-boot에는 4.0.4 릴리스가 있으므로 두 프로젝트의 유지보수 상태를 혼동하지 않는다. [핵심 저장소](https://github.com/jasypt/jasypt), [Spring Boot 연동 릴리스](https://github.com/ulisesbocchio/jasypt-spring-boot/releases)

## 2. 고려한 대안

### 대안 A — Spring Security Crypto + 공통 설정 해석 어댑터 (채택)

Spring 공식 암복호화 구현을 재사용하고 암호문 형식·외부 키 읽기·설정 복호화·초기화 순서·운영 도구·실패 보호를 공통 구현한다. 별도 설정 서버 없이 기존 배포 흐름을 유지하고 Boot가 관리하는 의존성을 활용한다. 대신 완성된 설정 복호화 starter의 편의성을 포기하고 자체 연동의 검증·유지보수 책임을 맡는다. 라이브러리의 암호 알고리즘을 직접 다시 구현하지 않는다. [Crypto 공식 문서](https://docs.spring.io/spring-security/reference/features/integrations/cryptography.html)

### 대안 B — Jasypt + jasypt-spring-boot 유지

암호문 감지와 Spring 설정값 해석을 제공하므로 초기 연동 개발량이 적다. 그러나 핵심 라이브러리의 유지보수 중단과 Boot 4 지원 불확실성이 장기 유지보수에 부담이 된다. 사용자는 이를 비교한 뒤 대안 A를 선택했다. 라이브러리 버전 4.0.4가 Spring Boot 4의 호환성 보장을 뜻하지 않는다. [Boot 4 지원 요청](https://github.com/ulisesbocchio/jasypt-spring-boot/issues/429)

### 대안 C — Bouncy Castle 기반 자체 설정 해석

폭넓은 암호 알고리즘·인증서·보안 프로토콜을 제공하지만 YAML 설정 자동 복호화는 별도 연동이 필요하다. 현재 설정 비밀 보호 목적에는 특수 알고리즘이나 인증서 기능을 새로 요구하지 않으므로 기본 구현으로 선택하지 않는다. [공식 Java 문서](https://www.bouncycastle.org/documentation/documentation-java/)

### 대안 D — 비밀별 외부 주입 또는 별도 설정·비밀 서버

비밀별 권한·교체 체계를 활용할 수 있으나 운영 항목과 외부 인프라가 늘어난다. ADR-021에서 사용자가 제외한 기본 운영 방식이며 이번 변경으로 다시 채택하지 않는다.

## 3. 결정

2026-10-02 사용자 결정에 따라 비밀 설정값의 암복호화는 Spring Security Crypto를 사용하고, YAML 설정 자동 복호화 연동과 암호문 생성·검증·재암호화 도구는 직접 공통 구현한다. ADR-021을 대체하되 암호화 yml 관리와 환경별 외부 활성 마스터 키 하나의 운영 방식은 유지한다.

암호문 표시는 `ENC(...)` 규약을 유지하되 Jasypt 암호문과의 호환성을 뜻하지 않는다. payload 형식·버전·암호 파라미터·키 재료는 P2에서 정한다. yml 파일은 암호문으로 유지하고 서버가 설정을 사용할 때 메모리에서 복호화한 값을 전달한다. 제품 카드 전체 확정이나 소유 작업흐름의 G3 승인을 대신하지 않는다.

## 4. 근거

현재 소스는 Spring Boot 4.1.1과 JDK 25를 사용하고 domain 모듈에 spring-security-crypto 의존성이 이미 있다. 설정 보호를 구현할 공통 계층은 자체 암호화 의존성을 직접 선언해야 하며 업무 모듈의 전이 의존성에 기대지 않는다. 기존 비밀번호 해싱 구현은 이번 결정의 수정 대상이 아니다.

Spring Boot는 설정값 암호화의 내장 기능 대신 초기 Environment를 조정하는 확장 지점을 제공한다. 이를 활용하되 환경별 파일·프로파일·환경 변수의 우선순위와 기존 바인딩 동작을 보존해야 한다. 라이브러리 선택만으로 조기 DB·Liquibase·로그 초기화까지 성공했다고 간주하지 않는다. [설정 암호화 확장 지점](https://docs.spring.io/spring-boot/reference/features/external-config.html#features.external-config.encrypting)

## 5. 포기한 것과 위험

- Jasypt 연동 starter와 기존 도구를 그대로 사용하는 편의성을 포기한다. 자체 암호문 형식·설정 어댑터·명령행 도구와 회귀 테스트의 유지보수를 맡는다.
- 사용자 검토 시 본체·운영 도구 7~9개 클래스/500~850줄, 테스트 포함 12~16개 클래스/1,100~1,850줄로 초기 추산했다. 일정·수용 기준이나 구현 상한이 아니며 P2/P3 상세화 뒤 다시 산정한다.
- 초기화 순서나 설정 우선순위를 잘못 다루면 복호화 전 DB 연결 시도, 다른 프로파일의 값 선택, 미사용 연동 때문에 기동 실패 등의 증상이 생긴다. 비밀을 포함한 바인딩·접속 예외와 도구 출력도 별도 누출 검증 대상이다.
- 마스터 키 유출·유실의 영향과 비밀별 외부 저장소 접근 제어·자동 교체를 기본으로 제공하지 않는 제약은 계속 존재한다. 서버가 접속하려면 평문을 사용하므로 실행 중 메모리나 호스트 침해까지 암호화 yml만으로 막을 수 없다.
- YAML 파일 전체 자동 편집, 비밀·키 관리 화면, 무중단 키 교체, Jasypt 암호문 호환은 이번 기본 구현에 포함하지 않는다. 필요하면 별도 요구·영향을 검토한다.

## 6. 되돌리기

- 가능 여부와 비용: Medium. 아직 설정 복호화 구현과 운영 암호문이 없으므로 현재 소스 이행 비용은 없지만 여러 문서·계약·운영 절차를 맞춰야 한다.
- 방법: 새 ADR로 대안을 결정하고 REQ-403·CON-011·FEAT-302·배포 안내·계약 시험을 바꾼다. 운영 암호문 도입 뒤에는 안전한 재암호화와 키/설정의 짝 검증·복구도 수행한다. 비밀을 소스·로그·평문 중간 파일에 출력하며 이행하지 않는다.
- 재검토 신호: 공통 어댑터가 Boot 업데이트에 반복적으로 깨지거나 설정 우선순위·비노출 경계를 검증하지 못하는 경우, 고객사가 비밀별 접근 제어·자동 교체를 필수로 요구하는 경우다. 사용자 결정 없이 다른 라이브러리로 대체하지 않는다.

## 7. 영향과 후속

REQ-403의 구현 방침과 CON-011을 갱신하고 REQ-402·602·603·608, ARCH-030, FEAT-302, 배포 안내·공통 가이드가 공통 요구를 참조하도록 맞춘다. 관리 대상 아홉 범주, 화면 비노출, 고객사·환경별 키 분리, 필수 실패 차단과 선택 연동 예외는 유지한다. REQ-604 전체 카드의 순차 확정 대기도 유지한다.

P2는 암호문·키·암호 파라미터, 공통 계층과 조기 설정 해석 경로, 운영 도구·교체/복구를 설계하고 Boot 4/JDK 25의 설정·DB·Liquibase·로그 경로를 검증한다. P3는 정상·오키·키 누락·변조·미지원 형식·프로파일 우선순위·선택 연동·바인딩/로그/도구 누출·교체 실패 시험을 명세한다. 실제 소스 구현은 integration 작업흐름의 G3 승인 이후다.

## 2026-11-10 검증 근거 보충

[실험 조건·재현 코드와 한계](../research/integration-auth-prerequisite-verification.md)에 실제 제품 runtimeClasspath/처리 리소스와 격리 PostgreSQL16의 부팅·설정 우선순위·키 교체/복구13건, 엄격 형식16검사를 추가했다. Liquibase6 changeset·JPA·실제 비밀번호 연결을 확인했고, 오류 키/상위 설정은 DB pool 시작 전에 차단했다. Boot 원천 mapper의 예외 삼킴/환경변수 캐시 우회 문제를 발견해 불투명 값의 선택 후 소비 변환으로 보완했다. ARCH-032.boot_design에 범위와 제품 이행 조건을 반영했다. 제품 어댑터·운영 도구 구현, 모든 설정 원천·고객 외부 키 저장소/배포 복구의 실증은 아니다. 라이브러리 채택 결정·기술 실험과 소유 게이트 승인을 구분한다.
