## 1. 맥락

[`ADR-001`](ADR-001-오케스트레이션-프레임워크.md) 이 그래프 런타임을 들이면서 **가장 큰 쟁점**이 함께 들어왔다 — 런타임의
체크포인트와 우리 턴 이력이 **이중 상태 원천**이 된다. 어느 쪽이 정본인지 정하지 않으면
감사(PRN-07)와 재개(REQ-013)가 어긋난다. 프레임워크 조사가 이것을 *B·C안의 핵심 검증
항목* 으로 지목하고 결정을 PoC 로 넘겼다.

## 2. 고려한 대안

### 대안 A — 우리 테이블을 `CheckpointSaver` 구현체로 만든다 — **채택**
- 내용: `ai_agent_checkpoint` 가 곧 런타임의 저장소다. **별도 저장소는 존재하지 않는다.**
- 장점: 원천이 물리적으로 하나가 되어 *어느 쪽이 정본인가* 라는 질문 자체가 사라진다.
  AI 전용 DB 가 PostgreSQL 고정(CON-001)이라 추가 구성요소가 없다.
- 단점: 런타임의 저장소 인터페이스에 우리 스키마가 묶인다. 그리고 **시간여행이 저장소에
  없는 id 로 갱신을 걸어오므로** upsert 가 필요하다(`03-glossary/_index.yaml` TRM-072) — PoC 에서
  드러난 것이며 문서만 읽고는 알 수 없었다.

### 대안 B — 런타임 기본 저장소를 쓰고 우리 이력과 동기화한다
- 왜 선택하지 않았나: **동기화는 갈릴 수 있고, 갈리면 감사가 무너진다.** 재개 상태와 감사
  이력이 서로 다른 말을 하는 순간 *무슨 일이 있었나* 에 답할 수 없다. 게다가 폐쇄망에
  운영 구성요소가 하나 늘어난다.

### 대안 C — 체크포인트를 감사 이력으로도 쓴다 (표 하나로 합친다)
- 왜 선택하지 않았나: **수명과 수정 규칙이 반대다.** 체크포인트는 갱신되고 턴 종결 시
  정리되며, 감사 이력은 append-only 이고 보관 기간을 따른다(REQ-107·REQ-109).
  하나로 합치면 둘 중 하나의 규칙을 포기해야 한다 — `03-glossary/_index.yaml` confusions 의
  *체크포인트 ≠ 감사 이력* 이 이 결정의 결과다.

## 3. 결정

**`ai_agent_checkpoint` 를 런타임의 `CheckpointSaver` 구현체로 만든다.** 표는 둘로 두되
(체크포인트 · 감사 이력) **저장소는 하나이며, 두 표의 분업은 답하는 질문이 다르기 때문이다.**

## 4. 근거

**PoC 에서 실행으로 확인했다**(§2.1) — 우리 테이블에 쓰는 saver 로 S1~S5 가 통과하고 이력이
A안과 동일했다. 프레임워크 조사가 남긴 확인 항목 2 는 그것으로 해소됐다.

**정리와 재개가 서로를 깨지 않는 것도 확인됐다**: 버려진 체크포인트를 지워도 시간여행
재개가 동작한다 — `updateState` 가 만든 분기 체크포인트는 상태 전체를 담아 조상 체인을
필요로 하지 않는다. **REQ-109 의 조기 정리가 재개를 깨지 않음이 실측으로 확인됐다.**

## 5. 포기한 것

- **런타임이 제공하는 기성 저장소를 쓰지 않는다** — 그쪽의 개선·최적화를 받지 못하고,
  스키마 변경이 오면 우리가 따라간다.
- **체크포인트를 감사 근거로 쓰는 길을 닫았다.** *무엇을 하다가 무엇으로 바꿨는가* 는
  감사 이력이 답해야 하며, 그래서 이력에 **회차를 함께 남기는 부담**을 진다.

## 6. 되돌리기

- 되돌릴 수 있는가: **가능하지만 감사 설계가 함께 흔들린다.**
- 예상 비용: saver 구현 교체 + 재개 상태 마이그레이션 + 이력과의 대조 경로 신설.
- 되돌려야 한다는 신호: ① 우리 테이블 구현이 런타임의 동시성 가정을 만족하지 못한다
  ② 재개 상태의 크기가 이 DB 에서 감당되지 않는다(**PostgreSQL 실환경에서 상태 컬럼
  크기·인덱스·동시 갱신을 아직 보지 않았다** — H2 로 대역했다).
