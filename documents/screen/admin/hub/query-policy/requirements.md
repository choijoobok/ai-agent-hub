# 요건 정의서 — 행 스코프·필터·조회 제약

## 개요

- **무엇을 하는 화면인가**: 카탈로그별 조회 정책 묶음을 등록하고 스코프·기본 필터·필수 조건을 함께 관리한다.
- **프로세스상 위치**: 카탈로그 선택 → 세 탭 조건 설정 → 전체 저장·이력 → agent의 현재 정책 검증·조회·조건 안내.
- **이 데이터를 누가 쓰나**: 관리자는 정책을 설정하고 서버는 실행 전에 검증하며 LLM(대규모 언어 모델)은 일반 파라미터 확보·결과 설명을 담당한다.
- **바꾸면 어디가 흔들리나**: REQ-611(보안·조회 정책)과 REQ-103(데이터 접근 통제). 원천 카탈로그 내용·접근 권한과 별도 소유다.

## 1. 화면 구성

조회조건 → 규칙 목록 → 상하 스플리터 → 스코프 설정·기본 필터 설정·필수 조건 제약의 세 탭이다.
상단 종류·조건 템플릿·해제 허용·검수 상태를 제거한다. 규칙 설명은 업무 설명이며 실행할 SQL 조건식은 하단 스코프에서 관리한다.
스코프 탭은 좌우로 나눈다. 왼쪽은 복수 스코프 목록, 오른쪽 위는 선택 스코프의 조건식 textarea, 아래는 파라미터 설명 그리드다.
스코프와 기본 필터는 AND(모두 만족), 필수 조건 제약은 OR(하나 이상 충족)로 적용한다. 같은 부모·행·탭의 입력을 보존하고 다른 부모 구성과 섞지 않는다.
상단 추가는 카탈로그 단일 조회 팝업을 먼저 연다. 선택 완료 전에는 빈 신규 행을 만들지 않는다. 식별자·명칭·데이터소스는 읽기 전용이다.
초기 화면은 검토용 한 행 선택 예시다. 실제 조회 후 자동 선택은 하지 않는다.
상태별 버튼: 허용 목록
행 추가 탭: 규칙 목록·스코프 설정 / 목록·기본 필터 설정·필수 조건 제약
목록 연동: 규칙 식별자

## 3. 조회 — 테이블과 범위

### 3-1. 사용 테이블 · 결합

REQ-611의 현재 조회 정책 원천과 카탈로그의 안정 참조를 읽는다. 카탈로그 내용에 정책 사본을 저장하지 않는다. ENT-009의 논리 경계와 §10 후속을 따른다.

### 3-2. 고정 조건 · 기본 정렬

현재 메뉴·대상 조회 권한 안에서 표시한다. 이름이 같아도 안정 식별자로 구분한다. 실제 페이징·정렬·동시성은 후속 상세 설계한다.

### 편집 가능 판단

현재 변경 권한과 정상 편집 문맥을 모두 만족해야 한다. 참조·예약 변수·서버 식별자는 읽기 전용이다. 이력은 원 화면의 세 탭을 읽기 전용으로 상속한다.

### 값 변경 후 연쇄 · 재계산

조건식 변경은 파라미터 추출을 낡음으로 표시한다. 재추출하면 같은 이름의 일반 설명을 보존하고 사라진 변수는 명세에서 제거한다. 현재 조건식과 일치하기 전에는 저장할 수 없다.
컬럼 변경은 자료형·허용 유형을 같은 현재 카탈로그에서 다시 구하고, 범위 불가 타입에는 범위를 남기지 않는다. 동일 값 또는 조인으로 변경하면 최대 차이는 지운다. 조인 전환 시 현재 단일 컬럼을 후보로 보여주되 팝업에서 선택을 확정한다. 다중 조인에서 단일 유형으로 전환하면 임의 첫 컬럼을 고르지 않고 단일 컬럼을 다시 선택한다. 취소·읽기 전용·부모 변경은 잘못된 문맥의 선택을 반영하지 않는다.

## 6. 규칙 — 저장 · 실행

### 6-1. 조건·파라미터

- 스코프는 0..N개이며 하나의 SQL 조건식 조각과 추출 파라미터 명세를 갖는다. 조건식 내부의 IN/EXISTS를 허용하되 다중 문장·쓰기·동적 식별자/SQL 치환은 허용하지 않는다. 대상 DBMS(데이터베이스 관리 시스템) 파서로 대상·별칭·참조·행 수 보존을 검증한다.
- 예약 변수 안내를 textarea 옆에 항상 표시한다: `#{userId}`는 현재 세션 사용자의 대상 데이터소스 사용자 식별자(서버 신원 매핑), `#{langCd}`는 현재 세션 언어 코드다. 서버 공급값을 LLM·사용자 인자로 덮지 않는다. 필요한 신원 매핑/세션 값이 없으면 임의 값·NULL·조건 생략으로 통과하지 않는다.
- 일반 `#{변수명}`은 업무 의미와 확보 출처를 설명하고 LLM이 대화/허용된 조회 결과로 값을 마련한다. 불명확하면 질문한다. 권한 신원은 일반 변수로 대체할 수 없다. 실제 값은 형식·자료형 검증 후 바인딩한다.
- 주석·문자열 안의 토큰은 파라미터가 아니다. 같은 이름은 스코프 안에서 하나로 합치고 서로 다른 스코프의 같은 이름을 자동 공유하지 않는다. 빈 조건식·누락 설명·추출 불일치·미지원 문법은 저장 오류다.

### 6-2. 기본 필터와 필수 조건

- 기본 필터는 등록한 컬럼·값과 일치하는 행만 조회한다. 예: deleted_yn=N이면 N만 조회하고 Y·NULL은 제외한다. 복수 기본 필터는 AND로 적용하며 문자열 선행 0과 자료형을 보존한다. 공란을 SQL NULL로 바꾸지 않는다.
- 필수 조건 제약은 사용 중이고 유효하게 해제되지 않은 항목 중 하나 이상 충족하면 통과한다. 주문번호 동일 값 또는 주문일 30일 이하 범위를 등록하면 주문번호만으로 기간 없이 조회할 수 있다. 별도 유일키 대체 예외는 두지 않는다. 각 테이블 참조마다 하나는 충족해야 한다.
- 필수 조건의 동일 값 매칭은 단일 동등 조건을 요구한다. 자료형과 무관하게 유형은 제공하되 실제 타입/DBMS의 동등 비교·바인딩이 불가능하면 실행하지 않는다. LIKE·다중값·NULL·다른 컬럼 조건으로 충족했다고 보지 않는다.
- 범위는 숫자와 날짜만 제공한다. 최소값·최대값을 모두 확보하고 최소≤최대 및 최대−최소≤설정 최대 차이를 실행 전에 검사한다. 날짜 최대 차이 30이면 대상 시간대 기준 날짜 차이 30일 이하는 해당 후보 충족, 31일은 미충족이다. 다른 후보가 충족되면 실행할 수 있고 사용자가 지정한 날짜 조건은 유지한다. 모두 미충족일 때만 보완 질문 또는 실행 거부한다. 누락 경계를 임의로 채우거나 자동 분할 조회하지 않는다.
- 조인은 등록한 컬럼 모두가 실제 조인 조건에 포함되어야 그 한 항목이 충족된다. 컬럼 두 개 중 하나만 조인하면 미충족이다. 검수된 등록 관계로 상대 테이블·대응 컬럼을 확인하며, 사용하는 관계의 복합 키는 선택 여부와 무관하게 전체를 검사한다. 테이블 이름만 등장하거나 유효한 관계 조건 없는 CROSS JOIN·ON 1=1·복합 키 일부·다른 별칭의 조인은 충족 근거가 아니다. INNER·LEFT 같은 종류만으로 제한하지 않으며 LEFT JOIN도 전체 컬럼/관계 조건이 확인되면 충족한다. 정확 참조와 조인 의미를 검증하지 못하면 해당 대안은 통과시키지 않는다. 조인과 동일 값·범위 항목 사이는 기존 OR이므로 다른 항목을 충족하면 이 집합은 통과한다. 접근 권한과 스코프·기본 필터는 별도로 유지한다.
- 상대 기간은 기존 REQ-611.query_constraints.period의 기준 시점·시간대를 따른다. 입력 검증뿐 아니라 실제 각 테이블 참조에 같은 값의 조건이 적용됐는지 최종 SQL과 바인딩에서 재검증한다.

### 6-3. 사용·해제·조회 결과 안내

- 세 탭의 각 조건에 사용 여부와 해제 허용을 독립 설정한다. 사용 OFF는 관리자 적용 중지이며 정의와 이력을 남긴다. 사용 ON·해제 OFF는 임의 제외할 수 없다. 스코프·기본 필터는 모두 적용하고 필수 조건은 OR 평가한다. 해제 ON도 사용자 요청 전에는 평가 대상이다. 해제 후 남은 필수 조건 중 하나는 충족해야 하며 사용/해제 확인 후 남은 항목이 0개면 이 묶음의 제약은 없다. 다른 접근·실행 통제는 유지한다.
- 해제는 종류·대상·조건 식별자/리비전·사용자 요청 근거를 서버가 검증한 해당 조건에만 적용한다. 설명이나 SQL 수정만으로 해제하지 않는다. 현재 자산 접근권·세션 신원·마스킹·전송 정책·행/시간/결과 크기 상한은 그대로 검사한다.
- LLM은 서버의 실제 적용 결과를 근거로 조회 결과와 함께 적용 조건·업무 의미·해제 가능 여부와 실제 해제 조건을 설명한다. 필수 조건에서는 충족한 항목과 미충족 대안을 구분하며 주문번호로 충족한 경우 날짜 조건을 적용 또는 해제했다고 표시하지 않는다. 해제 불가/거부·정책 변경도 안내하고 권한 테이블·세션 신원 원값은 노출하지 않는다. 모델이 쓴 설명 자체를 적용 증거로 삼지 않는다.

### 6-4. 저장·이력

전체 세 탭은 같은 규칙/기대 리비전으로 저장한다. 미열람·실패 응답을 빈 집합이나 삭제로 처리하지 않는다. 사유·소유 전체 구성·불변 이력·명령 결과는 같은 성공 단위다. 검수 상태 컬럼과 수동 검수 단계는 없으며 자동 검증 실패 시 저장/실행을 거부한다.
상속 이력은 당시 세 탭·참조 표시 근거·사유를 읽기 전용으로 보여 준다. 과거 복원은 현재 권한/참조로 새 저장하며 현재 접근권을 과거 값으로 덮지 않는다.

서버가 적용·충족을 증명하지 못한 조건을 LLM의 판단만으로 통과시키지 않는다. 파싱 오류의 재작성은 기존 AUTHZ-030의 제한된 재시도 경로를 따르며, 정책 미충족/검증 불가는 REQ-025에 따라 보완 또는 거부한다. LLM은 파라미터 확보·검증 가능한 SQL 작성·설명을 지원하고 실제 정책 판정은 서버가 한다.

## 7. API

조회 정책 공개 API(응용 프로그램 인터페이스)·물리 모델은 P3 후속이다. 새로운 URL·필드 키를 목업에서 확정하지 않는다. 카탈로그/파라미터 후보는 실제 서버 조회를 대신하는 가상 예시다.

## 8. 시드 · 데이터 전제

제품 소스·메뉴/메시지 시드는 화면·소유 G3(설계 완료 게이트) 승인 뒤 생성한다. 기존 시퀀스 기반 식별자 규칙을 따르며 목업에서 번호를 발급하지 않는다.
