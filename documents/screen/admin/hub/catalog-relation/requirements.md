# 요건 정의서 — 테이블 관계

## 개요

- **무엇을 하는 화면인가**: 데이터소스 안에서 두 카탈로그 테이블을 선택하고 좌우 컬럼을 연결해 관계를 구성한다. 관계는 조인 근거이며 상대 테이블 접근권을 부여하지 않는다.
- **프로세스상 위치**: 데이터소스·카탈로그 등록 → 관계/전체 컬럼 쌍 구성 → 현재 권한·기술 검증·소유 카탈로그 관계 영역 저장/전체 이력 → 검증된 관계만 소비한다.
- **문서 범위**: 2026-11-14 admin G3 승인 범위의 SLICE-011 관리 구현. 실제 SQL·모델·예제 소비와 연결 지식 조회는 FEAT-011.delivery_boundary의 후속이다.

## 1. 화면 구성

조회조건 → 상단 테이블 관계 목록 → 상하 스플리터 → 하단 컬럼 쌍·연결 지식 두 탭. 검수 근거 탭은 제공하지 않는다. 관계 설명에 용도·1측 유일성·양방향 상대 행 누락 가능성·중복/집계 의미를 적고 기술 검증과 기존 근거·검수/변경 이력은 보존한다. LEFT JOIN 등은 질문별로 판단하며 별도 설정 컬럼은 추가하지 않는다. 제목·건수는 왼쪽, 작업 버튼은 그리드 오른쪽이다. 실제 조회 후 자동 선택하지 않고 같은 대상의 탭/입력/선택을 보존한다. 목업 초기 선택·임시 ID는 시연용이다.

### 관계 선택과 초기화

데이터소스 미선택 상태에서는 테이블 선택을 열 수 없다. 팝업은 좌우2그리드와 하단 적용/닫기이며 양쪽 선택은 독립적이다. 한쪽 미선택/후보 조회 실패/권한 없음/다른 소스 후보는 적용하지 않고 기존 입력을 보존한다. 자기조인은 같은 catalogId를 양쪽에 선택하되 역할·방향을 유지한다. 새 관계의 비표시 ownerCatalogId는 적용한 왼쪽 catalogId이며 최초 저장 후 변경하지 않는다. 기존 관계의 소유는 그대로 보존하고 양끝점 중에 남아야 한다.

테이블 변경으로 기존 쌍이 영향을 받으면 팝업에서 현재 관계의 기존 쌍 초기화 동의를 받은 뒤 두 테이블을 함께 반영한다. 취소·실패는 기존 테이블/쌍을 유지한다. 데이터소스 변경 후 재선택 전에는 과거 테이블/쌍을 새 소스로 저장하지 못한다. 다른 관계의 입력/쌍을 지우지 않는다. 저장 후 소스는 고정하고 소스 이전은 별도 신규 관계다.

## 3. 조회 — 원천과 연결 지식

현재 연결 지식 생산자는 미설치다. 탭에는 미연결을 표시하며 아래 합집합 조회는 SLICE-048 후속 계약이다. 관계/컬럼은 현재 소유 구성과 정확 외부 과거 판에서 조회한다.

현재 소유 카탈로그 구성의 관계/전체 쌍과 양끝점 등록 컬럼을 읽는다. 연결 지식의 집합/활성·현재 판 대조는 REQ-301.relationship_metadata.related_knowledge와 REQ-601.asset_mapping_active를 따른다. 각 지식의 활성 직접 카탈로그 집합과 활성 지식–인증예제 링크가 참조하는 예제의 완전한 카탈로그 집합을 합집합으로 만든다. 왼쪽/오른쪽 catalogId가 모두 포함될 때만 그 지식을 한 번 표시한다. 직접+예제 혼합 경로, 서로 다른 예제 경로와 자기조인도 포함한다. 한쪽만 포함된 지식은 제외한다.

관리 역조회는 현재 관리 READ/대상 열람 범위를 검사하며 지식/예제 본문이나 운영 의미 검토를 수집하지 않는다. 불완전/실패한 예제 참조를 빈 정상 집합으로 바꾸거나 관계의 상대 객체/지식 권한을 확대하지 않는다. 실제 예제 소비의 Portal 접근 필터와 실제 호출의 정확 catalogId/revisionId·전체 쌍 검증은 기존 계약을 별도로 적용한다. 조회 실패/제한은 성공0건과 구분한다.

내부 자동 번호와 참조값은 [REQ-601의 자동 식별자 규칙](../../../../spec/10-requirements/011-reference-integration.yaml)을 따른다. 읽기 전용 번호는 입력하지 않는다. 신규 행에는 저장 전 번호가 없고 저장 성공 후 표시된다. 대상 선택은 이름으로 하며 저장되는 참조는 같은 숫자 식별자다. 업무 코드·설정 키·순번·리비전과 구분한다.

## 6. 규칙 — 저장 · 실행

### 6-1. 검증

- REQ-301.relationship_metadata.workspace를 따른다. 이 화면의 신규/변경 관계는 선택한 데이터소스 안의 두 등록 카탈로그만 연결한다. 같은 DB/스키마로 추가 제한하지 않고 연결의 실제 지원 범위·전체 물리 식별을 검사한다. 다중 데이터소스 질의의 별도 조회/결합 계약 자체를 금지하거나 단일 SQL 권한을 확대하지 않는다.
- 순서는 현행 DataGrid가 행 드래그 정렬을 제공하지 않아 number 타입/number 에디터로 표시한다. 양의 정수/관계 내 중복 없음·ASC를 검증하며 그리드 No와 구분한다. 향후 행 드래그가 공통으로 구현되면 같은 순서값을 갱신하는 방식으로 표시/조작만 바꾼다.
- 반쪽·중복·정확 참조/타입 불일치·불완전 복합 키를 완전한 관계로 저장하지 않는다. 소유·양끝점 현재 READ/SAVE 및 기대 리비전 검사를 서버에서 다시 한다. 검수/유일성·누락/중복·집계 근거는 관계 설명/기존 소유 근거와 기술 검증으로 유지한다. 검수 근거 탭 삭제가 검증 면제나 원천 DDL 변경을 뜻하지 않는다.
- 변경되지 않은 기존 근거/이력은 미조회/탭 삭제를 이유로 지우지 않는다. 끝점/쌍 변경으로 기존 검수 근거가 낡으면 검수 상태를 재확인 대상으로 내리고 이전 근거를 새 관계의 유효 근거로 재사용하지 않는다. 별도 승인/전결/관계 리비전을 만들지 않는다.
- API-024의 RELATIONSHIPS 영역과 같은 소유 현재값·전체 HIST·변경자/시각/사유를 원자 반영한다. 다른 컬럼/정책/인덱스/미저장 입력을 함께 저장하거나 누락을 삭제로 추정하지 않는다. 실패·충돌·결과 불명은 입력/원 명령을 보존한다.
- 연결 지식은 읽기 전용 역조회다. 직접/예제 경유 활성 카탈로그 합집합에 두 끝점이 모두 있을 때만 보이며 그 조회로 예제/지식/상대 객체의 권한을 부여하지 않는다.

- 매칭 누락과 질문별 JOIN 판단은 REQ-301.relationship_metadata.matching_semantics가 정본이다. 관계 설명에서 양방향 상대 행 부재 가능성과 확인 근거를 보존한다. LEFT JOIN의 기준은 SQL 왼쪽이며 화면 왼쪽 역할이나 N:1만으로 고정하지 않는다. 상대 조건의 ON/WHERE 배치도 요청한 포함 범위와 현재 행/신원 정책을 충족해야 한다.
- 지식 검색 후 프롬프트 소비는 REQ-301.relationship_metadata.consumption_scope·prompt_guide와 50-api FEAT-011.relation_read_contract를 따른다. 관계 화면의 연결 지식 역조회와 실제 검색 결과의 최종 선택 카탈로그 집합은 별개다. 양쪽 정확 판·전체 조인 컬럼이 최종 허용 집합에 포함되고 현재 검수/사용·권한이 유효할 때만 테이블 관계 가이드로 제공하며 최종 집합 축소 시 재필터한다. 정상 0건·실패/불완전을 구분한다. 이 화면에서 실제 LLM 호출을 실행하지 않는다.

- 검수 상태 입력은 관리자의 검수 의사이며 서버 완료 판정을 대체하지 않는다. 신규 수동 관계는 논리 작성 원천으로 기록하고 관계 설명의 용도·1측 유일성·누락/중복/집계 설명을 논리 검수 근거로 연결한다. VERIFIED 요청은 비공백 설명·현재 정확 참조/전체 쌍·검증 가능한 기술 조건을 확인한 경우만 수락하고 실제 검수자/시각은 서버가 기록한다. 원천에서 확인한 물리 FK/기술 사실과 관리자의 업무상 설명은 구분해 보존한다. 근거 부족/검증 불가는 UNKNOWN이며 UI 선택만으로 VERIFIED로 저장하지 않는다.

### 6-2. 영향 테이블

소유 카탈로그 현재 관계·전체 쌍과 동형 HIST를 재사용한다. 현재 논리 정본 ENT-008과 API-024의 저장 계약을 따르며 신규 물리 테이블/관계 독립 원장을 추가하지 않는다. 원천 DB의 FK/DDL은 변경하지 않는다.

### 6-3. 상태 전이

현재 구성 → 로컬 행/소스/두 테이블/컬럼 쌍 입력 → 현재 권한·참조/전체 쌍/순서·소유 기대 리비전 검증 → 관계 영역 저장/전체 이력 원자 반영. 저장 전 효력은 기존 구성이다.

### 6-4. LLM 입력 준비

[REQ-610](../../../../spec/10-requirements/012-reference-business.yaml)의 `prompt_contract.admin_input_preparation.sources.catalog_relation`가 이 화면의 **프롬프트 포함 후보 / 서버 집행 / 관리·감사 항목**, 해석 가이드 및 제공 단계·조건을 정의한다. §4의 실제 컬럼과 대응하며 공통 해석 규칙은 같은 절의 `guides`·`conditions`·`stages`를 따른다.

화면 목록/상세 응답을 그대로 모델에 전달하지 않는다. 기존 관리 값을 사용하고 입력 분류용 컬럼·탭을 추가하지 않는다. 실제 조합·전송과 최종 JSON/CLI·API 계약은 업무 지식 관리·전체 흐름 합의 뒤 소유 작업흐름에서 구체화한다. 아래 검수는 설계 대조이며 목업에서 LLM 호출을 시연하거나 제품 실행 검증을 완료한 것으로 표시하지 않는다.

## 7. API

API-604 getRelationList는 데이터소스/검색어/양끝점 catalogId 조건의 공통 페이지 조회다. API-019 getList는 같은 소스의 객체명·업무명 후보 검색, API-020 getOne은 소유 전체 relations와 columns를 확보한다. API-024 saveChange의 RELATIONSHIPS 명령은 소유 전체 관계를 저장하고 API-027 getRelatedJoins는 양쪽 관리 역조회다. 본문/응답의 정본은 50-api FEAT-011.implementation_transport이며 URL은 /api/admin/service/catalog/ 아래다. 화면 밖 같은 소유 관계도 보존하며 외부 끝점 leftColumns/rightColumns는 정확한 과거 판의 읽기 전용 값이다.

## 8. 시드 · 데이터 전제

039-catalog-relations.sql은 현재/이력의 관계명·감사를 추가하고 041-relation-menu-messages.sql은 메뉴·API 인가·MSG.REL_* 메시지를 등록한다. DBMS_DATA_TYPE의 활성 코드와 PARENT/NATIVE_TYPE 매핑을 서버에서 검사한다. 데이터소스 후보·정확 테이블/컬럼은 실제 등록 원천에서 읽어야 하며 목업 예시를 제품에 하드 코딩하지 않는다.
