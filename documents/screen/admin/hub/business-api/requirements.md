# 요건 정의서 — 업무 API

## 개요

- **무엇을 하는 화면인가**: REQ-608의 API 계약과 입력 필드별 자료형·필수 여부·허용값·값의 출처·채우기 가이드·검증 조건을 관리한다. 고정값·기본값과 허용 조회 참조·결과 추출/변환 안내를 구분하고 해당 지식-API 매핑 건의 사용 설명·업무별 절차를 참조한다. API 자체 저장과 지식 매핑 저장의 경계는 REQ-608을 따른다. 실제 필드 배치·화면 요건서·목업은 P3에서 정한다 REQ-608.result_handling_guide의 API 공통 결과 안내·질문/선택별 후속 처리 가이드를 자연어로 관리하고 계약 원천을 참조한다. 구체 필드·배치·목업은 P3에서 정한다.
- **프로세스상 위치**: 관련 자산·정책 확인 → 이 화면의 조회·입력 → 소유 업무의 검증·직접 저장·변경 이력 기록.
- **이 데이터를 누가 쓰나**: 연결된 관리 업무와 agent의 현재 권한 검증 및 실행 기록.
- **바꾸면 어디가 흔들리나**: REQ-608·REQ-601·REQ-111와 연결된 참조·변경 권한·이력. 정본은 documents/spec이며 이 문서는 화면 검토 초안이다.

## 1. 화면 구성

조회조건 → 상단 업무 API 목록 → 상하 스플리터 → 하단 요청 필드·응답 필드·코드명 제공·결과·재실행 계약·검수 근거·접근 그룹·응답 그룹 예외·대응 도구·연결 지식.
1:1 값은 상단 컬럼, 1:N 집합은 하단 탭으로 표시한다. 장문은 셀 뷰어를 쓴다.
제목·건수는 왼쪽, 작업 버튼은 오른쪽에 정렬한다. 초기 화면의 모든 탭은 실제 전환되며 같은 대상의 입력·선택을 유지한다.
초기 목업은 한 대상 선택 예시이며 실제 목록 조회 후 행은 자동 선택하지 않는다.
상태별 버튼: 허용 목록
행 추가 탭: 요청 필드·응답 필드·접근 그룹

### 1-1. 마스터-디테일 연동

- 대상 안정 식별자와 읽은 문맥/기준 버전으로 전체 구성을 확보한다. 탭의 행과 상위 대상을 섞지 않는다.
- 다른 대상 선택·재조회·화면 이탈은 미저장 입력 확인 후 수행하며 같은 대상 탭 이동은 입력을 유지한다.
- 조회 실패·부분 목록·접힌 탭을 삭제나 빈 전체 집합으로 해석하지 않는다. 처리 중 중복 명령을 막고 결과 불명은 원 키로 확인한다.

## 3. 조회 — 테이블과 범위

### 3-1. 사용 테이블 · 결합

현재 적용된 최종 관리 구성과 현재 권한 범위를 조회한다. 미저장 편집본을 운영 목록에 섞지 않는다.
물리 테이블·결합 키의 신규 상세 설계는 후속이다. 다른 소유의 관측·역참조는 읽기 전용이며 저장 사본에 포함하지 않는다.

### 3-2. 고정 조건 · 기본 정렬

현재 유효 조회 권한과 대상 범위를 적용한다. 표시명과 안정 식별자로 동일 이름을 구별한다. 정확 정렬/페이징 계약은 후속 상세 설계한다.

## 6. 규칙 — 저장 · 실행

### 6-1. 검증

- 변경 권한을 부여받은 소수의 업무 전문가와 관리자만 소유 범위의 전체 구성을 직접 저장한다. 메뉴 표시뿐 아니라 서버가 저장 직전 현재 액션·대상 범위 권한, 자기 기준 리비전, 필수 참조와 기술 검증을 확인한다. 검증된 전체 변경과 변경 전후 이력·변경자·시각·사유는 같은 트랜잭션으로 반영한다. 일반 admin 계정이나 조회 권한만으로 변경할 수 없다. 별도 승인 요청·검토자/승인자 판정·전결/승인 사용 설정은 제공하지 않는다.
- 자기 기준 리비전 충돌·현재 권한·필수 참조 유효성·SQL/API 기술 검증은 유지한다. 저장 전에는 현재 적용본을 바꾸지 않는다.
- 지식은 외부 자산의 안정 ID를 매핑한다. 외부 리비전 상승만으로 지식 매핑·내용을 자동 변경하지 않는다.
- 현재 열람 권한 안의 사용처 식별자·이름·종류·리비전·참조 경로만 조회한다. 지식 본문을 모아 업무 의미의 영향이나 보완 필요성을 판정하지 않는다. 내용 적합성 검토는 운영·유지보수 조직의 자체 절차이며 이 화면에 검토 작업을 만들거나 저장의 필수 단계로 요구하지 않는다. 조회 실패·열람 제한을 참조 없음으로 처리하지 않으며 현재 참조 무결성과 기술 계약 검증은 유지한다.
- 실제 실행에 사용한 정확 계약·가이드 버전은 실행 당시 기록한다. 관리자 저장과 사용자의 실제 업무 실행 확인은 별개다.
- 코드명 조회 실패는 원 업무 성공·접수·불명과 별개다. 원 실행을 재전송하거나 다른 원천·LLM 추정 이름으로 대체하지 않는다.
- API 저장만으로 대응 도구를 생성·노출하지 않는다. 코드 조회 참조가 호출 권한·행 스코프·마스킹을 확대하지 않는다.

### 6-2. 영향 테이블

물리 테이블을 새로 확정하지 않는다. 소유 업무 구성·처리 근거·적용 이력을 기존 정본의 같은 반영 단위로 다룬다. 실패 시 부분 반영·부분 권한 변경을 남기지 않는다. 조회 전용 동작은 변경 없음.

### 6-3. 상태 전이

현재 적용본 → 로컬 변경 입력 → 현재 변경 권한·기준 리비전·전체 구성 검증 → 직접 저장과 이력 원자 반영 → 새 적용본. 저장 전에는 기존 적용본을 유지한다.

## 7. API

신규 물리/API 상세 설계는 후속이다. 이미 정해진 기능·화면·공통 직접 저장 계약을 참조하고 새로운 경로·메서드·요청 DTO는 정하지 않는다. 실행 당시 정확 버전 기록과 현재 권한 검사는 유지한다.

## 8. 시드 · 데이터 전제

메뉴/경로는 화면 정본의 검토안이다. 이번 작업에서 메뉴·메시지·공통코드 시드나 제품 sources/를 변경하지 않는다. 미정 코드/메시지 키는 화면 합의 후 상세 설계한다.
