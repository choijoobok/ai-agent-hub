# 요건 정의서 — 품질 신고 처리

## 개요

- **무엇을 하는 화면인가**: 채팅 또는 저장 조회 개별 실행의 품질 신고 원본·근거와 개별 회신을 관리하고 사후 조사에 연결한다.
- **프로세스상 위치**: 본인 품질 신고 → 관리자 검토/조사 연결 → 개별 조치·회신 → 신고 자체 종결
- **이 데이터를 누가 쓰나**: 권한 있는 관리자와 연결 업무의 담당자가 현재 적용값 또는 업무 처리 근거로 사용한다.
- **바꾸면 어디가 흔들리나**: 소유 기능의 저장·권한·참조 및 이력/감사 연결을 함께 확인한다.

> 미구현 화면 초안이며 사용자 화면 합의·제품 구현·G3(설계 승인 게이트) 승인이 아니다. [화면 정본](../../../../spec/60-screens/_index.yaml)과 [기능 정본](../../../../spec/31-features/002-admin.yaml)을 따른다. 표시 예시는 실제 데이터·물리명·운영 기본값이 아니다.

## 1. 화면 구성

상단 조회조건 → 품질 신고 처리 목록 → 처리·회신 · 당시 증거 · 조사 연결 기록 순서다. 제목·건수는 왼쪽, 작업 버튼은 상단·그리드 툴바·모달 하단에서 우측 정렬한다. 초기 화면의 모든 탭은 실제 전환하며 같은 상위 대상의 입력·선택·추가/제거 행을 유지한다.

### 1-3. 마스터-디테일·이력 경계

- 선택 변경·조회·이탈 때 미저장 변경을 확인하고 취소하면 선택·입력을 보존한다. 결과 불명에는 새 명령 없이 원 처리 결과를 확인한다.
- 업무 원장·로그의 자체 기록을 조회한다. 이 화면 자체를 관리 구성 이력으로 복제하지 않는다.
- 선택 신고의 검토/회신·종결 근거와 현재 조사 연결 사건. 신고 원문·실행 원본은 수정하지 않음

## 3. 조회 — 테이블과 범위

### 3-1. 사용 테이블 · 결합

| 테이블 | 역할 | 결합 기준 |
|---|---|---|
| 미정 — 논리: 품질 신고 처리 | 소유 업무 기록/원장 | 안정 식별자 + 해당 조회 문맥. 물리 테이블·컬럼·조인/API는 소유 상세 설계 후속 |

### 3-2. 고정 조건 · 기본 정렬

- 항상 현재 메뉴·액션과 대상 열람 범위를 서버에서 검사한다. 선택한 업무 기록의 당시 내용과 현재 관측을 구분한다.
- 기본 정렬·페이지 방식·조회 기간/상한·보존 기간·대량 반출 한도는 소유 계약 미정이다. 운영값을 추정하지 않는다.
- 빈 결과·권한 제외·조회 실패·미확인을 구분한다. 명령과 연계 조회의 권한을 자동 승계하지 않는다.

### 6-2. 영향 테이블 · 저장 범위

| 트리거 | 테이블 | 작업 | 조건 · 내용 |
|---|---|---|---|
| 소유 저장/명령 | 물리명 미정 — 소유 논리 집합 | 선택 신고의 검토/회신·종결 근거와 현재 조사 연결 사건. 신고 원문·실행 원본은 수정하지 않음 | 검증·현재 권한·자기 기준본과 실제 결과를 함께 확인. 일부만 반영하지 않음 |

### 6-3. 상태 전이

접수 → 검토 → 종결. 조사 접수/분석/종결은 별도 상태다. 완료 조사에 사후 연결하더라도 신고의 회신/종결을 자동 대체하지 않는다.

## 8. 시드 · 데이터 전제

- 코드그룹·메시지 키·물리 테이블·필드·신규 API 경로는 미정이다. A 담당 공통 정본 확정 후 연결하며 이번 작업에서 시드·제품 소스를 변경하지 않는다.
- 메뉴/경로는 §0의 등록된 설계값만 사용한다. 연결 대상 메뉴·본문·증거·반출은 현재 유효 권한을 각각 검사한다.
- 초기 운영값·조회 상한·보존 기간은 미정. 기존 정본의 확정 계약을 소비하고 목업 예시로 운영 기본값을 정하지 않는다.
