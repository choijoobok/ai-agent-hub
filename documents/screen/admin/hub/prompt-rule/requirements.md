# 요건 정의서 — 프롬프트 규칙

## 개요

- **무엇을 하는 화면인가**: 제목·사용 여부와 관리자 참고용 설명·Markdown(마크다운 문서 표현 형식) 본문을 작성하고, 전체 규칙을 실제 전송 형태로 조합해 모순·문제를 검토한다.
- **프로세스상 위치**: 규칙 작성 → 전체 가공본 확인/agent 경유 LLM(대규모 언어 모델) 검토 → 관리자 판단·사유 → 직접 저장/불변 이력 → 호출별 유효 내용 소비.
- **이 데이터를 누가 쓰나**: 관리자는 설명과 본문을 편집하고 agent는 본문을 조합한다. 규칙 설명은 운영·검토 모델에 전송하지 않는다.
- **바꾸면 어디가 흔들리나**: 전사 안내·응답 정책과 전체 검토 결과의 최신성. 현재 권한·실행 승인·통신 계약은 별도로 유지한다.

> 미구현 설계 검토본이다. 실제 서버 저장·LLM 호출·화면 전체 승인·G3(설계 완료 게이트) 승인을 뜻하지 않는다. [화면 정본](../../../../spec/60-screens/005-screens.yaml)과 [규칙 정본](../../../../spec/10-requirements/012-reference-business.yaml)의 REQ-610을 따른다.

## 1. 화면 구성

조회조건 아래 **좌측 규칙 목록 그리드 / 우측 두 textarea(여러 줄 입력창)**를 둔다. 우측은 규칙 설명 위·본문 아래이며 하단 탭은 없다. 가운데 스플리터로 너비를 조절한다. 목록의 내부 식별자는 기본 숨김, 업무 표시 열은 제목·사용 여부와 등록자·등록일시·수정자·수정일시 네 감사 컬럼이다. 공통 번호·선택/편집 상태·삭제 열은 그리드 표준을 따른다.

우선순위·적용 조건·리비전·변경 사유·검토 상태는 목록 업무 컬럼으로 두지 않는다. 리비전은 서버 동시성/이력 근거로 유지하고 변경 사유와 관리자 최종 판단은 저장 레이어에서 받는다. 별도 의미 검토·관리자 판단 탭은 없다.

### 1-3. 모달과 저장 사유

본문 크게 편집은 현재 행 본문의 임시 편집본을 연다. 모달 오른쪽 아래 모서리를 마우스로 끌어 가로·세로 크기를 조절하며 본문 입력창도 함께 늘어나고 줄어든다. 크기 조절은 편집 내용을 유지하며 화면 범위 안에서 조절해 반영·취소 버튼에 접근할 수 있어야 한다. 반영하면 같은 행 textarea에 옮기고, 취소·닫기·Esc는 열기 전 본문을 유지한다. Markdown 미리보기는 저장된 HTML이 아닌 현재 본문 원문으로 읽기 전용 렌더링한다. 검토 모달은 전체 조합 내용과 실제 검토 결과/최신성 상태를 보여준다. 모달만 열거나 미리보기를 바꾸어 저장·검토 호출하지 않는다.

저장은 변경된 규칙 집합의 같은 편집본과 새 사유를 검증한다. 경고·실패를 참고해 반영할 때 관리자의 판단 근거를 사유에 기록한다. 공백 사유는 거부하고 취소 시 입력을 보존한다. 저장 결과를 실제 LLM 검토 통과로 표시하지 않는다.

## 3. 조회 — 테이블과 범위

### 3-1. 사용 테이블 · 결합

물리 테이블·컬럼·공개 필드는 소유 P3(설계 단계) 후속이다. 현재 규칙과 기준 리비전·불변 이력은 REQ-601·REQ-108·REQ-610을 따른다. 실제 LLM 호출은 admin→agent 경유이며 운영용 모델·effort(추론 강도) 설정과 관리자 사용량 정책을 사용한다.

### 3-2. 고정 조건 · 기본 정렬

현재 메뉴/행위·대상 권한을 검사한다. 내부 숫자 식별자 오름차순을 안정된 기본 표시/조합 순서로 사용하고 미발급 신규 행은 이번 편집의 추가 순서로 뒤에 둔다. 이 순서는 규칙 사이의 우선순위나 충돌 해결 정책이 아니다. 사용자 정렬·검색·현재 페이지는 전체 검토 조합 순서를 바꾸지 않는다. 조회 실패/부분 조회를 완전한 전체 규칙으로 검토하지 않는다.

## 6. 규칙 — 저장 · 실행

### 6-1. 관리자 설명과 Markdown 본문

REQ-610.prompt_contract.editor가 정본이다. 설명은 작성 이유와 운영 메모이며 프롬프트/검토 대상에 포함하지 않는다. 본문은 Markdown 원문을 저장·전송하고 화면 미리보기 HTML은 저장/전송하지 않는다. 제목·목록·강조·인용·표·코드 블록을 확인할 수 있으며 raw HTML은 실행하지 않는다. 스크립트/이벤트/위험 URL(주소)·외부 이미지 자동 요청을 막는다. 미리보기는 보호 설정/원문을 조회하거나 변수 치환을 수행하지 않는다.

### 6-2. 전체 규칙 검토

REQ-610.prompt_contract.review_set을 따른다. 사용 중인 전체 저장 규칙에 이번 미저장 변경/추가/삭제/사용 전환을 반영한 최종 편집 구성을 검토한다. 현재 선택 행·검색 결과·페이지에 한정하지 않는다. 미사용 본문과 관리자 설명·감사 컬럼은 전송하지 않는다. 전송 대상 제목/본문이 불완전하거나 전체를 확보하지 못하면 누락된 정상 검토를 만들지 않는다.

실제 agent 조립 경로를 사용해 규칙 사이의 구분·순서·Markdown 원문을 보존한다. 공통 규칙 묶음과 호출 유형별 기술 템플릿/출력 계약이 반영된 가공본을 구분해 검토한다. 단계별 동적 업무 데이터는 검토용 허용 예시/미제공 상태로 명시하고 실제 사용자/업무 데이터를 임의 조회·전송하지 않는다. 다른 단계의 계약을 하나의 실행 프롬프트로 섞지 않는다. 검토용 상위 지시는 고정하며 대상 규칙을 검토 자료로 전달하고 업무 도구 실행은 허용하지 않는다.

결과는 규칙 간 모순·중복·모호성·서버 계약과의 충돌 의심, 관련 구절·이유·수정 권고를 제시한다. 본문을 자동 수정·저장하지 않는다. 이 화면의 목업은 조합과 상태만 시연하며 실제 LLM 응답/무모순을 만들지 않는다.

### 6-3. 최신성·실패·저장·이력

전체 검토의 규칙 집합/정확 내용·사용 여부·조합 버전·출력 계약·모델·사용량·결과를 연결한다. 다른 규칙 변경·새 저장·늦게 도착한 검토 응답은 현재 가공본과 대조한다. 같은 결과를 현재 완료로 덮지 않으며 변경된 전송 내용은 다시 검토한다. 설명만 수정해 전송 내용이 같을 때의 재사용과 저장 리비전/현재 권한 재검증은 구분한다.

검토 실패·시간 초과·지원 불가·길이 초과·부분 전송은 미완료이며 자동 통과가 아니다. 권한 있는 관리자의 최종 반영 판단·사유와 검토 사실을 함께 보존하는 기존 정책을 유지한다. 필수 입력·현재 권한·동시성·실제 통신 계약 오류는 사유로 우회하지 않는다.

규칙 저장은 내부 식별자·기준 리비전·변경분·사유·전체 변경 이력을 원자 반영한다. 전체 검토는 변경되지 않은 규칙을 재저장하지 않으며 다른 관리자의 갱신을 덮지 않는다. SCR-050(프롬프트 규칙 변경 이력)은 원 화면을 읽기 전용 상속하고 당시 설명·본문·사용 여부와 저장 메타데이터를 표시한다. 현재 규칙으로 과거 내용을 대체하지 않는다.

### 6-4. 소비와 다른 기능의 경계

REQ-101의 업무 연관성 가이드, REQ-104의 SQL(질의문)·물리명 비노출, REQ-112의 전사 응답 규칙을 작성할 수 있다. 규칙은 현재 권한·데이터 전송·실행 승인·쿼터·출력 계약을 바꾸지 않는다. REQ-308의 사용 안내 지식 정본은 별도 지식 관리가 소유한다. 모델의 검토 통과는 서버 통제나 사용자 화면 승인을 대신하지 않는다.

## 7. API

API(응용 프로그램 인터페이스) 경로·메서드·공개 필드명은 소유 상세 설계 후속이다. 관리 저장과 agent 검토 요청을 구분하고 현재 권한·전체 구성 근거·원 명령/검토 식별자·정확 가공본·결과 상태를 연결한다. 목업에서 가상 성공이나 실제 호출을 하지 않는다.

## 8. 시드 · 데이터 전제

제품 소스·시드·물리 DB(데이터베이스) 모델은 화면/작업흐름 G3 승인 뒤 구현한다. 신규 식별자는 기존 서버 시퀀스를 따르며 목업은 숫자를 발급하지 않는다. 이 화면의 규칙 예시는 운영 필수 문구나 모델 전송 이력이 아니다.
