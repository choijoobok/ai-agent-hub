# 요건 정의서 — Portal 사용자 관리

## 개요

- **무엇을 하는 화면인가**: 관리자와 독립된 Portal 사용자의 계정·이용기간·상태를 관리하고 하단 다섯 탭에서 그룹·등급·추가 배정·대상별 아이디를 확인한다.
- **프로세스상 위치**: 사용자 선택 → 각 탭 조회/편집 → 소유 단위 직접 저장 → 현재 적용본 확인.
- **이 데이터를 누가 쓰나**: Portal 계정·접근·쿼터 관리 담당자와 현재 권한을 검사하는 portal·agent.
- **바꾸면 어디가 흔들리나**: REQ-616.screen_contract와 REQ-609.identity_management. 관리 콘솔 인증과 대상 Portal 로그인·대상 업무 신원은 별개다.

### 1-1. 마스터-디테일 연동

- 사용자와 탭을 왕복해도 각 입력·선택을 유지한다. 재조회·이탈은 미저장 확인 후 수행한다. 새 계정은 등록을 마친 뒤 하단 구성을 저장한다.
- 데이터소스 탭은 REQ-603/SCR-002, 대상 시스템 탭은 REQ-604/SCR-001의 현재 열람 허용 기준정보를 목록으로 불러와 현재 사용자 매핑과 함께 표시한다. 후보마다 새 매핑을 자동 생성하지 않고 필요한 행만 설정한다.
- 미설정은 빈 아이디·꺼짐, 미상/실패는 확인 필요다. 비활성 대상은 이유와 잠금을 표시하며 기존 매핑 근거를 지우지 않는다. 미열람·일부 결과·다른 탭 매핑을 전체 없음으로 해석하지 않는다.
- 대상 시스템 사용자 아이디는 그 시스템의 API 호출이 참조한다. API별 아이디 매핑·데이터소스별 DB스키마 매핑은 추가하지 않는다.

## 3. 조회 — 테이블과 범위

### 3-1. 사용 테이블 · 결합

Portal 계정 원장과 사용기간·감사, 사용자 그룹 부여/회수, 미래 등급 예약·월별 배정/계량·추가 신청, 대상 기준정보와 사용자별 신원 매핑을 소유 공개 계약으로 조회한다. 물리명·결합 키는 후속 상세 설계다. 대상 비밀번호·접속 계정·토큰·system 자격증명은 조회하지 않는다.

### 3-2. 고정 조건 · 기본 정렬

현재 메뉴/원 소유 열람 권한과 사용자 문맥을 적용한다. 한 사용자+대상 종류+안정 대상 참조의 매핑을 구분하며 동명 대상으로 대체하지 않는다. 인사 변경의 원 사건·처리 결과는 기존 SCR-031과 변경 이력(SCR-044)에서 참조하고 별도 하단 탭은 두지 않는다.

## 4. 컬럼

미정 라벨 키·필드·물리명은 화면 승인 후 상세 설계한다. 모든 여부형은 스위치이며 현재 권한/업무 조건이 허용한 설정만 편집한다. 감사 넷은 서버 기록이고 민감값을 노출하지 않는다.

그룹 탭에는 삭제를 제공하지 않는다. 아이디 매핑 두 탭은 기준정보 후보 목록이므로 행 추가/삭제도 제공하지 않고 필요한 행의 설정·중지만 처리한다. 스위치/셀 변경은 저장 전 입력이며, 실제 저장 성공은 목업에서 수행하지 않는다.

- 대상 시스템 기준정보는 REQ-604의 YAML 정본·DB 표시 보완을 조회한다. 설정 제거는 기존 계정 매핑과 감사를 보존하며 현재 설정 유효성으로 신규 후보·실제 사용을 제한한다. 시스템 기본 연결이나 접속 인증 비밀을 이 탭에 설정하지 않는다.

## 6. 규칙 — 저장 · 실행

### 6-1. 검증

변경 권한을 부여받은 소수의 업무 전문가와 관리자만 직접 저장한다. 서버는 저장 직전 현재 액션·대상 범위 권한과 자기 기준 리비전·필수 참조·기술 검증을 확인한다. 전체 변경과 변경 전후 이력·변경자·시각·사유를 원자적으로 반영한다. 조회 권한이나 일반 admin 계정만으로 변경할 수 없으며 별도 승인 요청·전결·승인 사용 설정은 제공하지 않는다.


- 관리자와 Portal의 계정·비밀번호 이력·인증·세션은 별개다. 자체 Portal 계정은 system과 동등한 실패 횟수 초과 잠금·최근 비밀번호 재사용 금지·설정 주기에 따른 변경 의무·임시 비밀번호/초기화·잠금 해제를 제공한다. 정책 검증의 공통 구현은 재사용할 수 있으나 계정 상태는 공유하지 않는다. 외부 인증의 비밀번호는 원천이 소유한다.
- 신규 계정은 이용 상태 꺼짐으로 먼저 저장하며 최초 등급은 현재 유효 기준의 최저 등급을 기본 선택해 부여한다. 그룹 추가 저장 후 이용 조건을 확인해 이용을 켠다. 계정 선등록 시각과 실제 Hub 이용 개시일을 구분하고 최초 배정은 효력일에 한 번만 수행한다.
- 로그인 아이디는 신규 때만 입력하고 기존 변경/재사용으로 과거 이력·권한을 다른 사람에게 넘기지 않는다. 내부 안정 참조·외부 subject를 삭제하거나 system 계정과 병합하지 않는다.
- 사용 시작/종료일은 고객사 업무일의 양 끝을 포함하고 종료일은 시작일 이상이다. 이용 상태·기간·그룹·등급·잠금 등은 각각 검사한다. 시작 전/만료 후 이용을 막고 미래 시작일만으로 당월 일할 배정을 미리 생성하지 않는다. 대상 월 1일에 기간 전/만료인 사용자는 월 배분 대상/인원에서 제외하고 월중 이용 개시는 효력일 일할 배정으로 한 번만 처리한다. 재활성화는 REQ-116의 월별 중복 방지 규칙을 따른다.
- 그룹 추가·재부여·중지는 현재 권한을 가진 관리자가 직접 처리하며 별도 승인 화면/요청을 만들지 않는다. 마지막 활성 그룹 중지는 이용자 비활성화와 함께 처리한다. 감사 넷과 원 부여/회수 이력을 보존하고 물리 삭제하지 않는다.
- 신원 매핑 신규·아이디 교체·중지·재설정은 승인·전결 없이 직접 저장한다. 현재 변경 권한·사용자/대상 유효성·아이디 연결 근거·사유·기대 버전 검사 후 현재값과 변경 전후 감사 이력을 함께 반영한다. 다른 대상/사용자/탭은 포함하지 않는다. 켜짐은 아이디/근거 필수, 꺼짐은 권한 없음이며 과거 이력은 남긴다.
- 대상 아이디는 DB 접속 서비스 계정/API 인증 토큰과 별개다. 매핑만으로 카탈로그/개별 API의 그룹 권한·행 스코프·대상 시스템 자체 권한을 우회하지 않는다. 신원이 없으면 신원 설정 오류로 거부하며 정상 0건으로 바꾸지 않는다.
- 쿼터 일반 추가/수정/비활성화는 미래 년월만 가능하다. 신규 등록 당월 최초 등급·일할 배정과 첫 사용 전 최초 정정은 REQ-116의 등록 예외로 구분한다. 토큰 한도는 배분에서, 사용량은 실제 계량에서 생성하며 이 탭에서 입력하지 않는다.
- 추가 토큰은 선택 사용자의 신규/재활성 일할 배정 및 추가 신청 원장을 조회만 한다. 신청량과 실제 승인량·부분 승인·미처리 상태를 구분하고 승인/한도 반영은 REQ-119/SCR-022가 소유한다. 당월 적용·월말 만료·이월 금지를 유지한다.

두 탭의 소속 데이터 항목·복합 식별·감사 의미는 REQ-609.membership_record를 따른다. 같은 사용자/그룹 조합의 중복 행을 만들지 않고 재부여는 기존 소속을 활성화하며 최초 등록 감사값을 보존한다. 어느 화면에서 저장하든 동일한 현재값·변경 이력과 기대 버전을 사용한다. 사용자/그룹 이름은 참조 정보이며 별도 소속 저장 컬럼으로 복제하지 않는다.

### 6-2. 영향 테이블

Portal 계정·소속 부여/회수·등급 예약·신원 현재 매핑/감사는 각 소유 원장으로 저장한다. 목록 후보를 새 매핑으로 일괄 등록하지 않는다. 기존 신원 승인 대기/과거 기록이 있으면 이력으로만 보존하고 새 직접 저장/그룹 부여로 자동 전환하거나 늦은 승인으로 현재 매핑을 덮어쓰지 않는다.

### 6-3. 상태 전이

신원: 기준정보 후보/현재값 조회 → 필요한 행 편집 → 직접 저장·감사와 원자 반영 → 현재값 재조회. 실패/충돌은 기존 유효 매핑과 입력 보존, 결과 불명은 원 저장 결과 확인이다.
그룹: 그룹 선택·사유 입력 → 현재 변경 권한·사용자/그룹 유효성·기대 버전 검사 → 직접 부여·이력 기록. 중지는 직접 회수이며 재부여는 새 부여 이력이다.

추가 후보의 원천과 선택 결과는 REQ-609.membership_record.candidates를 따른다. 추가 버튼은 이 탭에 하나만 두며 표시명은 추가다. 추가한 행에서만 사용자 그룹 콤보를 편집하며 사용자는 상단 선택에 고정한다. 중지는 활성화 여부를 끄고 저장한다. 그룹 추가/중지 전용 명령과 중복 추가 버튼은 제공하지 않는다. 현재·미저장 소속의 중복을 검사하고 저장 시 현재 권한·대상 유효성·기대 버전을 다시 검증한다.

## 7. API

Portal 계정 공개 계약·기준정보 후보 조회·대상별 아이디 직접 저장·그룹 부여/회수·미래 등급 예약·배정 이력 조회는 기능 소유 공개 계약에서 상세 설계한다. 이번 화면 검토에서 URL·DTO·테이블을 새로 확정하지 않는다.

## 8. 시드 · 데이터 전제

메뉴·권한·메시지 시드와 제품 sources/는 변경하지 않는다. 데이터소스와 대상 시스템 기준정보를 현재 열람/설정 권한 범위에서 조회할 수 있어야 한다. 신원·그룹 부여에 대한 승인 절차·설정은 제공하지 않는다.
