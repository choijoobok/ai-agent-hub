# 요건 정의서 — 스키마 카탈로그

## 개요

- **무엇을 하는 화면인가**: 공개 테이블·뷰의 마스터와 컬럼·그룹·인덱스를 관리하고 현재 매핑된 연관 지식을 조회한다. 관계 편집은 별도 SCR-039가 맡는다.
- **프로세스상 위치**: (선행) 데이터소스·공개 대상 선정 → **이 화면의 적용본 조회/변경 입력** → (후행) 자산 변경 세트의 검증·직접 저장·이력 반영.
- **이 데이터를 누가 쓰나**: 지식·인증 예제·agent 조회 계획. 현재 운영본·제출본·미완성 초안을 구분하며 현재 접근/정책을 별도 재검증한다.
- **바꾸면 어디가 흔들리나**: 연결 지식·인증 예제·관계·조회 제약의 의미와 참조 버전. 원천 구조 정상만으로 업무 의미 변화가 없다고 판단하지 않는다.

> 미구현 설계 초안이다. [REQ-301/304/306](../../../../spec/10-requirements/007-knowledge-catalog.yaml), [FEAT-003/011](../../../../spec/31-features/002-admin.yaml), [카탈로그 저장/공개 계약](../../../../spec/50-api/005-admin-catalog-contracts.yaml)이 정본이다. 현재/이력 저장의 공통 경계는 REQ-601.management_storage를 따른다.

## 1. 화면 구성

[조회조건 / 조회·신규·저장 또는 저장]
[현재 적용 카탈로그 목록]
[컬럼 정의 · 사용자 그룹 · 컬럼 그룹 예외 · 인덱스 · 연관 지식]

- 목록·상세는 최종 적용본만 조회한다. 선택 마스터의 적용 리비전을 기준으로 영역별 입력을 유지한다. 각 저장 버튼은 자기 영역만 반영한다.
- 변경 권한을 부여받은 소수의 업무 전문가와 관리자만 소유 범위에서 클릭한 버튼 영역의 변경을 직접 저장한다. 메뉴 표시뿐 아니라 서버가 저장 직전 현재 액션·대상 범위 권한, 자기 기준 리비전, 필수 참조와 기술 검증을 확인한다. 검증된 해당 영역 변경과 그 시점 전체 구성 이력·변경자·시각·사유는 같은 트랜잭션으로 반영한다. 일반 admin 계정이나 조회 권한만으로 변경할 수 없다. 별도 승인 요청·검토자/승인자 판정·전결/승인 사용 설정은 제공하지 않는다.
- 저장 성공 후 해당 영역/기준 리비전을 갱신하며 다른 탭의 미저장 입력을 보존한다. 저장 실패·결과 불명은 입력과 원 명령 키를 보존한다.
- 신규 마스터를 먼저 저장한 뒤 발급 ID로 자식 영역을 저장한다. 미완성 메타데이터의 AI 사용 제한은 유지한다.
- 관리 화면에 내용 버전/이력 탭을 두지 않는다. 실제 반영 이력은 별도 원 화면 상속 이력에서 읽는다.
- 각 탭은 그리드 하나이며 같은 조회 기준으로 영역별 입력을 유지한다. 관계는 별도 SCR-039에서 확인하고 미열람 관계도 전체 저장에 보존한다.
- 그룹 코드·상세 설명·그룹 예외·인덱스의 업무 검증은 REQ-301·103·111과 FEAT-003/011을 따른다. 원천 관측·연관 지식는 저장 대상이 아니다.
- 현재 열람 권한 안의 연관 지식 식별자·지식명·매핑 활성 여부만 조회한다. 지식 본문을 모아 업무 의미의 영향이나 보완 필요성을 판정하지 않는다. 내용 적합성 검토는 운영·유지보수 조직의 자체 절차이며 이 화면에 검토 작업을 만들거나 저장의 필수 단계로 요구하지 않는다. 조회 실패·열람 제한을 참조 없음으로 처리하지 않으며 현재 참조 무결성과 기술 계약 검증은 유지한다.

### 1-1. 마스터-디테일 연동

- 최초 및 행 선택은 CURRENT 문맥의 전체 구성을 읽는다. 마스터 REVISION으로 충돌을 검사하며 탭별 독립 업무 리비전은 없다.
- 저장은 saveTarget·해당 영역 변경값·reason·BASE_REVISION을 전달한다. 서버는 현재 확정된 다른 영역과 합쳐 전체 참조를 검증하고 그 시점의 전체 HIST를 복사한다. 현재 구성과 _HIST의 원자 저장 경계는 REQ-601.management_storage를 따른다.
- 적용 이력은 HISTORY_NO로 별도 이력 화면에서 전체 세트를 읽고 현재 탭 데이터를 섞지 않는다.
- 미저장 변경이 있는 행 전환·조회·이탈은 확인하고 취소하면 입력을 보존한다. 저장/결과 불명 중에는 원 키와 입력으로 결과만 확인한다.
- 별도 SCR-042는 이 화면의 조회조건·배치·탭을 읽기 전용 상속하고 변경 요약과 이력 저장일시 범위만 추가한다.

### 1-6. 저장 사유 입력창

상단과 각 편집 탭의 저장 버튼은 소유 영역의 고정 saveTarget 코드를 전달한다. MASTER=마스터 데이터, COLUMNS=컬럼 정의, ACCESS_GROUPS=사용자 그룹, COLUMN_GROUP_EXCEPTIONS=컬럼 그룹 예외, INDEXES=인덱스, RELATIONSHIPS=별도 관계 편집이다. 변경 사유 레이어 팝업의 trim 후 비공백 reason과 해당 영역 변경값만 반영한다. 단, ACCESS_GROUPS에서 그룹을 제거할 때 그 그룹의 저장된 컬럼 예외를 서버가 함께 정리하는 것은 동일 명령의 필수 연쇄 처리이며 다른 탭 입력 저장이 아니다. 삭제 대상 그룹에 속한 미저장 예외는 함께 폐기될 내용을 먼저 확인하고, 취소하면 그룹·예외 입력을 모두 보존한다. 다른 그룹의 예외 편집은 유지한다. 서버는 대상 코드·허용 필드·현재 권한/기준 리비전·전체 참조 무결성을 검증하며 다른 탭의 미저장값은 반영하지 않는다. saveTarget을 그대로 이력에 저장하고 실제 차이로 대상을 재계산하지 않는다. 변경 없음은 새 이력 없이 반환한다. 현재 확정 구성에 영역 변경을 합쳐 같은 HISTORY_NO의 전체 HIST를 복사하며 부모에 saveTarget과 HIST_REASON을 기록한다. 취소는 전송하지 않고 다른 탭 입력도 유지한다. 실패/충돌/결과 불명 및 동일 명령 재시도는 원 대상·reason·입력·commandKey를 보존한다. 성공 후 새 저장은 새 메모를 받고 다른 탭 편집은 보존한 채 최신 기준 리비전/참조를 재검사한다. SCR-042는 저장된 saveTarget 명칭과 메모를 변경 대상/변경 사유로 조회한다.

변경 근거/근거 대상 원장은 품질 조사·구조 비교의 소유에서 관리하며 저장 메모와 합치지 않는다.

### 4-2. 편집 가능 판단 — 조건부

현재 SAVE/소유 권한 + 적용본 전체 구성 확보 + 기준 리비전 일치에서만 임시 변경 입력을 편집한다. 관계 입력은 이 화면에서 제공하지 않으며 관리 카탈로그의 전체 후보 관계/쌍은 보존한다. 정책 값·서버 검수자/시각·현재 리비전/식별키는 편집하지 않는다.

- 상단 신규행은 데이터소스·정확 객체 식별·유형을 직접 입력하고 업무명/설명은 검수 전까지 완성한다. 조회 행도 업무명/설명/사용 여부를 수정하며 물리 이름/위치는 입력을 허용하고 저장 시 동일 객체 정정 검증을 거친다. 내부 식별자·DBMS/버전·식별 규칙·감사/리비전은 직접 수정하지 않는다.

### 컬럼 순서와 기본 정렬

컬럼 순서 ordinalPosition은 원천 DBMS에서 확인한 양의 정수 순서를 보존하는 카탈로그 메타데이터다. 원천 메타데이터 조회 성공 시 채우며 수기 등록/정정도 허용하고 출처·확인 근거를 구분한다. 확인 불가 시 기존 값을 지우거나 임의 0/행 번호를 저장하지 않으며 신규 미확인은 null이다. 같은 카탈로그의 확인된 순서는 중복 불가이고 공개한 컬럼이 부분 집합일 수 있으므로 연속 번호를 강제하지 않는다. 컬럼 정의는 순서 오름차순, null은 마지막, 동률은 안정 컬럼 ID(신규는 clientKey)로 정렬한다. 원천 테이블의 실제 순서·PK 안의 컬럼 순서와 그리드 No는 다른 값이다. 카탈로그 순서 입력은 원천 DDL/컬럼 재배치를 실행하지 않는다. COLUMNS 영역과 같은 HIST에 저장하고 과거는 당시 값으로 정렬한다.

### 4-3. 값 변경 후 연쇄 · 재계산

구조·의미·그룹 코드/상세 설명·키 변경은 관련 기술 검수를 유지한다. valueMode/직접 코드값 목록은 저장하지 않는다. 데이터소스는 기존 카탈로그에서 고정하고 다른 실체 이전을 우회하지 않는다.

### 4-4. 팝업 · 모달 선택 결과 매핑

API-028의 선택적 원천 객체 확인과 수동 입력, API-036의 등록 컬럼/키 후보 선택 계약을 셀 선택 창에 연결한다. 전달값은 소유 catalogId와 명시 readContext·용도·현재 권한, 결과는 정확 대상/선택 버전·역할이다. 후보 페이지에 없음을 MISSING으로 추정하지 않는다. 관계 생성·관리측 고정·전체 쌍 편집은 SCR-039에서 상세 설계한다. 신규 clientKey의 같은 저장 내부 참조와 서버 memberId 매핑을 구분한다.

### 4-5. 행 추가 기본값

신규 구성은 clientKey를 부여하고 확인하지 않은 의미/검수/차원은 UNKNOWN 또는 미지정으로 둔다. 개인정보 아님·검수 완료·임의 시간대/조인 관계를 자동 선택하지 않는다. 코드/공통코드의 실제 허용값은 소유 계약을 따른다.
복사/복원은 같은 카탈로그의 새 DRAFT이며 원본 버전과 현재 기준 버전을 별도로 기록한다. 과거 직접 정책·기존 검수 완료를 새 내용/현재 권한의 근거로 자동 복사하지 않는다. 원천 DB 기본값은 관리하지 않는다. 사이즈와 인덱스 메타데이터는 REQ-301.column_workspace/index_metadata에 따라 후보에 포함하며 물리 저장 매핑은 후속이다. DB 구조 변경 기능은 없다.

### 4-6. 비노출 저장 컬럼

OBJECT_KEY·COLUMN_KEY·명령 지문 및 명령/서버 검수 근거는 서버가 계산/검증한다. 정정/이름 변경의 사용자 근거를 지문/서버 식별 근거로 대체하지 않는다. 1:N 값은 자식 테이블에 저장하며 화면 표시 문자열을 DB의 짧은 연결 문자열로 저장하지 않는다.

### 마스킹 유형의 원천

REQ-611.masking_utility가 정본이다. 이름·전화번호·상세 주소·차량 번호·이메일·연봉·계약금·식별정보 등 배포 유틸이 지원하는 유형을 공통 조회 계약으로 읽어 선택한다. 위 후보는 검토용 예시이며 실제 소스 구현 전 지원 완료를 뜻하지 않는다. 개인정보 유형은 보호 분류, 마스킹 유형은 값을 가릴 유틸의 정보 유형이므로 구분한다. 규칙/정규식·자릿수 설정 버튼이나 별도 정의 편집 화면은 없다.

조회 실패/지원 중단은 기존 선택 코드를 보존해 확인 필요로 표시하며 검수 확정을 막는다. 유형 변경은 소유 컬럼 전체 구성/이력에 반영한다. 실제 변환의 적용 코드/유틸 버전과 이미 저장된 마스킹 사본의 보존은 해당 REQ의 history를 따른다.

유틸의 목록 응답은 [{value,text}]이며 원응답 text는 유형명 메시지 키다. 화면은 items.map(item => ({value:item.value,text:label(item.text)}))로 번역해 기존 SelectOption 규약을 사용한다. CodeSelect·검색 콤보는 text를 완성된 표시 문구로 받는다. 언어 전환으로 선택·저장 코드나 실제 마스킹 유형을 바꾸지 않는다. 유형별 다국어 키/지원 언어 번역은 기존 메시지 체계에 등록하며 별도 유형명 관리 화면을 만들지 않는다. 위 한글 후보/코드 매핑은 목업 예시다.

- 테이블 관계는 [테이블 관계](../catalog-relation/requirements.md)에서 관리한다. 관계·그룹 편집은 같은 카탈로그 전체 구성을 보존하며 이동 전 미저장 입력 확인·현재 권한 재검사를 적용한다. 숨은 탭/미조회 관계를 삭제로 간주하지 않는다. SCR-042 이력은 원 화면 상속이다.

구조 불일치 비교는 REQ-304.batch_structure_comparison.relevance_scope에 따라 LLM SQL 작성/키 의미/인덱스 활용 관련 메타데이터에 한정하며 데이터소스 화면에서 수행한다. DBA 저장/압축/조각화 등 운영 속성은 비교 대상이 아니다.

사용자 그룹 탭의 후보 상태는 편집 차이여서 별도 열을 제공하지 않는다. 공통 행 상태를 사용하고 자산 useYn과 별개인 매핑 활성 여부 mappingActive를 설정 스위치로 관리한다. 인덱스 탭은 정의 종류·이름·유일 여부·구성 순서·컬럼·정렬 방향·원천 근거를 관리하고 검수 상태를 직접 입력하지 않는다. 서버 기술 검증/지원 범위·미확인 근거는 유지하며 불완전한 인덱스를 검증된 SQL 작성 근거로 사용하지 않는다.


매핑 활성 여부는 REQ-601.asset_mapping_active를 따른다. 소유 매핑 그리드는 신규/조회 행 모두 설정 스위치로 바꾸고 원 소유 구성 저장과 전체 이력에 반영한다. 역조회 그리드는 같은 원값의 읽기 전용 스위치이며 현재 참조 존재 여부는 기술 참조 보호용 비표시 응답 문맥으로 보존하고 매핑 활성은 원 소유 링크의 별도 값으로 표시한다. 비활성 행도 관리 조회에 남기고 실제 후보/접근/검색/호출 경로에는 활성 링크만 사용한다. 자동 SQL 카탈로그 참조는 읽기 전용 필수 기술 참조이며 임의 해제하지 않는다. 같은 부모의 다른 행/탭 입력·선택과 원복을 보존한다.

## 6. 규칙 — 저장 · 실행

### 6-1. 검증

- 그룹/컬럼 예외 편집은 이 화면의 사용자 그룹·컬럼 그룹 예외 탭에서만 제공한다(FEAT-007). 정의 편집 권한과 정책 영역의 현재 변경 권한을 별도로 검사한다. 정책만 변경 가능한 관리자는 마스터/컬럼 정의를 편집할 수 없고, 정의 편집 권한만으로 그룹/예외를 변경할 수 없다. 서버는 클릭한 저장 대상과 현재 권한에 맞는 필드만 허용하며 다른 영역의 저장된 값은 보존한다.
- MASK는 컬럼 정의에서 선택한 현재 유효 maskingRef를 참조한다. 그룹별 마스킹 구현/파라미터를 따로 설정하지 않는다. 테이블 밖 그룹·중복 예외·미지원 유형/자료형을 거부한다. 사용자 그룹 제거를 저장하면 서버는 제거한 그룹의 해당 카탈로그 컬럼 예외도 같은 트랜잭션으로 함께 삭제한다. 예외를 먼저 삭제하도록 요구하지 않는다. 컬럼 예외만 삭제하는 저장은 사용자 그룹을 유지하고 해당 컬럼의 그룹 기본 권한으로 복귀한다. 매핑 OFF는 제거와 달라 예외를 휴면 보존한다. 매핑 OFF는 예외를 휴면 보존한다. 여러 활성 그룹 합집합 판정과 개인정보 사본 마스킹은 기존 정책을 따른다.

- 컬럼의 그룹 코드/상세 설명 정본은 REQ-301.value_domain이다. 공통 코드면 원천 그룹 코드를 전달해 데이터소스 가이드로 조회하고, 아니면 상세 설명의 명확한 하드 코딩 의미를 LLM이 해석한다. 모호하거나 없는 값을 만들어내지 않는다.
- 실제 원천 조회 결과는 실행 근거이며 카탈로그 저장 자식이 아니다. 공통 코드가 아닌 경우 상세 설명의 명확한 값/의미를 사용하며 모호함은 확인한다.
- LLM 문맥에는 현재 허용된 선택 카탈로그·컬럼과 그 데이터소스의 데이터 조회 가이드를 중복 제거해 제공한다. 필요한 코드/참조 테이블 스키마도 현재 권한으로 조회하고 read-only·신원/행 필터·마스킹/상한을 적용한다. 가이드 문구는 인가를 부여하거나 우회하지 않는다.
- 타입·필수·미정의 파라미터·상충 코드·결과/토큰 상한을 검증한다. 사용여부 Y를 일괄 강제하지 않으며 과거 상태 포함은 설정으로 명시한다. 값 확보 실패 시 LLM이 코드를 추측하여 실행하지 않는다.
- 테이블/뷰를 목록·조건·후보에서 구분한다. 뷰 NULL/길이는 제공 범위만 확인하고 원본 PK를 승계하지 않는다. 일반 뷰 물리 PK는 해당 없음, 지원/권한 불명은 확인 불가다. 업무상 유일키와 물리 PK는 구분한다.


- 자료형 선택은 `REQ-301.source_type_catalog`를 따른다. 공통 참조 조건 콤보 유틸/API-600에 그룹코드 `DBMS_DATA_TYPE`, 참조코드 `PARENT`, 참조값인 소속 DBMS 코드를 전달한다. DBMS별 활성 공통코드에서 선택하고 버전은 후보 필터로 쓰지 않는다. 코드 조회 실패/기존 비활성 코드/미등록 원천 타입을 표시하고 원문·입력을 보존한다. 자료형 코드와 당시 타입 원문을 따로 저장하며 실제 원천 자료형·치수 대조 전 검수 완료로 만들지 않는다.
- 컬럼 예외는 `REQ-103.column_group_exclusions`의 HIDE/MASK를 따른다. 대상 그룹은 같은 후보의 테이블 허용 그룹에서만 고른다. 중복·사유/유형 누락·테이블 밖 그룹을 거부하고 MASK에는 유효한 컬럼 마스킹 유형을 요구한다. 테이블 그룹 물리 제거 시 해당 그룹의 예외를 같은 저장에서 함께 삭제한다. 매핑 OFF는 삭제가 아니며 예외는 휴면 보존하고 다시 ON할 때 현재 마스킹/참조를 검증한다. 복수 그룹은 원본 > 마스킹 > 숨김의 기존 합집합 판정을 유지하며 개인정보 표시 컬럼의 이력 저장은 항상 마스킹한다.

- 전체 입력/자식·소유/종류·clientKey/안정 ID·기대 편집 버전·현재 권한을 서버에서 검증한다. 미완성 초안은 허용하되 존재하지 않는 참조·다른 소유·중복·비밀값·임의 SQL은 거부한다.
- 정확 식별·이름 변경은 FEAT-003.identity_contract, 값·키·관계·검수는 composition_contract를 따른다. 모든 필드/목록을 명시하며 생략과 빈 목록을 합치지 않는다.
- 실제 검증 DTO/오류의 MsgKey는 400 invalidInput / 409 versionConflict·referenceConflict·identityConflict·commandConflict / 503 dependencyUnavailable의 공개 계약에 연결한다. 현재 구체 오류 코드는 API 정본을 따르며 이 문서의 분류로 새 코드를 만들지 않는다.

- 수동 사용 여부와 실행 전 유효성 검사는 [REQ-601.asset_availability](../../../../spec/10-requirements/011-reference-integration.yaml)를 따른다. 현재 변경 권한자가 전체 소유 구성·기대 리비전·변경 이력과 함께 직접 저장한다. 승인 요청 절차를 추가하지 않는다.
- 화면은 수동 사용 여부만 제공하며 사용 가능 여부·사용 불가 사유 컬럼은 숨김 선택 열을 포함해 제공하지 않는다. 데이터소스 연결 문제는 SCR-002에서 확인하고 이 화면에 테이블별 진단 열을 중복하지 않는다. 서버는 데이터소스 누락·연결 유효성 확인 불가 시 해당 데이터소스의 모든 테이블·뷰 업무 SQL 접근을 차단한다. 관리용 메타데이터·이력 조회는 현재 권한에 따라 유지한다.
- 기술 오류나 복구는 수동 사용 설정을 덮어쓰지 않는다. 저장된 정의·워크플로우의 신규/재개/재시도도 실제 사용 직전 현재 수동 설정·유효 적용본·참조·현재 권한을 검사한다. 이미 전송/완료한 외부 업무를 소급 취소·자동 재전송하지 않는다.
- 수동 OFF 카탈로그는 새 LLM 컨텍스트·SQL 계획/실행에서 제외한다. 과거 SQL·저장 정의·워크플로우가 정확 카탈로그/버전을 보관해도 현재 수동 중지·연결 무효를 우회하지 않는다.

### 6-2. 영향 테이블

- REQ-601.management_storage가 저장 정본이다. 직접 저장 성공 때 본 데이터·마스터 REVISION·전체 _HIST·명령 결과를 원자 확정한다. 요청 원장·_SNP는 새로 생성하지 않는다.
- 업무 컬럼만 복사하고 기존 REG 값을 유지하며 MOD 값과 결과 리비전은 서버가 확정한다. 자식만 변경해도 마스터 리비전을 한 번 올린다.
- 원천 관측/업무 근거 ENT-010/027은 품질 조사·구조 비교 소유에서 관리한다. 카탈로그 저장 메모와 합치지 않는다.

### 6-3. 상태 전이

적용본 조회 → 영역별 편집 → 해당 영역 저장 버튼·고정 saveTarget → 사유 메모 → 권한·기준/전체 참조 검증 → 해당 영역 반영·전체 이력 원자 저장 → 해당 영역/기준 갱신, 다른 입력 보존.
응답 유실은 원 키/입력으로 결과 확인·재시도한다. 동일 성공을 다시 반영하거나 리비전을 추가 증가시키지 않는다.

### 6-4. LLM 입력 준비

[REQ-610](../../../../spec/10-requirements/012-reference-business.yaml)의 `prompt_contract.admin_input_preparation.sources.catalog`가 이 화면의 **프롬프트 포함 후보 / 서버 집행 / 관리·감사 항목**, 해석 가이드 및 제공 단계·조건을 정의한다. §4의 실제 컬럼과 대응하며 공통 해석 규칙은 같은 절의 `guides`·`conditions`·`stages`를 따른다.

화면 목록/상세 응답을 그대로 모델에 전달하지 않는다. 기존 관리 값을 사용하고 입력 분류용 컬럼·탭을 추가하지 않는다. 실제 조합·전송과 최종 JSON/CLI·API 계약은 업무 지식 관리·전체 흐름 합의 뒤 소유 작업흐름에서 구체화한다. 아래 검수는 설계 대조이며 목업에서 LLM 호출을 시연하거나 제품 실행 검증을 완료한 것으로 표시하지 않는다.

## 8. 시드 · 데이터 전제

- 메뉴/메시지/공통코드·API 시드는 소유 G3·화면 승인 후 생성/추가한다. 위 MSG 이름은 의미 연결 초안이며 아직 등록하지 않는다.

- 반출 허용 속성·현재 마스킹/권한 계약은 REQ-301.open과 FEAT-003.pending에서 완성한다. 표의 엑셀 허용 예시는 해당 계약과 READ+EXPORT가 충족된 검토 상태다. 확인 불가 또는 미완성 배포는 반출을 활성화하지 않는다.

- @defer P3 access_policy·knowledge — 그룹 후보/당시 정책의 정확 형식·컬럼 개인정보/마스킹 참조·그룹 참조 무결성·권한 회수 동시성/세트 저장 계약. 확인 불가/미완성 상태를 유지한다.
- @defer P3 integration·agent — DBMS 정확 객체·식별 profile 이행/실행 환경·일괄 비교 상한·실행/불일치 이력 계약. 샘플링은 재요청 전까지 제외한다.
- @defer P3 knowledge·audit_trace — 고정/실제 저장 세트 결과·이력 보존과 늦은 명령 재수신 계약. 검증 결과를 접수/반영 허가로 쓰지 않는다.
- @defer P3 integration_assets — 사이즈의 형식/단위/미확인과 인덱스 정의·순서 구성·완전성의 물리 저장/검증·복사/고정·이행을 ENT-006/007 및 공개 전체 후보 계약과 설계한다. 현재 기존 물리 표에 신규 저장 컬럼이 존재하는 것으로 취급하지 않는다.
- @defer P3 integration_assets — 실제 코드값/DTO 필드·구체 응답/오류 메시지, 전체 화면 승인과 구현 슬라이스 착수 전 정합화. 작업영역 5개 의존 조건을 유지한다.
