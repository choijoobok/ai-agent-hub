# 요건 정의서 — 스키마 카탈로그

## 개요

- **무엇을 하는 화면인가**: 고객사가 공개한 테이블·뷰와 등록 컬럼의 최종 적용값을 조회하고 변경 내용을 입력하며 관계는 읽기 전용 요약으로 확인한다. 관계 편집은 별도 SCR-039가 맡는다.
- **프로세스상 위치**: (선행) 데이터소스·공개 대상 선정 → **이 화면의 적용본 조회/변경 입력** → (후행) 자산 변경 세트의 검증·직접 저장·이력 반영.
- **이 데이터를 누가 쓰나**: 지식·인증 예제·agent 조회 계획. 현재 운영본·제출본·미완성 초안을 구분하며 현재 접근/정책을 별도 재검증한다.
- **바꾸면 어디가 흔들리나**: 연결 지식·인증 예제·관계·조회 제약의 의미와 참조 버전. 원천 구조 정상만으로 업무 의미 변화가 없다고 판단하지 않는다.

> 미구현 설계 초안이다. [REQ-301/304/306](../../../../spec/10-requirements/007-knowledge-catalog.yaml), [FEAT-003/011](../../../../spec/31-features/002-admin.yaml), [카탈로그 저장/공개 계약](../../../../spec/50-api/005-admin-catalog-contracts.yaml)이 정본이다. 현재/이력 저장의 공통 경계는 REQ-601.management_storage를 따른다.

## 1. 화면 구성

[조회조건 / 조회·신규·저장 또는 저장]
[현재 적용 카탈로그 목록]
[컬럼 정의 · 테이블 정의 · 접근 그룹 · 컬럼 그룹 예외 · 인덱스 · 코드 값 · 코드 바인딩 · 조회 코드 값 · 변경 근거 · 근거 대상 · 사용처]

- 목록·상세는 최종 적용본만 조회한다. 선택한 마스터의 적용 리비전을 기준으로 전체 구성의 임시 편집을 시작한다.
- 변경 권한을 부여받은 소수의 업무 전문가와 관리자만 소유 범위의 전체 구성을 직접 저장한다. 메뉴 표시뿐 아니라 서버가 저장 직전 현재 액션·대상 범위 권한, 자기 기준 리비전, 필수 참조와 기술 검증을 확인한다. 검증된 전체 변경과 변경 전후 이력·변경자·시각·사유는 같은 트랜잭션으로 반영한다. 일반 admin 계정이나 조회 권한만으로 변경할 수 없다. 별도 승인 요청·검토자/승인자 판정·전결/승인 사용 설정은 제공하지 않는다.
- 저장 성공 후 최신 적용본을 조회한다. 저장 실패·결과 불명은 입력과 원 명령 키를 보존한다.
- 신규 입력은 미저장 편집 상태이며 전체 검증과 저장이 성공한 뒤 운영 목록에 표시한다.
- 관리 화면에 내용 버전/이력 탭을 두지 않는다. 실제 반영 이력은 별도 원 화면 상속 이력에서 읽는다.
- 각 탭은 그리드 하나이며 같은 전체 편집본을 공유한다. 관계는 읽기 전용 요약과 SCR-039 연계로 확인하고 미열람 관계도 전체 저장에 보존한다.
- 코드 값/바인딩·그룹 예외·인덱스의 업무 검증은 REQ-301·103·111과 FEAT-003/011을 따른다. 원천 관측·사용처는 저장 대상이 아니다.
- 현재 열람 권한 안의 사용처 식별자·이름·종류·리비전·참조 경로만 조회한다. 지식 본문을 모아 업무 의미의 영향이나 보완 필요성을 판정하지 않는다. 내용 적합성 검토는 운영·유지보수 조직의 자체 절차이며 이 화면에 검토 작업을 만들거나 저장의 필수 단계로 요구하지 않는다. 조회 실패·열람 제한을 참조 없음으로 처리하지 않으며 현재 참조 무결성과 기술 계약 검증은 유지한다.

### 1-1. 마스터-디테일 연동

- 최초 및 행 선택은 CURRENT 문맥의 전체 구성을 읽는다. 마스터 REVISION으로 충돌을 검사하며 탭별 독립 업무 리비전은 없다.
- 저장은 전체 관리 구성과 BASE_REVISION을 전달한다. 현재 구성과 _HIST의 원자 저장 경계는 REQ-601.management_storage를 따른다.
- 적용 이력은 HISTORY_NO로 별도 이력 화면에서 전체 세트를 읽고 현재 탭 데이터를 섞지 않는다.
- 미저장 변경이 있는 행 전환·조회·이탈은 확인하고 취소하면 입력을 보존한다. 저장/결과 불명 중에는 원 키와 입력으로 결과만 확인한다.
- 별도 SCR-042는 이 화면의 조회조건·배치·탭을 읽기 전용 상속하고 변경 요약과 이력 저장일시 범위만 추가한다.

### 1-4. 컬럼 셀의 설정 창

같은 데이터소스에서 검수·활성화된 조회 정의와 정확한 버전을 선택한다. 고객사 코드 테이블 구조·조인은 데이터소스의 SQL이 담당하며 이 창에서 구조를 추정하지 않는다. 선택 후 코드 바인딩 탭에서 그룹코드·언어·사용여부 등을 입력하고 조회 코드 값 탭에서 조회한다. 설정은 전체 저장/반영 전 운영에 적용되지 않는다.

| 선택창 | 필드 | 입력방식 | 예시 | 후보 예시 | 상위 필드 | 후보 매핑 |
|---|---|---|---|---|---|---|
| 코드 조회 설정 | 조회 정의 | 검색콤보 | ERP 공통코드 / 버전 3 | ERP 공통코드 / 버전 3·주문 유형 코드 / 버전 1 | — | — |

내부에는 조회 정의/버전 ID를 보관하며 최신 버전으로 자동 전환하지 않는다. 목업 선택은 시연이고 실제 후보 조회·서버 검증은 구현 후 동작한다.

### 1-6. 수동 근거 접수 입력창

변경 근거 탭의 근거 접수를 누르면 모달 입력창을 연다. 이 화면에서는 상단에서 선택한 테이블에 대한 통지/업무 근거를 접수한다. 대상 추가로 같은 테이블의 관측 기준·전후·후보 버전을 여러 건 연결할 수 있고 마지막 대상은 제거하지 않는다. 다른 테이블은 해당 카탈로그를 선택해 접수한다. 데이터소스 관리의 원천 구조 비교는 서버가 수행하는 관측 경로이며 이 창에 구조 관측 결과를 수동 작성하지 않는다.

접수는 API-033의 별도 명령이다. 입력 내용은 선택한 카탈로그 저장에 합쳐지지 않는다. 성공을 확인한 뒤 변경 근거 목록을 다시 읽고 새 근거를 선택하면 근거 대상 탭에서 관련 테이블·버전을 확인한다. 실패/결과 불명에는 입력·원 명령 키를 보존하고 기존 결과 확인 규칙을 따른다. 관측 상태는 수동 접수 시 UNCONFIRMED이며 접수자/접수 시각은 서버가 기록한다. 원천 실제 시각을 입력해도 시스템 관측 완료로 승격하지 않는다. 목업의 접수 버튼은 입력 확인만 시연하며 실제 전송하지 않는다.

### 4-2. 편집 가능 판단 — 조건부

현재 SAVE/소유 권한 + 적용본 전체 구성 확보 + 기준 리비전 일치에서만 임시 변경 입력을 편집한다. 관계 입력은 이 화면에서 제공하지 않으며 관리 카탈로그의 전체 후보 관계/쌍은 보존한다. 정책 값·서버 검수자/시각·현재 리비전/식별키는 편집하지 않는다.

### 4-3. 값 변경 후 연쇄 · 재계산

구조/의미/값/키/관계 변경은 해당/의존 검수를 무효화한다. CODE/INLINE 모드 변경 시 다른 모드 자식을 명시 제거/보완하며 서버가 남은 부적합 자식을 거부한다. 데이터소스는 기존 카탈로그에서 고정하고 이름 변경으로 다른 물리 실체 이전을 우회하지 않는다.

### 4-4. 팝업 · 모달 선택 결과 매핑

API-028의 선택적 원천 객체 확인과 수동 입력, API-036의 등록 컬럼/키 후보 선택과 코드 조회 정의 후보 계약을 셀 선택 창에 연결한다. 전달값은 소유 catalogId와 명시 readContext·용도·현재 권한, 결과는 정확 대상/선택 버전·역할이다. 후보 페이지에 없음을 MISSING으로 추정하지 않는다. 관계 생성·관리측 고정·전체 쌍 편집은 SCR-039에서 상세 설계한다. 신규 clientKey의 같은 저장 내부 참조와 서버 memberId 매핑을 구분한다.

### 4-5. 행 추가 기본값

신규 구성은 clientKey를 부여하고 확인하지 않은 의미/검수/차원은 UNKNOWN 또는 미지정으로 둔다. 개인정보 아님·검수 완료·임의 시간대/조인 관계를 자동 선택하지 않는다. 코드/공통코드의 실제 허용값은 소유 계약을 따른다.
복사/복원은 같은 카탈로그의 새 DRAFT이며 원본 버전과 현재 기준 버전을 별도로 기록한다. 과거 직접 정책·기존 검수 완료를 새 내용/현재 권한의 근거로 자동 복사하지 않는다. 원천 DB 기본값은 관리하지 않는다. 사이즈와 인덱스 메타데이터는 REQ-301.column_workspace/index_metadata에 따라 후보에 포함하며 물리 저장 매핑은 후속이다. DB 구조 변경 기능은 없다.

### 4-6. 비노출 저장 컬럼

OBJECT_KEY·COLUMN_KEY·명령 지문 및 명령/서버 검수 근거는 서버가 계산/검증한다. 정정/이름 변경의 사용자 근거를 지문/서버 식별 근거로 대체하지 않는다. 1:N 값은 자식 테이블에 저장하며 화면 표시 문자열을 DB의 짧은 연결 문자열로 저장하지 않는다.

- 원천 구조 비교는 데이터소스 SCR-002에서 수행하며 이 화면에는 비교/샘플 조회 탭·버튼이 없다. 신규 객체 확인은 선택적인 입력 보조로 유지한다. 샘플 조회 기능은 현재 구현 범위에서 제외한다.


- 테이블 관계는 [테이블 관계](../catalog-relation/requirements.md)에서 관리한다. 관계·그룹 편집은 같은 카탈로그 전체 구성을 보존하며 이동 전 미저장 입력 확인·현재 권한 재검사를 적용한다. 숨은 탭/미조회 관계를 삭제로 간주하지 않는다. SCR-042 이력은 원 화면 상속이다.

## 6. 규칙 — 저장 · 실행

### 6-1. 검증

- 코드 설정 정본은 REQ-301.value_domain이다. CODE는 등록 조회 정의/정확 버전/정형 바인딩, INLINE은 직접 값/명칭이다. 기존 코드 테이블·값/명칭 컬럼·AND 동등 조건 방식은 사용하지 않는다.
- 조회 코드 값은 현재 원천/유효 캐시 관측이며 카탈로그 버전 자식이 아니다. 실패·빈 목록·상한 초과를 구분하고 과거 정의로 실행해도 당시 원천 목록으로 표시하지 않는다. 오래된 성공값으로 무단 대체하지 않는다.
- LLM 문맥은 현재 허용된 선택 컬럼만 모으고 데이터소스·정확 정의 버전·typed 바인딩·현재 권한 문맥이 같으면 한 번 조회한다. 원천 객체·컬럼과 조회 정의의 현재 권한/마스킹/전송 정책을 재검사한다.
- 타입·필수·미정의 파라미터·상충 코드·결과/토큰 상한을 검증한다. 사용여부 Y를 일괄 강제하지 않으며 과거 상태 포함은 설정으로 명시한다. 값 확보 실패 시 LLM이 코드를 추측하여 실행하지 않는다.
- 테이블/뷰를 목록·조건·후보에서 구분한다. 뷰 NULL/길이는 제공 범위만 확인하고 원본 PK를 승계하지 않는다. 일반 뷰 물리 PK는 해당 없음, 지원/권한 불명은 확인 불가다. 업무상 유일키와 물리 PK는 구분한다.


- 자료형 선택은 `REQ-301.source_type_catalog`를 따른다. 공통 참조 조건 콤보 유틸/API-600에 그룹코드 `DBMS_DATA_TYPE`, 참조코드 `PARENT`, 참조값인 소속 DBMS 코드를 전달한다. DBMS별 활성 공통코드에서 선택하고 버전은 후보 필터로 쓰지 않는다. 코드 조회 실패/기존 비활성 코드/미등록 원천 타입을 표시하고 원문·입력을 보존한다. 자료형 코드와 당시 타입 원문을 따로 저장하며 실제 원천 자료형·치수 대조 전 검수 완료로 만들지 않는다.
- 컬럼 예외는 `REQ-103.column_group_exclusions`의 HIDE/MASK를 따른다. 대상 그룹은 같은 후보의 테이블 허용 그룹에서만 고른다. 중복·사유/유형 누락·테이블 밖 그룹을 거부하고 MASK에는 유효한 컬럼 마스킹 옵션을 요구한다. 테이블 그룹 축소 시 해당 예외를 함께 제거한다. 복수 그룹은 원본 > 마스킹 > 숨김의 기존 합집합 판정을 유지하며 개인정보 표시 컬럼의 이력 저장은 항상 마스킹한다.

- 전체 입력/자식·소유/종류·clientKey/안정 ID·기대 편집 버전·현재 권한을 서버에서 검증한다. 미완성 초안은 허용하되 존재하지 않는 참조·다른 소유·중복·비밀값·임의 SQL은 거부한다.
- 정확 식별·이름 변경은 FEAT-003.identity_contract, 값·키·관계·검수는 composition_contract를 따른다. 모든 필드/목록을 명시하며 생략과 빈 목록을 합치지 않는다.
- 실제 검증 DTO/오류의 MsgKey는 400 invalidInput / 409 versionConflict·referenceConflict·identityConflict·commandConflict / 503 dependencyUnavailable의 공개 계약에 연결한다. 현재 구체 오류 코드는 API 정본을 따르며 이 문서의 분류로 새 코드를 만들지 않는다.

### 6-2. 영향 테이블

- REQ-601.management_storage가 저장 정본이다. 직접 저장 성공 때 본 데이터·마스터 REVISION·전체 _HIST·명령 결과를 원자 확정한다. 요청 원장·_SNP는 새로 생성하지 않는다.
- 업무 컬럼만 복사하고 기존 REG 값을 유지하며 MOD 값과 결과 리비전은 서버가 확정한다. 자식만 변경해도 마스터 리비전을 한 번 올린다.
- 근거 접수는 ENT-010/027에서 현재/이력 문맥을 명시하며 과거 내용을 수정하지 않는다.

## 8. 시드 · 데이터 전제

- 메뉴/메시지/공통코드·API 시드는 소유 G3·화면 승인 후 생성/추가한다. 위 MSG 이름은 의미 연결 초안이며 아직 등록하지 않는다.

- 반출 허용 속성·현재 마스킹/권한 계약은 REQ-301.open과 FEAT-003.pending에서 완성한다. 표의 엑셀 허용 예시는 해당 계약과 READ+EXPORT가 충족된 검토 상태다. 확인 불가 또는 미완성 배포는 반출을 활성화하지 않는다.
