# 요건 정의서 — 요청함 처리

## 개요

- **무엇을 하는 화면인가**: 사용자가 낸 요청(권한 신청 · 잠금 해제 · 기타)을 **처리하거나 반려한다.** 결과와 사유가 **요청자에게 알림으로 간다.**
- **프로세스상 위치**: (선행) 사용자가 알림 모달에서 요청을 낸다 → **이 화면**(판정) → (후행) 실제 조치는 다른 화면에서 한다 — 권한은 `ROLE_AUTH_MGMT`·`USER_AUTH_MGMT`, 잠금 해제는 `USER_MGMT`. **이 화면은 판정만 기록한다.**
- **이 데이터를 누가 쓰나**: 알림 모달의 **내 요청 탭**(사용자 측 · 별도 공통 경로).
- **바꾸면 어디가 흔들리나**: **되돌아가는 전이가 없다** — 한 번 처리하거나 반려하면 그 상태가 끝이다. **반려 사유가 그대로 요청자에게 간다.**

> **편집 열이 통째로 없는 첫 화면이다.** *그리드가 목록이자 편집 화면* 의 예외이며 이유가 셋이다 — 처리는 **저장이 아니라 판정**이고, **부수 효과가 있고**(요청자에게 알림이 나간다), **반려는 두 값을 함께 강제**해야 하는데 셀 하나로는 안 된다.

> **대기열이라 오름차순이다 — 이력 셋과 반대다.** 이력은 *"방금 무슨 일이 있었나"* 를 묻지만 여기는 **할 일 목록**이고, 대기열은 **오래 기다린 것이 먼저**다. 최신을 위에 두면 **가장 오래 방치된 요청이 목록 맨 아래로 밀려 영원히 안 보인다.**

> **비어 있는 것이 정상인 유일한 화면이다.** 대기열이 비었다는 것은 **좋은 소식**이고 그렇게 읽혀야 한다.

> **이 문서는 구현된 소스에서 역으로 작성했다**(2026-09-03).

## 1. 화면 구성

```
[조회조건 — 넷]
[그리드: 요청]   ⓐ [처리]  ⓑ [반려]        ← 다중 선택. 편집 열이 없다
[모달: 처리 / 반려 — 방향에 따라 다르다]
```

- 진입 시 자동 조회: **안 함.**
- 모달: **처리·반려 모달** 하나(방향으로 갈린다).
- 쪽수: 기본 **50** · 후보 `50 · 100 · 500` — **처리 대기를 훑는 화면이라 넘기며 보는 것보다 한눈에 보는 것이 낫다.**
- 하단 pane 이 없다 → **다중 선택**을 연다.

## 2. 조회조건

| 조건 | 대상 컬럼 | 입력방식 | 연산 | 필수 | 기본값 | 라벨 키 |
|---|---|---|---|---|---|---|
| 요청 기간 | `CRE_DTM` | 날짜(기간) | `between` | **아님** | **비어 있음** | `MSG.NOTI_REQUEST_SEARCH_PERIOD` |
| 상태 | `REQ_STAT_CD` | 셀렉트(다중) | `in` | 선택 | **`접수` 하나** | `MSG.NOTI_REQUEST_SEARCH_STAT` |
| 유형 | `REQ_TYPE_CD` | 셀렉트(다중) | `in` | 선택 | — | `MSG.NOTI_REQUEST_SEARCH_TYPE` |
| 요청자 | `SYS_USER.USER_NM` | 텍스트 | `contains`(기본) · `eq` · `startsWith` | 선택 | — | `MSG.NOTI_REQUEST_SEARCH_USER` |

- **상태의 기본값이 `접수` 하나다.** 처리함은 **할 일 목록**이다 — 전체를 기본으로 두면 **처리된 것이 대기 중인 것을 덮는다.** `NOTICE_MGMT` 의 기본값과 방향이 같고 **더 좁다.**
- **기간의 기본값이 비어 있다.** 대기열에서 기간을 기본으로 걸면 **가장 오래 방치된 요청이 기본 조회에서 사라진다** — 그것이 이 화면이 정확히 보여줘야 하는 행이다. **좁히기는 `상태` 가 한다.**
- **기간이 필수가 아니다** — 이력의 근거가 대용량인데 **요청은 수천 건**이다.
- **`처리 메모` 조건이 없다** — 실을 수는 있지만 **관리자가 그때 쓴 문장**이라 형식이 없다. 조건으로 열면 부분 일치가 되고, **그 물음에 답하는 것은 상태**다.
- **요청자를 이름으로 찾는다** — 로그인 ID 로 찾는 사람은 계정을 조사할 때뿐이고 그 화면은 `USER_MGMT` 다.

`○` = 기본 숨김.

- **`editable` 이 붙은 컬럼이 하나도 없는 것이 이 표의 요점이다.** 편집을 열면 **저장할 곳이 없는 셀**이 생기고, 이 화면에는 **저장 경로 자체가 없다** — 상태는 모달로만 바뀐다.
- **읽기 전용이어도 열린다.** 요청 내용과 처리 메모는 2000자라 셀 한 줄에 안 들어간다 — *읽기 전용이 못 본다를 뜻하지 않는다.* **`nclob` 이 아닌 컬럼에 그 규약이 적용되는 첫 사례**이며, *"읽기 전용 셀입니다"* 라는 거부가 **여기서는 나오지 않는다**: 거부할 것이 아니라 보여줄 것이기 때문이다.
- **처리 메모가 중요한 이유**: 반려 사유가 여기 있고 **그것이 요청자에게 간 문장**이다.
- **미사용 계정이면 이름 옆에 표시가 붙는다**(`MSG.NOTI_REQUEST_USER_DISABLED`) — *지금 로그인할 수 없는 사람* 임을 알리되 **처리는 막지 않는다**: 요청은 **계정이 살아 있을 때 낸 것**이다.
- **`(삭제된 사용자)` 라는 상태가 없다** — 계정은 물리 삭제를 하지 않으므로 고아가 생기지 않는다(`BATCH_HISTORY` 의 *(삭제된 배치)* 와 갈리는 자리).
- **처리자가 비어 있으면 *아직 아무도 안 봤다* 의 표시다.**

**배지 둘 — 값은 코드이고 글자만 라벨이다.**

| 상태 | 색 |
|---|---|
| `RECEIVED` 접수 | 칠하지 않음 |
| `DONE` 처리 | 정상 |
| `REJECTED` 반려 | 주의 |

| 유형 | 색 | 왜 |
|---|---|---|
| `ROLE_GRANT` 권한 신청 | 칠하지 않음 | — |
| **`UNLOCK` 잠금 해제** | **주의** | **지금 못 들어오고 있는 사람**이라 기다리는 비용이 다르다 — 권한 신청은 하루 늦어도 일이 되고, **잠긴 계정은 그동안 아무것도 못 한다** |
| `ETC` 기타 | 회색 | — |

- **유형은 공통코드가 아니라 소스의 값이다** — 관리자가 늘리면 **처리 코드가 없는 값이 생긴다.**
- **모르는 값은 글자로 옮기되 지어내지 않는다**(문자열이 아니면 빈 칸).

### 4-2 ~ 4-6

- 편집 · 연쇄 · 행 추가 기본값 · 비노출 저장 컬럼: **전부 없음.**
- 팝업 결과 매핑: **모달은 값을 돌려주지 않고 실행한다**(§5-1).

## 5. 버튼 · 액션

| 버튼 | 라벨 키 | 액션 | 활성 조건 | 동작 |
|---|---|---|---|---|
| 조회 | (공통) | `R` | 항상 | 목록을 읽는다 |
| ⓐ 처리 | `MSG.NOTI_REQUEST_ACTION_DONE` | **`S`** | **§5-2** | 모달을 연다 |
| ⓑ 반려 | `MSG.NOTI_REQUEST_ACTION_REJECT` | **`S`** | **§5-2** | 모달을 연다 |

- **`api.actions` 가 아니라 임의 컨트롤이다.** 표준 액션은 *고른 행을 서버에 넘긴다* 는 한 모양인데, **여기는 모달이 값을 하나 더 받아야** 하고 **그 값의 필수 여부가 방향마다 다르다.**
- 저장 · 행 추가 · 행 삭제 · 엑셀 · 진행률 창: **없음.**
- **다중 선택**을 연다 — 확인 모달이 *요청 N건* 을 말한다.

### 5-1. 처리 · 반려 모달 — **비대칭이 의도다**

| | 처리 | 반려 |
|---|---|---|
| 제목 | `MSG.NOTI_REQUEST_MODAL_DONE` | `MSG.NOTI_REQUEST_MODAL_REJECT` |
| 안내 | `MSG.NOTI_REQUEST_DONE_NOTICE` — **알림이 들어간다** | `MSG.NOTI_REQUEST_REJECT_NOTICE` — **사유가 상대에게 간다** |
| 메모 | **선택** | **필수** |
| 메모 상한 | 2000자 | 2000자 |

- **처리는 결과 자체가 답이지만 반려는 이유가 없으면 답이 아니다** — 사유 없는 반려는 **요청자가 같은 요청을 다시 내게 만들고**, 그것이 워크플로를 만들지 않기로 한 대가를 실제 비용으로 바꾼다.
- **확인 문구가 실행마다 다르다.** 일반 문구는 *무엇을 몇 건* 만 말하는데, **반려에서 중요한 것은 사유가 상대에게 간다는 사실**이다 — 그것을 모르고 쓴 메모가 그대로 나간다. 처리 쪽은 **알림이 들어간다**는 사실을 말한다 — **되돌리는 길이 없으므로 누르기 전에 알아야 한다.**
- **모달은 열 때마다 새로 마운트되어 사유 칸이 저절로 빈다.** 비우는 것이 중요한 이유는 **그 메모가 다른 사람에게 가기 때문**이다 — 앞서 반려하며 쓴 사유가 남아 있으면 **다음 처리에 딸려 간다.**
- 선택에 미사용 계정이 있으면 모달이 그 사실을 알린다.

### 5-2. **섞이면 전부 막는다**

```
버튼이 활성 = 선택이 1건 이상  AND  전부 REQ_STAT_CD='RECEIVED'
```

- **처리 가능한 것만 골라 실행하지 않는다** — 일부만 처리하면 **알림이 일부에게만 나가고** 사용자는 무엇이 처리됐는지 모른다. **되돌리는 길이 없으므로 부분 성공을 만들지 않는다.**
- **왜 눌리지 않는지 말한다**(`MSG.NOTI_REQUEST_HINT_NOT_RECEIVED`). 선택이 0건인 것은 눈에 보이지만 **이미 처리된 것이 섞인 것은 안 보인다** — 고른 행이 다섯인데 버튼이 죽어 있으면 **사용자는 권한을 의심한다.**
- **서버도 같은 것을 다시 본다.** 대상 요청 행을 `REQ_ID` 오름차순으로 잠근 뒤 상태를 확인하므로, 동시에 같은 요청을 판정하면 먼저 잠금을 얻은 호출만 처리하고 뒤 호출은 `ERR_NOTI_REQ_NOT_RECEIVED`(409)로 끝난다. 결과 알림은 한 건만 생긴다.

### 5-3. 실행 뒤

- **다시 읽는다.** 상태와 처리자·처리일시가 서버에서 채워지고, **기본 조건이 `접수` 라 처리한 행은 목록에서 사라진다** — **그것이 대기열의 정상 동작이며 *처리됐다* 의 가장 분명한 신호다.**

## 6. 규칙 — 저장 · 실행

### 6-1. 검증

| # | 시점 | 위치 | 검사 | 위반 시 메시지 |
|---|---|---|---|---|
| 1 | 실행 | 서버 | 대상 요청이 있는가 | `MsgKey.ERR_NOTI_REQ_NOT_FOUND` |
| 2 | 실행 | 화면+서버 | **선택 전부가 `접수` 인가** | `MsgKey.ERR_NOTI_REQ_NOT_RECEIVED` |
| 3 | 반려 | 화면+서버 | **사유 필수** | `MsgKey.ERR_NOTI_REQ_MEMO_REQUIRED` |
| 4 | 실행 | 서버 | 같은 요청을 동시에 판정하면 대상 행 잠금 뒤 현재 상태를 다시 확인 | 뒤 호출은 `MsgKey.ERR_NOTI_REQ_NOT_RECEIVED`(409), 추가 알림 없음 |

**사용자 측(요청 등록)의 검증**은 이 화면의 것이 아니다 — `ERR_NOTI_REQ_CONTENT_REQUIRED`(내용 필수) · `ERR_NOTI_REQ_DUPLICATE`(같은 유형의 접수된 요청 중복)는 알림 모달이 받는다.

### 6-2. 영향 테이블

| 트리거 | 테이블 | 작업 | 조건 · 내용 |
|---|---|---|---|
| 처리 · 반려 | `SYS_NOTI_REQUEST` | UPDATE | `REQ_STAT_CD` · `HANDLER_ID` · `HANDLE_DTM` · `HANDLE_MEMO` **넷** |
| 처리 · 반려 | `SYS_NOTI_INBOX` | **INSERT** | **요청자에게 결과 알림** |

- **한 트랜잭션**이다.
- **처리와 반려가 한 경로다** — 쓰는 컬럼이 같고 트랜잭션이 같다. **둘로 가르면 알림 INSERT 코드가 두 벌이 되고 한쪽만 고치는 날이 온다.**
- **이 화면은 실제 조치를 하지 않는다.** 권한을 주거나 계정을 푸는 것은 다른 화면의 일이며, **여기는 판정만 기록한다.**

### 6-3. 상태 전이 — **되돌아가는 전이가 없다**

| 지금 | 동작 | 다음 |
|---|---|---|
| `RECEIVED` 접수 | ⓐ 처리 | `DONE` |
| `RECEIVED` 접수 | ⓑ 반려 | `REJECTED` |
| `DONE` · `REJECTED` | — | **끝** |

- **한 번 정하면 되돌릴 수 없다.** 잘못 처리했으면 사용자가 **요청을 다시 내야** 한다.

## 7. API

| 용도 | `endpoints.ts` 키 | 경로 | 메서드 | 액션 | 페이징 |
|---|---|---|---|---|---|
| 목록 | `getList` | `/service/system/notiRequest/getList` | POST | R | offset |
| **처리 · 반려** | `updateHandle` | `/service/system/notiRequest/updateHandle` | POST | **S** | — |

- **`updateHandle` 이 `SAVE` 다** — 경로 접두가 정하며, *우리 테이블의 컬럼을 쓰는가* 라는 기준으로 봐도 그렇다: 처리는 `SYS_NOTI_REQUEST` 의 **컬럼 넷을 쓴다.** `BATCH_HISTORY` 의 중단이 `EXECUTE` 였던 것과 **갈리는 자리**이며, **그쪽은 요청만 남기고 종결은 배치가 했지만 여기는 이 호출이 끝나면 상태가 끝난 상태**다.
- **처리와 반려가 한 경로**이며 상태 값이 가른다.
- **폴더가 인가 경계다** — 공지와 한 폴더에 두면 **공지 권한이 요청 처리를 연다.** 요청 처리는 **남의 요청을 판정하는 일**이라 그 사고의 대가가 크다.
- **사용자 측이 여기 없다** — 자기 요청의 상태 확인은 알림 모달의 *내 요청* 탭이며 공통 경로다.
- `exportExcel` 없음.

## 8. 시드 · 데이터 전제

- 코드그룹: **없음.** 유형 셋과 상태 셋은 **소스의 값**이다 — 값에 따라 처리 코드가 갈리므로 소스가 값을 가져야 한다.
- 메시지 키: 화면 `MSG.NOTI_REQUEST_*` · 서버 `MsgKey.ERR_NOTI_REQ_NOT_FOUND` · `ERR_NOTI_REQ_NOT_RECEIVED` · `ERR_NOTI_REQ_MEMO_REQUIRED`.
- 메뉴 시드: `menu-tree.yaml` — `code: NOTI_REQUEST` · `parent: NOTICE` · `url: /admin/system/noti-request`. **`export` 없음.**
- 초기 데이터 전제: 없음. 요청은 사용자가 만든다.
- 설정: `sys-config.retention.noti-inbox-days`(90) — **결과 알림의 보존.**

## 10. 미결 · 확인 필요

- **처리를 되돌릴 수 없다.** 잘못 처리하면 사용자가 요청을 다시 내야 한다 — *현재 답은 "부분 성공도 되돌림도 만들지 않는다" 이며 이것이 결정이다.*
- **이 화면이 실제 조치를 하지 않는다.** 처리를 눌러도 권한이 생기거나 계정이 풀리지 않는다 — **다른 화면에서 조치하고 여기서 판정을 기록하는 두 단계**다.
- **유형을 관리자가 늘릴 수 없다** — 늘리려면 소스를 고쳐야 한다.
